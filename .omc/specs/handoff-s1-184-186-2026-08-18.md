## 6. 🔴 SSL 제보의 진짜 원인 — Python 3.13 strict X509 (§1을 대체한다)

`aelix status`를 넣은 덕에 제보자에게 한 줄로 받을 수 있었고, 거기서 갈렸다.

**제보자 상태는 건강했다** — `state: active`, cafile 존재, capath 해시 있음, truststore 주입 성공.
그래서 "신뢰저장소 실패" 가설이 배제됐고, 남은 건 검증기 쪽이었다.

**실제 에러**: `certificate verify failed: Missing Authority Key Identifier (_ssl.c:1032)`

```
3.12.1   verify_flags = 32768    VERIFY_X509_STRICT OFF
3.13.13  verify_flags = 557088   VERIFY_X509_STRICT ON  (+PARTIAL_CHAIN)
```

* 그 절은 **strict에서만** 검사된다. `_ssl.c:1032`는 **3.13**의 줄 번호(3.12는 `:1000`).
* `openssl s_client`는 strict를 안 켜므로 같은 호스트에 `Verify return code: 0 (ok)`.
  curl·Node·브라우저·3.12도 마찬가지 → **"다른 도구는 다 되는데 이것만 안 된다" = 이 진단.**
* Palo Alto 프록시가 즉석 생성한 인증서에 AKI가 없다. **회사 CA는 정상 신뢰 중이었다.**
* `install.sh`는 `uv tool install`을 쓰고 그건 `.python-version`(3.12)을 안 본다 →
  **사용자 3.13 / 기여자 3.12.** 그게 "clone은 되고 설치는 안 된다"의 전부였다.

**들어간 것** (오너 결정: 세션 단위 자동 완화 + strict 해제 재검증):
`_tls_strict.maybe_relax_strict_for_session(exc)`를 4개 프로바이더 어댑터 + login_wizard +
copilot poll 루프에 배선. 검증 실패 시 같은 호스트를 strict만 끄고 재검증 → 통과하면 세션 완화,
아니면 무변경. **`CERT_REQUIRED`·호스트명·유효기간·신뢰 루트 체인은 유지.**

**설계에 쓸 사실 3개** (전부 실측):
1. seam은 `ssl.create_default_context` **하나** — httpx·OpenAI SDK·Anthropic SDK가 클라이언트당 1회 호출,
   aelix의 ~13개 클라이언트 지점 중 `verify=`를 넘기는 곳 **0**.
2. 🔴 **`ssl.SSLContext`를 서브클래스로 리바인딩 금지** — CPython `verify_mode` 세터가 모듈 전역을 다시 찾아
   무한 재귀(499프레임). truststore도 같은 이유로 래핑한다.
3. 예외에서 **호스트·verify_code 복구 가능** — `.request` + `__cause__` 체인.

**제보자 즉시 우회**: `uv tool install --force --python 3.12 <원래 인자>`

### 🔴 1차 수정이 한 단계 늦었다 — 제보자 재현으로 확인 (`1106389`)

제보자가 새 빌드를 돌리자 **탐지·재검증·완화까지 전부 작동**했는데(메시지에 신규 문구가 떴다)
**로그인은 여전히 실패**했다. 실패 호스트 `api.business.githubcopilot.com`이 단서였다 — 디바이스 플로우 호스트가 아니다.

```
1 디바이스 코드(github.com) 성공 → 2 브라우저 승인 성공 → 3 폴링 성공 → 4 토큰 교환(api.github.com) 성공
5 enable_all_github_copilot_models → 🔴 ~19개 정책 POST가 asyncio.gather로 동시 발사 → 전멸 → 재raise → 토큰 폐기
```

**동시 발사라 19개가 다 실패한 뒤에야 완화가 걸린다.** 그래서 "다음 /login은 되고 이번 건 실패"였고,
여기서 "다시"는 **브라우저 + 새 디바이스 코드**를 뜻한다.

→ 전멸 배치에 **측정 기반 재시도 1회**. 게이트는 더 느슨한 게 아니라 **같은 것**
(`maybe_relax_strict_for_session`이 재검증에 성공할 때만). 마법사는 완화 시 **"Run /login again"**을 명시한다
(`describe_provider_error`는 프로바이더 범용이라 자기가 `/login` 안에서 읽히는 줄 모른다).

🔴 **테스트 더블 주의**: `patch.object(_tls_strict, "maybe_relax_strict_for_session", ...)`는
`login_wizard`에 **안 닿는다** — 모듈 스코프로 이름을 바인딩하므로 **호출자 쪽 바인딩**을 패치해야 한다.

**남은 것**: 연결별 검증(세션 단위 대신)은 후속 — truststore OpenSSL 백엔드의
`_verify_peercerts_impl`이 no-op이라 재시도 훅이 없고 전송 계층 작업이 필요하다.

## 1. SSL 제보 1차 조사 (§6이 이걸 대체한다 — 기록용)

오너 제보: `git clone`+`uv sync`+`uv run aelix`는 되고, `uv tool install`+`aelix`는
**OAuth는 통과하는데 모델 쓸 때 SSL 에러**.

깨끗한 `git archive 51d26fa`로 두 환경을 만들어 세 다리 전부 실제 github.com에 때렸다:

| 다리 | Env A (`uv sync`) | Env B (`uv tool install`) |
|---|---|---|
| `/login/device/code` | 3/3 OK | 3/3 OK |
| `/login/oauth/access_token` | 200 pending → slow_down×5 | **동일** |
| `/copilot_internal/v2/token` | 401 JSON | **동일** |

**와이어에서 바이트 동일.** `_inject_truststore`의 주장도 참이었다(음성→양성 대조:
주입 후 httpx·anthropic SDK·openai SDK 셋 다 `truststore._api.SSLContext`).

🔴 **진짜 결함 = 진단 불가능성이었다.** `except Exception: pass`가 신뢰저장소 실패를 삼켜서
'작동 중'과 'certifi로 조용히 강등됨'이 밖에서 **완전히 같은 상태**였다.

→ `aelix status`가 이제 답한다. **다음 SSL 제보는 이 한 줄로 시작할 것:**

```bash
aelix status --no-extensions          # 사람이 읽는 형태
aelix status --no-extensions --json   # 제보자에게 그대로 받을 형태
```

읽는 법:
- `store: certifi only — truststore injection FAILED` → 회사 CA가 안 보인다. `! ` 줄에 원인 예외가 있다.
- `cafile ... ← MISSING` + `capath ... ← present but holds no hashed certs` → **아무것도 신뢰하지 않는다**.
- `CAs loaded: not reportable` 은 정상이다(OS 저장소는 열거를 안 한다). **`0`이면 진짜 0이다.**
- `interpreter ... uv-managed` → `install.sh` 경로로 깔린 것.

**아직 오너에게 필요한 것: 제보자의 OS와 SSL 에러 전문.** truststore는 OS별로 완전히 다른 백엔드를 쓴다
(Windows CryptoAPI / macOS Security / Linux OpenSSL). Linux 백엔드는 `capath` 해시가 있으면 구제되지만
5개 후보 경로가 다 없으면 CA가 0이 된다.
