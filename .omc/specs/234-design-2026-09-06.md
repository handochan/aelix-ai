## 0. Baseline

`_LocalBashOperations.exec`'s innermost `finally` does `watcher_task.cancel()`, then
`with contextlib.suppress(asyncio.CancelledError, Exception): await watcher_task`. `await` cannot
tell the watcher's own cancellation (the line above) from an **external** cancellation of the task
running `exec`, so the external one is swallowed and `exec` returns a normal `ExecExitResult`. The
comment claims it "is captured and re-raised at the `except asyncio.CancelledError` above" — that leg
is only on the stack when `_wait()` itself was cancelled, which it was not on either leg reaching here.

Measured on `main` `b94a6db`, **with an abort signal supplied** (see the reach row):

| probe | result |
| --- | --- |
| aimed cancel, `probe_a_deterministic.py` | **RED 6/6** — `ExecExitResult(exit_code=0, timed_out=False) cancelled=False`; 3 single- + 3 double-cancel rounds, 0.198 s |
| `probe_b_random.py 300 <seed>`, **ten runs**, seeds 234/99 | **LOST 3–7 per run**; aggregate **48 of 1967 delivered cancels = 2.44 %** (1.55–3.59 % per run), 1.1–1.2 s each |
| same, post-fix | **0 of 380** delivered cancels (600 rounds) and 0 of 6 aimed |
| **reach**, `probe_ab_signal.py` ×3 seeds | `signal=None` (what every shipped Esc path passes) **0 LOST of 524** requested over 900 rounds; `signal=AbortSignal` **14 of 388** |
| suites | `pytest tests/tools tests/pi_parity -q` → 683 passed, 17.98 s |

LOST = `task.cancel()` returned `True` **and** the task still finished with a normal result.
`cancel_requested` is the denominator, not `n` — 18–42 % of rounds found the command already
finished. **The seed fixes the delay *sequence* only**: `hi = median(exec) × 1.6` is re-measured every
run (3.5–6.0 ms observed), so the race outcome differs run to run. Any row is a sample; quote the range.

## A. Decision

Replace `await watcher_task` with `await asyncio.wait([watcher_task])`, delete the `suppress`, and
retrieve the watcher's exception in a `finally` around the wait. The four-`finally` order
(watcher → drain → detach → close) and every other teardown line stay as #222 left them.

`asyncio.wait` absorbs how the awaited task *finished* — cancelled or raised — as membership of the
`done` set, so the only thing that can come out of that `await` is the caller's cancellation
(measured on 3.11.15 and 3.12.13, stdlib-only and at the real site).

**Three dispositions of `_wait()` reach this `finally` and the fix does not treat them alike**
(measured, two module copies of the same blob):

| leg | `main` | with the fix |
| --- | --- | --- |
| **NORMAL** — `_wait` returned an int | `exit_code=0, timed_out=False`, 0.006 s | **CANCELLED**, 0.005 s — the window the issue is about |
| **TIMEOUT** — `_wait` caught `TimeoutExpired`, already ran `_end_the_tree(reap=REAP_GRACE_SECONDS)` + `_mark_the_kill()`, returned `None` with `_timed_out=True` | `exit_code=None, timed_out=True`, 0.305 s | **CANCELLED**, 0.310 s — **the timeout label is discarded** |
| **ABORT** — the signal fired, the watcher completed | `exit_code=None, timed_out=False`, 0.203 s | **identical**, 0.203 s — `cancel()` returns `False`, nothing to swallow |

The timeout row is a second observable change, **accepted deliberately**: the caller asked for the
call to stop, and a cancellation is a stronger statement than a timeout report. Stated in §B's
comment, the ADR and the CHANGELOG; pinned by §C.1. Owner question in §G.

**The retrieval is adopted, not rejected** (rev 1 rejected it on a measurement of one ordering):

- `Task.cancel()` disarms the GC report only for a watcher that had **already failed** —
  `cancel()`→`False`, `_log_traceback True→False`. That is the *only* ordering rev 1 measured.
- A foreign `signal.wait()` that fails **during its own cancellation** fails *after* that `cancel()`,
  and `Future.set_exception` sets `_log_traceback` back to `True` (measured `False→False→True` on
  3.11.15/3.12.13/3.13.13, C `_asyncio.Task`). `main`'s `await` retrieves that into the `suppress`; a
  bare `asyncio.wait` does not, so the loop reports `Task exception was never retrieved` at GC —
  a **regression against `main`** on the foreign-signal path.
- It must be in a `finally`. A retrieval written *after* the wait never runs when the caller's
  cancellation propagates out of the wait — the one window this issue exists for. Measured at the
  real site, four shapes × three watcher behaviours × cancel on/off: `main` silent; bare `wait`
  REPORTED in both `during-raises` arms; retrieval-after REPORTED under a concurrent cancel; the
  `finally` form silent in **all six** arms while still letting the cancel out. `watcher_task.done()`
  was `True` at the retrieval in every arm; the guard exists because `.exception()` on a pending task
  raises `InvalidStateError`.

Alternatives ruled out:

- **`await watcher_task` + re-raise when `current_task().cancelling()` is non-zero.** `cancelling()`
  counts every cancel ever requested on the task, including the one the ordinary Esc path already
  consumed at `_wait()` — it moves the guess. Also 3.11+ bookkeeping tangled with `uncancel()`.
- **`asyncio.gather(watcher_task, return_exceptions=True)`.** Measured **equally correct** — silent
  in all six arms (its done-callback retrieves eagerly) and it propagates the caller's cancel.
  Rejected on cost, not correctness: it cancels its children on an outer cancel where `wait` leaves
  them alone, and returns a value we would discard. Bare `wait` is the only shape measurably wrong.
  **`asyncio.shield`** does not help: the inner task's `CancelledError` still reaches the awaiter.

Two scheduling facts, because #230 and #233 read this teardown next. `asyncio.wait([<Task>])` emits
no `DeprecationWarning` on 3.11 (3.11 deprecates **coroutines**; a Task is fine) — measured `[]` under
`simplefilter("always")` on both. And `await asyncio.wait([t])` **always yields a loop turn**, even
for an already-done `t`, where `await t` does not suspend at all (`yielded_to_loop` `False`→`True`).
On the abort leg the watcher is normally already done, so the fix inserts one unconditional suspension
point between the disarm and the drain. Inert as far as anything here can measure (the ABORT row is
identical), but no case covers it and the next reader needs it written down.

```python
class _CancelsTheTurnFromInsideTheWatcher:
    """The whole signal surface ``exec`` needs (it starts the watcher on ``hasattr(signal, "wait")``)."""
    def __init__(self) -> None:
        self._event = asyncio.Event()
        self.exec_task: asyncio.Task[ExecExitResult] | None = None
        self.cancelled_the_turn = False
    async def wait(self) -> None:
        try:
            await self._event.wait()
        except asyncio.CancelledError:   # the teardown's own ``watcher_task.cancel()``
            assert self.exec_task is not None
            self.cancelled_the_turn = True
            self.exec_task.cancel()      # ... and now the caller's, at the exact instant
            raise                        # ``exec`` is suspended on the teardown's await
```

## G. Risks, open questions, out of scope

- **OPEN QUESTION FOR THE OWNER — the timeout label.** A cancellation landing in the teardown after a
  *timeout* kill is now delivered as a cancellation instead of
  `ExecExitResult(exit_code=None, timed_out=True)`, which `create_bash_tool` renders as its own label
  and retry guidance. This design chooses "the cancel wins" and says so in the ADR and CHANGELOG; it
  is adjacent to #230's policy question about the same window. If the owner prefers the timeout report
  to survive, the fix needs an extra arm and #234 should wait on #230 instead of landing ahead of it.
- **The decision no longer leans on CPython's private `_log_traceback`** — it retrieves explicitly, so
  a change to that flag cannot leak a warning; C.2 pins the observable on both interpreters.
- **Reach.** Only `--mode rpc`'s `bash` arms the watcher in the shipped product, so today the fix
  protects the RPC/embedder surface and stops the defect becoming reachable the moment `ctx.signal` is
  threaded. That dispatch task **is** cancellable from outside: `run_rpc_mode` drains with
  `await asyncio.gather(*pending_command_tasks, return_exceptions=True)`, where
  `return_exceptions=True` only stops a child's *failure* from cancelling siblings — an outer cancel
  still propagates (measured: `child.cancelled()=True`). SIGTERM/SIGHUP set `shutdown_event`, which
  reaches that gather, and `asyncio.run` cancels the main task on KeyboardInterrupt.
- **The probability numbers are a timing-dependent sample on one host, not a constant** — not
  reproducible from the seed, and 2.4 % is not a product-level Esc-loss rate (with `signal=None`, 0/524).
- **A second cancel** from the *same* synchronous stretch is one cancellation requested twice (the
  first cancels the wait's internal waiter; the second finds `_fut_waiter.cancel()`→`False` and sets
  `_must_cancel`, consumed by the error already in flight) (on the shipped teardown that second
  cancel needs a hop past `_on_completion`; inside one synchronous stretch the second `cancel()`
  still finds the waiter live). That is all `probe_a_deterministic.py`'s
  double-cancel rounds measure and the design claims no more. The second cancel that matters lands at
  a *different* suspension point — the outer `finally`'s `await _drain_to_the_end()`, which under the
  fix now runs with a `CancelledError` already unwinding, a state `main` never reached. C.4 is the
  case in that shape and case 10 covers the drain; not separately measured under 2× cancels.
- **#233 touches this same file.** Not to be batched with #234 (handoff §2); whoever lands second
  rebases **and re-runs `check_citations.py --fix`**, since the relocated numbers are a function of
  `bash.py`'s final length. Warn #233: a belt written `except BaseException: …` around this teardown
  re-introduces exactly this defect, and measured it reddens C.1 only (`1 failed, 261 passed`) — no
  real-children case unless C.4 lands. **#230** owns the policy of this window; **#232** owns the
  unbounded exit-path drain that delays delivery (2.03 s for a 2 s holder on the normal-exit leg).
- **Eight other `suppress(asyncio.CancelledError, Exception)` sites**: `tui/shell.py` ×4 (shutdown —
  the process is going away) and the OAuth login flows ×4 (`await manual_task` inside the suppress,
  where an Esc during `/login` is swallowed the same way). **File one follow-up to audit the OAuth
  pair before the session handoff**; do not touch them here.
- Not measured: the windows leg, and the win32 cost of C.1's timeout arm (≤5 s estimated from
  `REAP_GRACE_SECONDS` and `bash.py`'s own comment).
