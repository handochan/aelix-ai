## 오너 판단 (권고 포함)

1. **#334가 바꾼 동작.** 권고: 수용. pi와 같고, ADR-0023 #334 amendment와 CHANGELOG에 적었다.
   - 재시도 백오프나 closing compaction 중에 온 두 번째 `prompt()`는 `busy`로 거절된다. RPC는 busy를 돌려준다. TUI는 원래 Enter가 steer였으므로 그대로다.
   - `abort()`, 확장의 `ctx.abort()`, 기본 `ctx.shutdown()`, `dispose()`가 재시도, overflow 재실행, closing compaction을 멈춘다. 턴이 abort된 뒤 threshold를 넘었어도 compaction하지 않는다.
   - `wait_for_idle()`과 `dispose()`는 꼬리가 끝날 때까지 기다린다. 따라서 꼬리 안에서 그것들을 await하는 코드는 교착한다. CHANGELOG에 경고를 적었다.
2. **#334 C7.** `await harness.abort()`는 idle 전에 돌아온다. pi의 `abort()`는 `waitForIdle`한다. 알고 택한 divergence로 적고 #346으로 넘겼다. 권고: 수용.
3. **#334의 쓰기 시점 변화.** 공개 compaction 도중의 `append_message()`가 다음 턴의 turn_end flush가 아니라 **다음 prompt 진입에서, 그 prompt의 메시지보다 먼저** 기록된다. pi의 "before the new prompt" 순서다. 권고: 수용.
4. **#334의 한 번 취소 거래.** 끝나지 않는 drain 뒤에서 release를 기다리는 prompt는, storage append가 영영 돌아오지 않으면 한 번의 취소로는 `turn`에서 벗어나지 못한다. 두 번째 취소는 release한다. 순서를 지키는 대가이고, ADR에 적었다. 권고: 수용.
5. **#325의 재시도.** idle 전제가 실패하면 케이스 전체를 최대 3회 다시 돌린다. 그냥 통과시키면 8a가 `last_chunk_at` 회귀를 못 잡는다(사보타주 S-d). 권고: 수용.
6. **#330 pipe-holder 케이스.** 원시 stop 기록을 그대로 판정한다. grace(1.0 s) 전체를 덮는 프로세스 정지가 오면 결함과 같은 빨강이 된다. 주석과 메시지에 적었다. 권고: 수용하고, Windows에서 단독 `timed out, exit`가 보이면 그때 다시 본다.
7. **#344 우선순위.** 지금은 P1이다. 보드 기준의 P0(보안, 데이터 유실)에 해당할 수 있다: 사용자가 로컬 엔드포인트를 골랐는데 프롬프트가 OpenRouter로 나간다. 권고: **P0로 올리고, `docs/05`의 beta.3 마일스톤 "보안" 행(#188 #131)에 넣기.**
8. **#350.** idle 규칙에 POSIX `drained()`까지 요구하면, 굶은 reader 때문에 helper 출력이 잘리는 일은 사라진다. 대신 호출이 cap까지 길어질 수 있다. 제품 판단이라 권고하지 않는다.

## 이 레포에서 실제로 물린 규칙

- **로컬 검증이 py3.12뿐이면 py3.11 CI가 빨개질 수 있다.** 3.11의 `asyncio.wait_for`는 내부 task를 하나 더 만든다. 그 사이에 hook이 읽는 holder를 await 뒤에 채운 테스트가 추월당했다. #334의 브랜치 CI 36052006149에서 ubuntu와 windows의 py3.11 두 레그만 빨갛고, 레인 3라운드와 독립 검증 모두 초록이었다. 순서에 민감한 새 테스트는 3.11 워크트리에서도 돌린다: `git worktree add --detach … && uv sync --all-packages --python 3.11`(메모리 `py311-wait-for-extra-loop-turns`).
- **Windows의 `str(list)`는 경로의 역슬래시를 두 번 쓴다.** argv 텍스트의 부분 문자열로 프로세스를 거르던 #330 도우미가 Windows 두 레그에서 결정적으로 빨갰다(CI 36052010894). 프로세스는 pid로 거른다(메모리 `windows-runner-traps-no-local-run-shows` 4번).
- **레인의 경합 주장은 그 레인의 트리거로 재현한다.** 트리거가 다른 내 probe 21회가 전부 음성이라 "재현 안 됨"으로 묻을 뻔했던 결함이 #351(P1)이다. 결함은 한 루프 턴에 있었다(메모리 `not-reproduced-is-weak-for-one-turn-races`).
- **Codex는 #334에서 두 번 다 값을 했다.**
  - 1차(aeea1074): 내부 리뷰 2회와 검증을 통과한 커밋에서, release flush 도중 취소하면 쓰기 순서가 뒤집히고 `dispose()`에서 쓰기를 잃는다는 것을 찾았다.
  - 2차(e384ca4a): 그 수정이 만든 drain lock 밖의 순서 공백을 찾았다. 메인 루프가 실제 `_run`으로 main과 #334 모두에서 같게 재현했다. 기존 결함이라 #314로 넘겼다.
  - 교훈: 새 동기화 장치(lock)는 라운드마다 새 인터리빙을 낳았다. #334는 5라운드가 걸렸다. release를 동기화할 때는 "누가 이 락 밖에서 같은 자원을 쓰는가"를 처음부터 목록으로 만든다.
- **테스트를 고치는 배치에서 판정이 약해질 수 있다.** #330의 1차 변환이 건전한 하한(`>= _COMMAND_TIMEOUT`, 제품과 같은 시계, win32에선 안 돎)을 기록 판정으로 바꾸면서 "timeout을 치렀다"를 잃었다. 독립 검증의 사보타주가 잡았다. 벽시계를 모두 없애는 것이 목표가 아니다. 판정이 여전히 빨개지는지가 기준이다.
- **공용 정지 플러그인의 증거는 절반이다.** 원판은 Popen.wait에서만 무장해서, asyncio로 띄운 사다리 케이스(rpc stop, hook, print-channel)는 344개 중 30개만 멈췄다. 세 판 모두 가끔 SIGCONT를 잃는다(#349). 결과를 인용할 때는 "그 케이스가 실제로 멈췄는가"까지 적는다.
- **main checkout의 로컬 전체 스위트는 기준 수치가 아니다.** 루트의 추적되지 않는 `.aelix/` 때문에 `tests/cli` 10개가 빨갛다(#352). 배치 전후 비교는 새 워크트리(`git worktree add --detach … && uv sync --all-packages`)에서 한다.
- **레인이 브리프의 전제를 뒤집을 수 있다.** #325 레인이 내가 준 기전("win32 잔여 #339")을 반증하고 진짜 기전(idle 규칙 + 굶은 reader, 모든 플랫폼)을 결정적으로 재현했다. 브리프의 가설은 가설로 적는다.

## 반증된 것 — 다시 믿지 말 것

- "#325의 조기 종료는 win32 잔여(#339)가 맡는다", "POSIX는 같은 hold에서 조기 종료하지 않는다": 둘 다 거짓이다. idle 규칙은 reader가 넘길 때 찍는 `last_chunk_at`으로 무장한다. 그래서 grace 동안 아무것도 넘기지 않으면 **모든 플랫폼에서** idle로 끝난다. #260 이후로는 `caught_up()` 증명이 붙는다. 강제 native/win32 분기에서 각각 3/3이었다.
- "#260이 #325를 고쳤다": 보이지 않았다. 새 drain에서 160회(windows 80회) 중 0회라는 것은 그 조건에서 안 났다는 뜻일 뿐이다. 기전은 설계로 남아 있다(#350).
- "#330 레인의 delegation 취소 멈춤은 main에서 재현되지 않는다"(내 첫 판단): 거짓이다. #351이다. 한 루프 턴을 정확히 맞춰야 한다.
- "로컬 3.12 초록이면 CI 3.11도 초록이다": 거짓이다(#334 `waiter` 경합).
- "argv 텍스트 부분 문자열로 프로세스를 거르는 것은 플랫폼과 무관하다": 거짓이다(Windows `str(list)`).
- "원판 `stall_plugin`이 asyncio 자식을 멈춘다": 거짓이다(344개 중 30개).
- "`test_a_non_terminal_stop…`의 `>= 1.0`은 #313 모양(불건전한 하한)이다": 거짓이다. 같은 시계를 읽고 win32에서는 돌지 않으므로 건전하다.
- "#334의 drain lock이 모든 세션 쓰기의 순서를 보장한다": 거짓이다. idle 직접 append는 lock 밖이다. main에도 똑같이 있던 공백이다(#314 코멘트: `['low','medium'] restores medium`).
- "#330 flood 테스트의 1.0 s 창은 phantom 결함에 필요한 backlog 때문이다"(#330 2차): 거짓이다. 867개 backlog는 약 0.11 s면 쌓인다. 창이 필요한 이유는 둘이다. any-snapshot 전제는 spawn 전이라 아무것도 재지 않고, first-reduced-line 전제는 취소가 삼켜지는 턴(#351)에 떨어진다.
