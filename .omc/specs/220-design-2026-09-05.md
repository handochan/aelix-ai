## 1. What is broken on `main` 6586f8a

Four sites in `aelix_agents/` still end only the ROOT of a delegation, and on Windows they cannot even
ask it to stop:

| site | today | POSIX consequence | Windows consequence |
| --- | --- | --- | --- |
| `print_channel.py:952-980` spawn | `start_new_session=True`, `preexec_fn=pdeathsig_preexec()` | child leads its own group (fine) | `start_new_session` silently ignored (CPython `unused_start_new_session`); no job; child is in the PARENT's console group, so a `CTRL_BREAK_EVENT` cannot be addressed to it without hitting the parent, **and a console CTRL+C reaches every subagent at once** |
| `reaper.reap()` leg 1 | `_signal_child(proc, SIGTERM)` = `os.kill(pid, SIGTERM)` | cooperative; the child's `_signal_cleanup_and_exit` reaps its bash grandchildren **[M]** (`220-progress` §1: `sleep 120` gone within 1 s) — but the child's own exit code is **1**, not 143 **[M]**, with two tracebacks on stderr | `os.kill(pid, SIGTERM)` is `TerminateProcess` — uncatchable; child never runs cleanup; grandchildren orphaned by the FIRST leg (#207 measured grace 0.047 s / 0.062 s **[M]**) |
| `reaper.kill_tree()` escalation | `/proc` walk deepest-first + `os.kill(root, _kill_signal())` | reaches `setsid` grandchildren on Linux; `descendant_pids` is `[]` on macOS, so a NON-`setsid` descendant survives **[M]** (posix-lane Darwin probe) | `descendant_pids()` is `[]` (no `/proc`); root-only `TerminateProcess` again |
| `print_mode.py:114-131` | whole handler block under `if sys.platform != "win32"` | SIGTERM/SIGHUP → `_signal_cleanup_and_exit` | NO handler; a `SIGBREAK` would hit the CRT default → process ends without `dispose()` |
| `rpc_channel.py:711-745` `_reap`/`_eager_abort` | `reap(proc, descendants=descendant_pids(pid))` / `kill_tree(...)` — through `RpcClient.process`, ignoring the `ProcessTree` the client attached in #202 | the walk; group kill only via `client.stop()` afterwards | root-only `TerminateProcess` (uncatchable), then `client.stop()` runs the job path — so the job DOES eventually end the tree, but the cooperative leg is skipped and the reported exit status is the `TerminateProcess` one (15). After #220 it is **1** (job) or **149** (cooperative) |
| `print_channel._drain_after_exit` | `kill_tree(proc, pipe_holder_pids(links))` — pipe-inode walk | Linux: finds the squatter; macOS: `[]` | `[]` — the squatter (an MCP server the child spawned, holding fd 1/2) is never killed |

The primitive that closes all of these exists since #202: `aelix_ai.utils._process_tree.ProcessTree`
(`attach` → `soft_kill()` → `hard_kill()` → `close()`), `containment_spawn_kwargs()`,

`RpcChannel` is **not wired into the product** — the `agent` tool builds a `PrintChannel`

correctness work for the injected channel, not a user-visible fix, and §H.6 tests it with a driver
script rather than an `agent` call.

## A. Decision

### A.1 The print channel spawns a contained tree

`print_channel.py`'s spawn passes `**containment_spawn_kwargs(new_session=True)` in place of the literal
`start_new_session=True` (POSIX: byte-identical `{"start_new_session": True}`; win32:
`{"creationflags": CREATE_NEW_PROCESS_GROUP}`), and attaches
`ProcessTree.attach(proc.pid, kill_on_close=True, handle=_retained_handle(proc))` immediately after
`create_subprocess_exec` returns, before any `await` (the assignment window, ADR-0238 §B.4). The tree
lives on the registry row: `RunningChild.tree: ProcessTree | None`.

`kill_on_close=True` because the print child meets ADR-0238's two stated criteria for it
(`0238:118-122`): **one child per task**, so releasing the tree is the same event as being done with it;
and it is the win32 analogue of the `pdeathsig` the spawn already installs on Linux — a parent's death
closes its last job handle and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` then ends the tree (ADR-0238:151-155,
Q6). The pipe-squatter is a *consequence*, not the reason: §A.5's explicit `hard_kill()` covers the
squatter that still holds fd 1/2, and `close()` covers the job member that let the pipes go and kept
running. (win32/W3: revision 1 rested this decision on the weakest of the three reasons.)

On Windows `CREATE_NEW_PROCESS_GROUP` also **disables console CTRL+C for the child and everything under
it**. That is a second, independent fix at this site: today a Ctrl+C in the parent's console SIGINTs
every subagent at once with no envelope, and neither parent nor child installs a SIGINT handler
(win32/W14). Say so in the rewritten spawn comment. **[U]** on Windows — the windows leg does not drive
a console Ctrl+C; recorded in §D.6.

### A.2 The reaper takes the tree and uses it for the win32 legs — plus one POSIX escalation leg

`reap(..., tree=None)` and `kill_tree(..., tree=None)` gain a keyword. Platform is decided by
`sys.platform == "win32"` read at call time through `_is_win32()` (the same read `_kill_signal()` and
`pdeathsig_preexec()` already make, and the one the existing win32 reaper tests inject through
`reaper.sys.platform`).

**A tree is USABLE only when `tree is not None and not tree.closed`.** Every dispatch below reads
"usable tree", never "tree present". A closed tree is normally an already-dead tree (a
`kill_on_close=True` job that closed its last handle terminated its members — ADR-0238:151,
`tests/process_tree/test_process_tree_real_processes.py:267-292`), but the `contained=False, job=None`
fallback shape (`_process_tree.py:551-556`) closes without killing anything, and dispatching to it would
signal nothing at all. Falling back to today's legs is strictly safer than that.

- **win32, usable tree.** Leg 1 = `tree.soft_kill()` (`CTRL_BREAK_EVENT`), with `returncode is None`
  re-read on the line immediately before it and no `await` between (win32/W13, mirroring
  `_signal_child` at `reaper.py:184-185` and `rpc_client.py:606-607`). If `soft_kill()` returns `False`
  — no console, `ESRCH`, or closed — the grace is skipped, exactly as `RpcClient.stop()` does. Escalation
  = `tree.hard_kill()` (`taskkill /T /F` then `TerminateJobObject`) and `return`: `_signal_child` and the
  descendant loop are NOT run on this arm, because `descendant_pids` is `[]` there and a root
  `TerminateProcess` would both preempt the cooperative exit and race the job for the exit status.
- **win32, no usable tree.** Today's behaviour, byte for byte: `_signal_child(SIGTERM)` → `kill_tree`.
- **POSIX.** Legs unchanged: leg 1 stays `_signal_child(proc, SIGTERM)` (root only), escalation stays
  `kill_tree(proc, snapshot)` — the `/proc` walk is what reaches a `setsid` grandchild and `killpg`
  cannot (ADR-0197 I2, ADR-0238 §A). **One addition (Q1):** `reap()` calls `tree.hard_kill()`
  (`killpg(pgid, SIGKILL)`) immediately after `kill_tree(proc, snapshot)`, guarded by a usable tree and
  `not _is_win32()`. It is **in `reap()` only, never inside `kill_tree`** — see §A.2's Q1 rationale below
  and §B.1's exact code.

**Q1 — resolved: YES, in `reap()`'s escalation body only.**

*Why yes.* On macOS `descendant_pids()` is `[]`, so today's escalation is a root-only `SIGKILL` and a
NON-`setsid` descendant survives. Measured on Darwin: a child that ignores SIGTERM and spawns a
non-`setsid` grandchild leaves that grandchild alive after today's `kill_tree` (`descendant_pids -> []`,
`root alive False grandchild alive True`) and `tree.hard_kill()` kills it (`grandchild alive False`)
**[M]** (posix-lane probe). Such descendants exist in this tree — `extensions/api.py:2045`
(`ExtensionContext.exec` → `subprocess.run` with neither `start_new_session` nor `process_group`) and
`util/tools_manager.py:175` (`subprocess.run([cmd, "--version"])`, reached from `get_tool_path`, i.e.
from `grep`/`find`) — and extensions load on the print path (`cli/entry.py:1461`, `:3083-3090`). Site
identification is **[M]** by grep; a survivor from one of those two sites in a *live delegation* is
**[U]** and §H.6(A) is where it gets measured. Not on Linux: the walk already reaches everything the
group would.

*Why not inside `kill_tree`.* One of its callers must never group-kill: `_drain_after_exit`
(`print_channel.py:1184`, reached only from `elif exited.done():` at `:1099-1101`,
~`POST_EXIT_DRAIN_SECONDS` after the reap) runs on the SUCCESS path of a delegation against a group whose
leader has already been reaped — which is exactly revision 1 of `close()`, reverted for measured harm
(`_process_tree.py:43-46`: "revision 1 sent `killpg(SIGKILL)` from it and that killed helpers a hook had
deliberately backgrounded and exited 0 over"). It also buys nothing there: the squatter that site exists
to evict is an MCP stdio server spawned `start_new_session=True`, outside the group.
(posix/P1, reaper-api/R6; scope/F4's "the coverage is empty" was refuted 2/2 with sites and a probe.)

> **CORRECTED IN ROUND 2 (posix2/P1, posix2/P2) — see §K.** Revision 2 wrote this paragraph as
> "`kill_tree` has two other callers and at both the child is already dead **and already reaped**", and
> justified `reap()`'s group kill with "`reap` owns the only `proc.wait()` and does not await it until
> after the kill, so an unexited child is unreaped". **Both sentences are false**, and both were falsified
> by probes in the review round:
>
> * `_eager_abort`'s primary call sites (`print_channel.py`'s `except asyncio.CancelledError` in
>   `_stream_and_reap`, and its last-line-of-defence `except Exception`) reach `kill_tree` with a child
>   that is **alive and unreaped**. Ctrl+C is `turn_task.cancel()`, so that is the path a human drives.
>   Measured on Darwin: a delegation cancelled before its deadline left its non-`setsid` grandchild alive,
>   while the timeout path killed it.
> * asyncio's child watcher `waitpid`s on its **own thread**, so `returncode is None` does not prove the
>   pid is unreaped — a fact `_process_tree.py`'s "THE PID/PGID HAZARD, BOUNDED PER SITE" already records
>   as measured. `reap()`'s Q1 sits under the SAME bound as the rpc and hook sites, not a tighter one: the
>   GROUP pins the number (a non-empty group's id cannot be reused; an empty one answers `ESRCH`), and the
>   residual is ADR-0238's accepted residual.
>
> The **dispatch decision is unchanged** — no group kill inside `kill_tree` — but the group kill is now
> also supplied by `PrintChannel._eager_abort` through a new `reaper.kill_group_if_live(proc, tree)`,
> guarded by `returncode is None` (the discriminator that separates a live-child cancel from a cancel that
> landed in the drain) and by "no reaper task is left to escalate" (so it cannot pre-empt the grace §A.6's
> close rule is observed across). `RpcChannel._eager_abort` does **not** take it; its tree is borrowed and
> `RpcClient.stop()` still owes it a hard leg.

*Consequence for §A.6:* once Q1 lands, the POSIX escalation goes through the tree too, so "close() must
not precede the escalation" now binds on POSIX as well — it can no longer be justified by "close() is a
POSIX no-op".

### A.3 `print_mode.py` gets the `SIGBREAK` twin — and a signal exit code that survives the loop

Two changes in one function, because the second is what makes the first observable.

**(a) The handler block is no longer switched off wholesale on win32.** POSIX arm unchanged
(`loop.add_signal_handler` for SIGTERM/SIGHUP). win32 arm: `signal.signal(signal.SIGBREAK, ...)`
recorded with its `previous` and restored in the `finally` on `previous is not None` (NOT
`callable(previous)` — `SIG_DFL` is an `int`, #202). `_handle_signal` moves OUT of the platform branch.
Revision 1's "two suppressed steps" rationale is deleted: it was imported from `rpc_mode.py:2160-2311`,
where ONE loop restores POSIX handlers and SIGBREAK out of a shared `installed_handlers` and
`remove_signal_handler` raises `NotImplementedError` before the restore. `print_mode`'s `finally` already
guards its removal loop with `if sys.platform != "win32":` (`print_mode.py:242-252`), so no
`remove_signal_handler` can precede the SIGBREAK restore and there is nothing to suppress there.
(win32/W8.)

**(b) `_signal_cleanup_and_exit` stops calling `sys.exit` from inside a task.** MEASURED on the real
product **[M]** (`220-progress-2026-09-05.md` §1, two runs, both `-p` text and `--mode json`): SIGTERM to
a real `aelix -p` child gives `returncode=1`, not 143, with

```
SystemExit: 143
During handling of the above exception, another exception occurred:
… RuntimeError: Event loop stopped before Future completed.
Task exception was never retrieved
```

`sys.exit(128 + sig)` raises `SystemExit` inside an `ensure_future`d task; it propagates out of the loop
mid-step, `asyncio.run`'s `Runner.close()` then raises `RuntimeError`, which REPLACES it, and `main_sync`
re-raises that. Pi's `process.exit(143)` (`print-mode.ts:60`, `origin/main` 47236c8) has no loop to tear
down; the literal port is wrong in Python. Two consequences: 143/149 is not the observable revision 1
assumed, and — worse for #220 — `TerminateJobObject(job, 1)` ALSO reads as exit 1 (`handoff-202` §3-12),
so on Windows the cooperative exit and the hard job kill would be **indistinguishable except by stderr
tail**. The whole point of §A.3(a) is a cooperative exit that can be told apart from a kill.

So: the signal path records its code and lets `run_print_mode` return it.
`_signal_cleanup_and_exit(runtime_host, sig, holder)` becomes `await _safe_dispose(runtime_host)` then
`holder["code"] = 128 + sig` — no `sys.exit`. `run_print_mode`'s body, after the prompt loop and before
`return exit_code`, does `if signal_exit["code"] is not None: exit_code = signal_exit["code"]`. That
override is required, not cosmetic: text mode's step 7 already sets `exit_code = 1` for an `aborted`
`stop_reason` **[M]** (same live run), so without it the parent still cannot tell "we killed it" from
"the model errored". `_safe_dispose` runs twice on this path (handler + `finally`), exactly as it does
today; it suppresses everything and `AgentSessionRuntime.dispose` is the same call both times.

A child whose work cannot be unblocked by `dispose()` never returns and therefore never reports the code
— measured shape **[M]** (posix-lane probe: a `stream_fn` that swallows `CancelledError` never exits on
SIGTERM at all, because `await _safe_dispose` never returns). That is what the reaper's grace and
escalation are for, on both platforms, and it is unchanged by this. Say so in the docstring.

After (b): POSIX exit is **143**, win32 is **149** (`SIGBREAK == 21`). Both are **[U]** until §H.6(B)
(POSIX, this box) and §H.7 (win32 leg) measure them. Neither number may be written into a test as
"already true" — §D.4 is a test that FAILS on `main` and that is its mutation property.

### A.4 `rpc_channel.py` hands the reaper the client's tree — through the row

`RpcClient` gains a read-only `tree` property (like `process`). `RpcChannel.run()` sets
`row.tree = client.tree` and `row.tree_owned = False` in the same statement group as
`row.proc = client.process` (`rpc_channel.py:513`). `_reap`, `_eager_abort` and — decisively —
`abort_child` all read `row.tree`.

The row is the only workable carrier: `RunningChild` has no `client` field
(`print_channel.py:185-201`), `RpcChannel._eager_abort` is a `@staticmethod` taking only `row`
(`rpc_channel.py:738`), and `abort_child` (the door `runtime.stop` at `:699`, `stop_all` at `:754` and
the stop-during-spawn race at `rpc_channel.py:519` all use) sees only the row. `abort_child` also
CREATES the reaper task, which `_reap` then reuses (`rpc_channel.py:720-731`), so a `tree=client.tree`
passed at `_reap` alone would be discarded on the path a human drives. (rpc/RPC-1, RPC-2; the §B.5
"Verify" of revision 1 is answered, not deferred.)

The tree stays **owned by the client**: `RpcClient.stop()` closes it and nulls `_tree`
(`rpc_client.py:619-624`), so `client.tree` never hands out a closed tree. The channel never closes it,
and `tree_owned=False` is what stops §A.6's rules from doing so.

Honest gap, recorded rather than fixed: `_shutdown` has no `try/finally` and `client.stop()` is its last
statement (`rpc_channel.py:686-709`), while `_drive`'s `finally` wraps it in
`contextlib.suppress(Exception)`, which does not catch `CancelledError`. So a cancellation during
`close_stdin`/`wait_for_exit`/`_reap`/`drain` skips `stop()` entirely and the tree is released only by
`weakref.finalize` — on win32 that means `KILL_ON_JOB_CLOSE` fires at an unpredictable GC moment. Giving
`_shutdown` a `finally` changes rpc teardown ordering and is out of scope (§I). (rpc/RPC-5.)

### A.5 `_drain_after_exit` uses the tree on win32

`_drain_after_exit(proc, pumps, tree)` passes `tree=tree` into its `kill_tree` call. On win32 with a
usable tree that is `tree.hard_kill()`; **POSIX is unchanged there** — Q1's group kill is in `reap()`
only (§A.2), and this site is exactly the caller it must not run at.

Two bounds to state in the docstring rather than leave a reader to re-derive:

- The kill is carried by `TerminateJobObject`, not by `taskkill`. `/T` follows LIVE parent links and the
  root is already dead here — #202 measured this exact shape and asserted the grandchild SURVIVES
  (`tests/process_tree/test_process_tree_real_processes.py:294-311`) **[M]**. If `_attach_win32` fell
  back (`contained=False`, `job is None`) the drain leg is a no-op on win32. (win32/W15.)
- It is not a stale-pid kill. The branch is entered only while `pumps` is not done, i.e. while a
  descendant still holds the child's stdio; the transport therefore still holds the `Popen`
  (`asyncio/base_subprocess.py:232-252` nulls `_proc` only once every pipe disconnects), whose open
  process handle pins the pid on Windows (CPython `subprocess.py:248-257`). **[U]** — read from CPython,
  not measured on a Windows host. (reaper-api/R6.)

### A.6 Who closes a tree — exactly one owner, and never before the escalation

`close()` is a release on POSIX (signals nothing, ever) and, for a `kill_on_close=True` tree, an
end-of-everything-left on win32. It must not run BEFORE the reaper's escalation on **either** platform
now that Q1 routes the POSIX escalation through the tree too, because `soft_kill`/`hard_kill` both
early-return on `_closed` (`_process_tree.py:599-600`, `:625-626`).

Rules:

1. **`RunningChild.tree_owned: bool = False`.** The print channel's own spawn sets `True`. The rpc
   channel sets `False` (the client owns it). Nothing closes a row's tree unless `tree_owned` is `True`.
2. **`PrintChannel.run()`'s `finally` is the single owner** for print rows. After `remove_prompt_dir`:
   ```python
   tree = row.tree
   if tree is not None and row.tree_owned:
       task = row.reaper_task
       if task is None or task.done():
           tree.close()
           row.tree = None
       else:
           # The reaper is DETACHED and may still be inside its grace; it must
           # reach hard_kill() before the tree is disarmed (§A.2).
           task.add_done_callback(lambda _: (tree.close(), setattr(row, "tree", None)))
   ```
   The `row.tree is None` guard is not optional: the abort-before-spawn path (`print_channel.py:932-936`)
   and the spawn-failure path (`:976-978`) both reach this `finally` with no tree. (posix/P10.)
3. **Closing NULLS the row's reference, in the same statement.** This is the mechanism, not a nicety: it
   is what guarantees a later `abort_child` → `reap(..., tree=row.tree)` gets `None` and falls back to
   today's legs instead of dispatching to a disarmed tree. It mirrors the reference adoption exactly
   (`rpc_client.py:502-503`, `:623-624`). (reaper-api/R2, rpc/RPC-3.)
4. **`ProcessTree.closed` becomes a public read-only property** (`return self._closed`, two lines,
   mirroring `job`). It is the belt for rule 3 and it is what makes §D.2's ordering test assertable from
   outside. The reaper's dispatch reads `tree.closed` directly — NOT `getattr(tree, "closed", False)` —
   so a §D.1 recording stub that forgets to declare it fails loudly instead of silently taking the POSIX
   arm.
5. **`stop_all` closes nothing.** Revision 1's belt is deleted. `runtime.stop_all` (`runtime.py:742-767`)
   iterates the shared registry with no idea which channel owns a row; with `row.tree` set for rpc rows
   it would close a tree `RpcClient.stop()` still owes a soft→grace→hard sequence, and (win32,
   `kill_on_close`) fire the job kill before `client.drain(POST_EXIT_DRAIN_SECONDS)`. Nothing is leaked
   by dropping it: print rows keep rule 2, rpc rows keep `RpcClient.stop()`, and an abandoned tree still
   releases through `weakref.finalize` in `ProcessTree.__init__` (`_process_tree.py:492-496`).
   (rpc/RPC-4, posix/P4, win32/W9.)

**Q2 — resolved: the done-callback shape, plus rules 1/3/4/5.** `reap()`-owned close is rejected: `reap`
is not on the success path (which never calls it), not on the abort-before-spawn or spawn-failure paths,
and `abort_child`/`_reap` both REUSE an existing `row.reaper_task`, so "the reap that was handed the
tree" is not a single well-defined owner. For rpc rows a `reap()`-owned close would close the client's
tree out from under `RpcClient.stop()`.

### A.7 `_eager_abort` on win32 = `tree.hard_kill()`, and Q4 is "hard only"

Through `kill_tree(..., tree=)`. Stated cost, since revision 1 was silent about it: `_eager_abort` is a
synchronous `@staticmethod` called from inside `except asyncio.CancelledError` handlers
(`print_channel.py:1107`, `:1122`, `:1219`; `rpc_channel.py:570`, `:579`, `:734`), and on win32
`hard_kill()` runs `subprocess.run(taskkill, …, timeout=5)` on the event-loop thread
(`_process_tree.py:411-439`). Today that leg is an instantaneous `os.kill`; after #220 it is a process
spawn, bounded at 5 s. This is the same cost `RpcClient.stop()` (`rpc_client.py:592`) and the hook
timeout ladder (`subprocess_hooks.py:238`) already pay on the loop, and it is accepted for the same
reason: the alternative to a bounded stall is a leaked tree. `_taskkill_tree`'s docstring enumeration of
its callers ("every win32 caller … is a coroutine") becomes false and is corrected in §B.6.
Both proposed remedies are rejected: a `terminate_job`-only path for synchronous callers drops the `/T`
walk that exists for the Pi #9129 shape, and `await asyncio.to_thread(tree.hard_kill)` inside `reap`
inserts an unshielded suspension point between the kill and `return int(await asyncio.shield(waiter))`,
which is precisely the zombie/uncollected-status hole the shield was added to close
(`reaper.py:279-283`). The duration is **[U]** and §H.7 measures it. (win32/W2, posix/P9, rpc/RPC-7.)

**Q4 — resolved: hard only.** When `eager_kill=True` on the win32 usable-tree arm, `soft_kill()` is NOT
called. `abort_child` always passes `eager_kill=True` (`print_channel.py:812-814`), so this governs every
`stop` / `stop_all` / extension teardown — the common path, not an edge. With zero grace the console
event buys nothing measurable, and it is not inert: after §A.3 the child's SIGBREAK handler starts
`_signal_cleanup_and_exit` → `dispose()` (which flushes the session file) and `taskkill` +
`TerminateJobObject` truncate it microseconds later. It also doubles the latency of the one path a human
is waiting on (see the blocking `taskkill` above).

This **diverges from the POSIX arm**, which keeps today's SIGTERM-then-immediate-SIGKILL, and the spec
says so rather than claiming the two are different in kind: POSIX has the same truncated-`dispose`
exposure today, and #220 is not chartered to change the POSIX legs. The win32 divergence is justified by
the two win32-only costs above, not by a claim that CTRL_BREAK is more dangerous than SIGTERM.
Pin: `soft_kill` call count == 0 when `eager_kill=True` on the win32 tree arm (§D.1 case 3).

### A.8 The `escalation_reachable` marker (#215) is retired — three linked sites, and its sibling stays

With leg 1 = `CTRL_BREAK_EVENT` and a stub that installs a `SIGBREAK` handler and keeps running, the
escalation IS reachable on win32. Retire **all three** linked sites together
(`tests/agents_ext/test_print_channel_spawn.py`): the module-level bool `escalation_unreachable` at `:93`,
the marker `escalation_reachable` at `:94`, and the inline `if not escalation_unreachable:` guard at
`:1237`. Removing only the marker leaves the win32 arm silently skipping its exit-code assertion.
(win32/W12.)

Its SIBLING `sigterm_ignoring_fixture_buildable` (`:110`) **STAYS**, and its comment block gains one
sentence saying #220 retired `escalation_reachable` but not it. Its precondition is an OS refusal —
`/bin/sh -c "trap '' TERM; exec …"` cannot be built on Windows and no product change makes it buildable —
which is the carve-out `tests/conftest.py` makes to the inject-don't-skip rule. Deleting it yields a
`[WinError 2]` spawn failure instead of a skip. (tests/T14, scope/F11.)

The two tests (`test_reap_still_escalates_after_the_signal_change`, `test_sigterm_then_sigkill`) assert:

- POSIX: `result.exit_code == -signal.SIGKILL`. Already mutation-sensitive **[M]** — a no-op `kill_tree`
  makes `test_sigterm_then_sigkill` fail at 40 s (tests-lane mutation probe).
- win32: `result.exit_code == 1` as CORROBORATION only, with the child's stderr tail and `elapsed`
  carried in the assertion message. It cannot separate `TerminateJobObject(job, 1)` from a crashing
  child (`handoff-202` §3-12 **[M]**); it CAN separate the tree arm from the tree-less fallback, which
  reaches `TerminateProcess(handle, SIGTERM)` → 15. Say both in the test comment.
- **Load-bearing on both platforms:** a spy wrapping `row.tree.hard_kill` on the instance. Platform-keyed
  counts, because the POSIX escalation reaches `hard_kill` only through Q1: assert exactly once on both
  arms, and state in the comment that on POSIX the assertion exists *because* Q1 landed — if Q1 is ever
  reverted, this assertion is the thing that must move, not be deleted. (reaper-api/R7, win32/W12.)
- Count scope: "exactly once" is asserted only in these two TIMEOUT tests. A cancelled run reaches
  `kill_tree` from `_eager_abort` at `print_channel.py:1219` and again at `:1107` plus the reaper's own
  escalation; cancellation tests assert `>= 1` and keep `_await_death(pid)` as the behavioural evidence.
  (posix/P7.)

### A.9 What else changes behaviour — stated, not denied

Revision 1 said "nothing else in `aelix_agents/` changes behaviour". That was false in one respect and
it is now stated (scope/F10): **on win32, a SUCCESSFUL delegation now ends every surviving job member**
when `run()`'s `finally` closes the `kill_on_close=True` tree. A background helper a child deliberately
left running dies where today it survives. This is deliberate and matches the rpc child
(`rpc_client.py:462`, shipped since #202); on POSIX `close()` still signals nothing, and the asymmetry is
already recorded as intended in ADR-0238:112-116. §G adds it to the CHANGELOG and §D.2 pins it.

`batch.py` reaches children only through `RunningChild` / `abort_child` / `reap` — it calls neither
`reap` nor `kill_tree` (`grep -rn -e kill_tree -e 'reap(' packages tests`: the `batch.py` hits at `:101`,
`:102` and `:635` are docstring citations) **[M]**. `pdeathsig_preexec()` stays.

## B. API changes

### B.1 `aelix_agents/reaper.py`

```python
if TYPE_CHECKING:
    from aelix_ai.utils._process_tree import ProcessTree


def _is_win32() -> bool:
    """``sys.platform`` read at CALL time, so a test can inject it.

    A function rather than a module constant for the same reason
    :func:`_kill_signal` reads it late: ``tests/agents_ext/
    test_reaper_kill_signal_win32.py`` patches ``reaper.sys.platform``.
    """
    return sys.platform == "win32"


def _usable(tree: ProcessTree | None) -> bool:
    """A tree that can still kill. ``closed`` is deliberately not ``getattr``-ed."""
    return tree is not None and not tree.closed


def kill_tree(
    proc: Any, descendants: Sequence[int] = (), *, tree: ProcessTree | None = None
) -> None:
    if _is_win32() and _usable(tree):
        # The JOB is the descendant set here, so ``descendants`` is ignored —
        # both product callers' walks are empty on Windows anyway. NOT followed
        # by ``_signal_child``: ``TerminateProcess(handle, SIGTERM)`` would race
        # ``TerminateJobObject(job, 1)`` for the exit status §A.8 asserts.
        tree.hard_kill()          # type: ignore[union-attr]
        return
    sig = _kill_signal()
    for pid in descendants:
        with contextlib.suppress(ProcessLookupError, PermissionError, OSError):
            os.kill(pid, sig)
    _signal_child(proc, sig)
    # NO POSIX ``tree.hard_kill()`` HERE. Two callers reach this function with a
    # child that is already dead AND already reaped (``_drain_after_exit`` on the
    # delegation SUCCESS path, ``_eager_abort`` after a cancel into the drain),
    # and a ``killpg(SIGKILL)`` there is revision 1 of ``close()`` again
    # (``_process_tree.py:43-46``). Q1's group kill lives in ``reap`` (posix/P1).


async def reap(
    proc: Any,
    *,
    grace: float = DEFAULT_GRACE_SECONDS,
    eager_kill: bool = False,
    descendants: Sequence[int] | None = None,
    tree: ProcessTree | None = None,        # NEW
) -> int:
    ...
    # leg 1 — the ONLY thing that changes on win32
    if _is_win32() and _usable(tree):
        if not eager_kill:
            # Q4: with ``eager_kill`` the human has already waited; asking again
            # and terminating microseconds later only truncates the child's
            # ``dispose()`` (§A.7).
            if getattr(proc, "returncode", None) is None and not tree.soft_kill():
                eager_kill = True      # nothing was delivered: nothing to wait for
    else:
        _signal_child(proc, signal.SIGTERM)

    if not eager_kill:
        try:
            return int(await asyncio.wait_for(asyncio.shield(waiter), grace))
        except BaseException:  # unchanged — finding B1
            pass

    kill_tree(proc, snapshot, tree=tree)
    if not _is_win32() and _usable(tree):
        # Q1. AFTER the walk, so the group kill only ever addresses what the
        # walk could not name. What bounds it is the GROUP, not the pid: a
        # non-empty group's id cannot be reused while any member lives
        # (POSIX.1 §3.293) and an empty one answers ESRCH. Deliberately NOT
        # guarded by ``returncode is None`` — after the grace the leader is
        # often dead while a descendant is not, and that is the shape this
        # exists for. (Round 2 corrected the earlier "reap owns the sole
        # proc.wait(), so the child is unreaped" wording — see §K.)
        tree.hard_kill()           # type: ignore[union-attr]
    return int(await asyncio.shield(waiter))
```

    """Ignores the soft signal on BOTH platforms and says so, without stderr.

    POSIX: ``SIGTERM -> SIG_IGN``, unchanged (#207's fixture).

    partial summary ``:1239`` asserts), and it is written from the LOOP on a
    flag the handler sets, so no I/O runs at delivery time.

        _hit = {{"v": False}}

  handle closes (today ours is the only one — `CreateJobObjectW(NULL, NULL)` is non-inheritable and the
  stdlib passes only handles named in `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` — but a future change could
  introduce another); members are TERMINATED, not signalled; and `weakref.finalize` fires the same kill
  when the tree is merely garbage-collected, at a nondeterministic moment.
