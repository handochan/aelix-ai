## 1. What is broken on `main` dff6b62

Three product sites call `subprocess.run(argv, capture_output=True, timeout=…)`:

| site | argv | timeout | caller |
| --- | --- | --- | --- |
| `extensions/api.py` `ExtensionAPI.exec` (`:2045-2054`) | `[command, *args]` from the extension | `timeout_ms/1000`, or **`None` by default** | `asyncio.to_thread` from an extension's coroutine — the **documented** extension exec surface (Pi `exec.ts execCommand`) |
| `cli/extension_catalog.py` `_default_git_runner` (`:469-474`) | `["git","clone","--depth","1",url,dest]` | `GIT_CLONE_TIMEOUT = 60.0` | `_git_clone_bytes` ← `fetch_catalog` ← `aelix extension discover --refresh` (CLI, foreground, main thread) |
| `tui/completion.py` `_fd_enumerate` (`:250-256`) | `[fd, --type f, --type d, --hidden, …, --max-results N]` | `_FD_TIMEOUT = 2.0` | `_enumerate_tree` ← the `@`-mention completer (TUI) |

CPython `run()` on `TimeoutExpired` does `process.kill()` — the root pid and nothing else — and then, **on
Windows only**, `process.communicate()` with no timeout, because the reader threads own the output and
must be joined to attach it to the exception (`Lib/subprocess.py`, quoted verbatim in `221-progress` §3).
A descendant that inherited the pipes and outlived the root keeps the write end open, so that join never
returns. On any exception other than the timeout, `run()` kills the root (`except: process.kill()`).

**Measured on `main`** (`221-progress` §1, §4) **[M]**: every site leaks a non-`setsid` grandchild on
POSIX (A/C/D/E `survivors=1`, and the real `api.exec` under a real model leaves the sleeper at `ppid 1` in
aelix's own group); a root that exits **0** at once but leaves a pipe-holder behind is reported as a
timeout after the whole `timeout` (B: `out=b'done\n'`, `TimeoutExpired` at 3.3 s; live: `code=124
killed=True stdout='done\n'`). Windows is **[U]** here and gets its number from the windows leg.

**Also measured, the reason the site inventory is what it is** (`221-progress` §5) **[M]**: a `git clone`
whose `git` is SIGKILLed root-only leaves `git remote-http` (blocked in libcurl on a hung server) alive
3 s later, `ppid 1`, in our group; the ssh transport helper likewise. So "the remote helper exits on pipe
EOF anyway" is false, and the git site needs the group kill on POSIX.

Not in this list, and why: `util/tools_manager.py` `_command_exists` (`:175-181`) is `subprocess.run`
with **no** timeout and all three stdio at `DEVNULL` — no pipe to deadlock on, and Pi parity
(`commandExists` has no timeout either); a hung `cmd --version` would still block the caller, which is a
separate issue if it is ever seen (DOC-12). It stays in the parent's group, which makes it the ONE plain
spawn reachable inside a delegated child that ADR-0238's Q1 group kill still reaches on macOS (§G).
`cli/extension_install.py` `_default_runner` (`:1369`, pip with inherited stdio, no timeout, CLI only),
`tui/shell.py:2577` (`$EDITOR`, TUI only) and `aelix_ai/oauth/_resolve_config.py` (already contained by
#202, its own byte-capped reader) are out of scope and named in §I.

## A. Decision

### A.1 One synchronous helper in the primitive's module: `run_contained`

`packages/aelix-ai/src/aelix_ai/utils/_process_tree.py` gains:

```python
def run_contained(
    argv: Sequence[str],
    *,
    timeout: float | None,
    cwd: str | None = None,
    env: Mapping[str, str] | None = None,
    platform: str | None = None,
    api: _Win32Api | None = None,
) -> subprocess.CompletedProcess[bytes]: ...
```

It is the `subprocess.run(argv, stdin=DEVNULL, capture_output=True, check=False, timeout=…)` shape and
nothing wider: bytes out, `TimeoutExpired` raised, `OSError` from the spawn propagated, any other exception
out of the wait propagated after the tree is ended. **No `kill_on_close` and no `new_session` knob** (rev 1
had both; DOC-3/PI-4 and DOC-1/PI-3 removed them): a contained run always has a session of its own and
`close()` is always a release. The three sites adopt it; each keeps its own decoding and its own exception
translation (§C).

Why here and not a sibling module: the issue names this module, `_resolve_config.py` already imports its
three names from here, and the helper is the primitive's one synchronous runner — the tests for the two
halves share one fake api (`tests/process_tree/test_process_tree_api.py::FakeApi`).

### A.2 What the helper does, in order

0. `start = time.monotonic()` — the origin of the deadline, taken immediately before the spawn, so the
   deadline the drain caps against is the one `proc.wait(timeout=)` bounded (CS5).
1. **Spawn** `subprocess.Popen(list(argv), stdin=DEVNULL, stdout=PIPE, stderr=PIPE, cwd=cwd,
   env=(None if env is None else dict(env)), **containment_spawn_kwargs(new_session=True,
   platform=platform))`. `stdin=DEVNULL` always — Pi's `execCommand` spawns with `stdio: ["ignore",
   "pipe", "pipe"]`, and today's `api.exec` **inherits** the TUI's stdin. `new_session=True` always — §A.4.1.
   A spawn failure (`FileNotFoundError`, `PermissionError`, `NotADirectoryError`, `ValueError`) propagates
   unchanged — the sites already translate it; no tree exists, `close` is not reached.
2. **Attach** before anything else runs: `tree = ProcessTree.attach(proc.pid, kill_on_close=False,
   handle=_retained_handle(proc), platform=platform, api=api)`. Attach failure on win32 is a degrade inside
   `attach` (`contained=False`, taskkill-only) and never raises; a POSIX attach cannot fail. **[M]** the
   `process_group`/`setsid` → `getpgid` race does not open: 400/400 spawns attached `contained=True`.
3. **Read** stdout and stderr on two daemon `_PipeReader` threads, each appending ≤ 64 KiB chunks
   (`read1(65536)` — returns what is available before EOF, measured `221-progress` §3) to its own list and
   stamping the shared `_ReadState.last_chunk_at`. One shape on both platforms (Windows anonymous pipes
   cannot be `select`ed; the thread arm is the one this box can test). A reader ends silently: `except
   (OSError, ValueError): pass`, `finally: suppress(Exception): stream.close()` — the thread owns the close
   (WIN-7).
4. **Wait for the root**: `proc.wait(timeout=timeout)`. This bounds the ROOT's lifetime, not pipe EOF.
   `timeout=None` waits without bound, as `subprocess.run(timeout=None)` does today.
5. **On `TimeoutExpired`** (the root is alive past `timeout`): the timeout ladder (§A.3.1), then raise
   `subprocess.TimeoutExpired(list(argv), timeout, output=stdout_so_far, stderr=stderr_so_far)` — both
   `bytes`, possibly `b""`, never `None` — `from None`.
6. **On exit**: stamp `state.exited_at = time.monotonic()` (Pi's `onExit → armIdleTimer()`), then drain.
   Compute once: `drain_until = state.exited_at + DRAIN_CAP_SECONDS`; if `timeout is not None`:
   `drain_until = min(drain_until, max(start + timeout, state.exited_at + exit_drain))`. Loop until **any**
   of: (a) both readers have seen EOF; (b) `now − max(state.last_chunk_at, state.exited_at) >= exit_drain`
   — the pipes fell idle for `exit_drain` **measured from the root's exit, re-armed on every chunk that
   arrives after it** (Pi `waitForChildProcess`, `EXIT_STDIO_GRACE_MS = 100`); (c) `now >= drain_until` —
   whichever is first; sleeping ≤ 5 ms between checks. A reader still alive after the drain is **left
   alone** (daemon; it ends when the holder closes the pipe — §A.5).
7. **Return** `CompletedProcess(list(argv), proc.returncode, stdout=b"".join(...), stderr=b"".join(...))`.
8. **On any other `BaseException`** out of steps 4–6 (`KeyboardInterrupt`, `SystemExit`, anything): the
   interrupt ladder (§A.3.2), then re-raise.
9. **`finally: tree.close()`** — reached on every path that attached; on POSIX a release; on win32
   `CloseHandle(job)`, which ends nothing (`kill_on_close=False`).

### A.3 The two kill ladders — hard only, then a belt, then a bound

#### A.3.1 Timeout (step 5)

```
tree.hard_kill()                                   # killpg(SIGKILL) / taskkill /T /F + TerminateJobObject
with suppress(OSError): proc.kill()                # BELT — see below
with suppress(TimeoutExpired): proc.wait(timeout=reap_grace)      # REAP_GRACE_SECONDS = 5.0
state.exited_at = time.monotonic()                 # the post-kill drain is armed HERE
drain as §A.2.6 with drain_until = exited_at + KILL_DRAIN_SECONDS   # 1.0
```

- **No soft leg.** `_resolve_config.py`'s reasoning applies verbatim: there is no grace stage to escalate
  from, and the producer is by definition not answering. Two more reasons, both measured: (i) hard-only is
  what these three sites do today — CPython's `run()` sends `process.kill()` on `TimeoutExpired` with no
  SIGTERM leg, so a soft leg would be NEW behaviour to justify, not preserved behaviour; (ii) Pi's soft leg
  is not a bound we could copy: `execCommand` sends `SIGTERM` and schedules `if (!proc.killed)
  proc.kill("SIGKILL")` on a detached 5 s timer (exec.ts:51-62 at 9841914c), and Node sets `killed` when
  the signal is SENT, so the guard never passes and the SIGKILL never fires — a `trap '' TERM` child ran
  its full 40 s under a 1 s Pi timeout; a SIGTERM-honouring one resolved at 1005 ms (POSIX-3). We go
  hard-only for one kill path and a latency bounded by us (`reap_grace`) rather than by the command; the
  three commands here need no cleanup (`git clone`'s temp dir is `rmtree`'d by the caller; `fd` has
  nothing; an extension's command is unknown). Divergence from Pi needs no ADR (ADR-0235); §G records it.
- **The belt is not redundant, and its safety is per-platform** (WIN-5). `hard_kill` does not touch
  `Popen` state, so the belt is always entered with `returncode is None` even when the root is already
  dead **[M]**. POSIX — `proc.kill()` is `send_signal(SIGKILL)`, which polls first (bpo-38630); the poll
  reaps the zombie and no second signal is sent. win32 — `Popen.kill` IS `terminate`, does not poll, and
  calls `TerminateProcess` on the retained HANDLE (`class Handle(int)`, `__del__ = Close`): a pid cannot be
  recycled while that handle is open, and on an exited process the call raises `PermissionError`, which
  `Lib/subprocess.py:1674-1681` converts into a `returncode`. Both are inside `suppress(OSError)`. On win32
  with no job (a failed attach) **and** no resolvable `taskkill.exe`, `hard_kill` is a silent no-op that
  does not raise (#202 review win-leg/F3), and the belt is the only thing that ends the root.
- **`reap_grace` bounds the root's death, and `KILL_DRAIN_SECONDS` bounds the readers** (TP4). After
  SIGKILL/TerminateJobObject, the tail the kill released is readable at once; a holder OUTSIDE the tree
  (a `setsid` descendant on POSIX; an assignment-window escapee on win32) will never EOF, so the reader
  drain is the exit drain's idle rule capped at 1.0 s — measured ~1.1 s total for a 1 s timeout with an
  escaped holder, against 6.0 s under rev 1. After it, `TimeoutExpired` carries whatever arrived. A root
  that outlives `reap_grace` is a **live orphan** (not a zombie) filed in `subprocess._active` and never
  collected — the residue `_resolve_config.py:133-136` already accepts (POSIX-6).
- **The win32 bound, stated** (WIN-3): `hard_kill` runs `taskkill /T /F` FIRST and UNCONDITIONALLY on
  win32 (`_process_tree.py:660-671`), and `_taskkill_tree` is a `subprocess.run(timeout=5)`, so the
  worst case is `timeout + 5 s + reap_grace + kill_drain`. `_taskkill_tree` was itself the #221 shape —
  `capture_output=True` with a discarded result, followed on win32 by CPython's untimed post-kill
  `communicate()` — so its stdio becomes `DEVNULL` (all three), which is the same reasoning §1 uses for
  `_command_exists`, now applied consistently. The windows leg measures `hard_kill`'s wall time
  (`warnings.warn`).

#### A.3.2 Interrupt (step 8) — CPython's own leg, at tree granularity (CS1/POSIX-1/WIN-2)

```
tree.hard_kill()
with suppress(OSError): proc.kill()
with suppress(TimeoutExpired): proc.wait(timeout=INTERRUPT_REAP_SECONDS)   # 0.25 — Popen._sigint_wait_secs
raise                                              # no drain, no output attached
```

Why it is load-bearing and not cosmetic: `subprocess.run` kills the root on ANY exception (`Lib/subprocess.py`
`except: process.kill()`), and `Popen.__exit__` states its assumption in a comment — "In the case of a
KeyboardInterrupt we assume the SIGINT was also already sent to our child processes" — which
`start_new_session=True` / `CREATE_NEW_PROCESS_GROUP` make false: the child is not in the terminal's
foreground group (POSIX) and `CREATE_NEW_PROCESS_GROUP` "disables CTRL+C signals for all processes within
the new process group" (win32, **[U]**). Measured under a real pty: `^C` → parent `KeyboardInterrupt`,
contained child alive. The affected sites are the foreground ones — `aelix extension discover --refresh`
(60 s clone on the main thread; and `_git_clone_bytes`'s `finally: rmtree` would have deleted the
directory out from under a live clone) and `aelix -p`; the TUI clears `ISIG` in raw mode and is not
affected. The bound is short so ^C does not feel like a 5 s hang; the readers are not joined (daemon).
**Corrected by the implementation review (§K, SITE-1/HC2):** the leg reaches `discover --refresh` (main
thread) and, at `ExtensionAPI.exec`, only a `BaseException` raised INSIDE the `to_thread` worker — a
terminal `^C` lands in the main thread and never enters that frame. The exec site is closed by
`AbortHandle` (§K.1) on `CancelledError` instead.

#### A.4.1 The session decision, measured — and the reversal path

`221-progress` §2 **[M]**: under a real pty a `process_group=0` child that reads `/dev/tty` is stopped by
`SIGTTIN` (`ps stat T`). The refutation round extended it **[M]**: real `git clone` over ssh with an
unknown host key, `process_group=0` — `git`, `ssh`, `sshd-session`, `sshd-auth` all `T`, **no prompt ever
printed** (ssh's `read_passphrase` calls `tcsetattr`, and `tcsetattr` from a background group raises
`SIGTTOU` group-wide); the same clone in our group prints the prompt and waits in `S+` — the flow works on
`main`. `GIT_TERMINAL_PROMPT=0` (rev 1's remedy) reaches only git's OWN terminal fallback, which
`prompt.c:git_prompt()` consults LAST — after `GIT_ASKPASS`, `core.askPass` and `SSH_ASKPASS` — and never
ssh or a credential helper that opens the tty itself; a VS Code integrated terminal exports `GIT_ASKPASS`
unconditionally. So rev 1 turned a working interactive first clone into a silent 60 s stall ending in
`… timed out after 60.0 seconds` — the wrong cause.

**Decision: `start_new_session=True` at all three sites.** With no controlling terminal, every tty read
fails at once with the tool's own message: `git` → `fatal: could not read Username for '…': No such
device or address` (exit 128, ~50 ms) **[M]**; `ssh` → `Host key verification failed.` (exit 128 at
0.62 s) **[M]**, both already surfaced by `_git_clone_bytes` (first 200 bytes of stderr). Askpass programs
and GUI/keychain helpers do not need the terminal and keep working (a blocking one still costs its own
block, bounded by the timeout — as today). Nothing is stopped, nothing stalls silently, and no environment
variable of the user's is overridden.

**What this gives up, stated as the reversible decision taken in the owner's absence** (precedent: #220's
exit-code decision): a catalog clone is now non-interactive — a first clone from a fresh machine whose ssh
host key is unknown, or whose key needs a passphrase not held by an agent, fails fast with git's/ssh's
message instead of prompting. The guide says so (§G, `private-catalog.md`). The exec surface likewise has
no terminal: an extension command that prompts fails at once rather than stopping until its timeout (under
Pi's contract such a command is already out of scope — `stdin: "ignore"`; Pi's exec stays in-session,
divergence declared). **The reversal path** is not `process_group=0` (the silent stop) but "no POSIX
group at the git site, job on win32 only" — and its measured cost is the leak in §1: `git remote-http`
outlives a root-only kill. The ADR amendment records both.

### A.5 What is accepted, stated

- **A reader thread that never sees EOF is leaked**, one per event, daemon, blocked in `read1()` until the
  holder closes the pipe — but from the moment `run_contained` returns it DISCARDS what it reads, keeping
  at most one chunk (R1 / site-exec-1), so what leaks is a thread and an fd and not a growing buffer.
  CPython's own `communicate()` threads are daemon threads too; Pi `destroy()`s the
  streams, which cancels Node's pending read, and Python has no portable equivalent
  (`CancelSynchronousIo` on win32 is named in §I, not adopted). The pipe's read end stays open in our
  process for as long as the thread lives. The cases: a `setsid` descendant on POSIX (outside the group,
  the asymmetry ADR-0238 states — measured with a tight bound in D.2), a job escapee on win32, and on the
  success path a helper the command deliberately backgrounded.
- **`timeout` bounds the root directly and the drain as a backstop.** After exit the idle timer is armed
  at exit and re-armed on writes (Pi); the drain ends at whichever of the idle grace, the original deadline
  (when given, floored at one grace after exit) and `DRAIN_CAP_SECONDS` from exit comes first. **The
  cap is an Aelix-only divergence from Pi** (Pi drains without bound) and its failure mode is a
  DESCENDANT still writing at the cap having its output cut, with the root's own `returncode == 0` — never
  the root's own output, which is at most the pipe buffer at exit and is drained in milliseconds. With
  `timeout=None` — `api.exec`'s DEFAULT — the cap is the only bound on a chatty holder, and without it the
  call never returned (measured: 10 MB buffered at 9 s, `ru_maxrss` 14 → 25 GB unthrottled).
  **What the cap bounds is the CALLER'S WAIT, not the readers** (R1 / site-exec-1): the two reader threads
  go on reading past the return so the holder is never stalled on a full pipe, but they discard from then
  on, so the bytes stop accumulating AT THE RETURN; the thread and its fd still live until the holder
  closes the pipe.
- **A deliberate outliver inside the tree dies on the timeout path and survives the success path.**
  `git credential-cache--daemon` is the measured example (§0 DOC-3/PI-4): reachable only when THIS clone
  started it (a pre-existing daemon keeps its own group — measured `ESRCH`, alive), so at most 60 s of
  cached credentials, and the next `store` restarts it (measured). `close()` never reaches it.
- **On a POSIX host with no `/proc` (macOS), an extension `exec` in flight is no longer reached by the
  delegation escalation** (CS2): `reap`'s Q1 `tree.hard_kill()` and `kill_group_if_live` address the
  delegation child's group, and the exec tree now leads its own session. Measured: 0 survivors today,
  2 under this design (the command and its non-`setsid` grandchild). Linux keeps the coverage through the
  `/proc` walk (the exec child is a direct child whatever its session); win32 through inherited job
  membership **[U]**. On macOS `run_contained`'s own ladder is that tree's only reaper, and with
  `timeout_ms=None` there is none once the agent process is SIGKILLed. Recorded in the ADR amendment as
  a loss; a follow-up issue is filed (§H).
- **The pid/pgid hazard** is ADR-0238's, restated: the helper's `hard_kill` runs on a root that
  `proc.wait(timeout)` just refused to reap, so the zombie pins the number for the synchronous case (the
  `!command` bound), and the group bound (a non-empty group's id cannot be reused) holds regardless. On
  win32 the retained handle pins the pid outright.
- **The assignment window** on win32 is the `Popen` return → `attach` gap, the same as `_resolve_config.py`;
  belt-and-braces is `hard_kill`'s `taskkill /T` first.
- **Terminal signals no longer reach these children** — neither the tty's ^C on POSIX nor the console's
  Ctrl+C on win32 — which is why §A.3.2 exists and is tested on both legs.

## C. Site by site — what each one must satisfy

### C.1 `run_contained`

1. `Popen` receives exactly: `list(argv)`, `stdin=DEVNULL`, `stdout=PIPE`, `stderr=PIPE`, `cwd`, `env` (a
   fresh `dict` or `None`), and `containment_spawn_kwargs(new_session=True, platform=)` —
   `start_new_session=True` on POSIX, `creationflags=CREATE_NEW_PROCESS_GROUP` on win32. Nothing else.
2. `ProcessTree.attach` is called with the pid, `kill_on_close=False`, `handle=_retained_handle(proc)`,
   before any read or wait.
3. Timeout path: `hard_kill` once, then `proc.kill` once, in that order; a `wait` bounded by `reap_grace`;
   a reader drain bounded by `KILL_DRAIN_SECONDS`; then `TimeoutExpired` with `.cmd == list(argv)`,
   `.timeout == timeout`, `.stdout`/`.stderr` bytes (never `None`).
4. Exit path: returns after both EOFs, or after `exit_drain` idle measured from exit (re-armed per chunk),
   or at the deadline (floored at one grace after exit), or at `DRAIN_CAP_SECONDS` after exit — whichever
   is first; never kills; `returncode` is the root's; a tail written after exit within the grace is in the
   output.
5. `ProcessTree.close` is CALLED on every path that attached (success, timeout, wedged root, interrupt) —
   exactly once (a call-count spy on the method, not the api log) — and only after the readers' bound.
6. Spawn errors propagate; no attach, no close.
7. Never signals a pid it did not spawn: every kill goes through the tree or `proc.kill()`; with
   `contained=False` the tree's kill is root-only (`os.kill`, no `killpg`).
8. A `BaseException` out of the wait or the drain ends the tree (`hard_kill`, `kill`, ≤ 0.25 s wait) before
   it propagates; no output is attached; `close` still runs.

### C.2 `api.exec`

- The two existing tests stay green unchanged (`echo` → code 0 stdout; missing binary → 127).
- Dispatch: `run_contained` receives `[command, *args]`, `timeout == timeout_ms / 1000` (`None` for
  `None`/`0`), `cwd` passed through, `env == dict(os.environ) | caller's env`.
- A real child that outlives `timeout_ms` with a pipe-holding grandchild → `code=124 killed=True`, the
  grandchild dead within `DEADLINE`, the call back within `timeout + reap_grace + kill_drain + slack`.
- Invalid utf-8 on stdout → U+FFFD, no exception — on the success path AND the timeout path (`b'\xff'`

- CRLF output → `\n` in `ExecResult.stdout`.
- A root that exits 0 leaving a pipe-holder → `code=0 killed=False`, returned within `exit_drain` +

- `stdin` is `DEVNULL` against a real child (`sys.stdin.read()` → `''`).

### K.1 `AbortHandle` — cancelling a contained run from another thread

```python
class AbortHandle:
    """A caller's grip on a run_contained call that is blocked on another thread."""
    def __init__(self) -> None: ...            # a Lock; tree/proc None; aborted False; finished False
    def abort(self) -> bool: ...               # thread-safe; if attached and not finished: tree.hard_kill(),
                                               # suppress(OSError): proc.kill(); returns True. If not attached yet:
                                               # marks aborted, returns False — run_contained's attach then kills at once.
```

`run_contained(..., abort: AbortHandle | None = None)`: right after `ProcessTree.attach`, under the handle's
lock, `handle._attach(tree, proc)`; if `handle.aborted` already, kill immediately (the worker's `wait` then
returns and the normal exit path runs). In `finally`, `handle._finish()` so a late `abort()` is a no-op.
`abort()` sends the kills and does NOT wait: the blocked `proc.wait(timeout=)` on the worker returns (root
dead), the exit path drains under its idle rule and returns a `CompletedProcess` with the kill's `returncode`
(`-9` / `1`) to a caller that has already stopped listening. No new thread, no polling.

`ExtensionAPI.exec`:

```python
        abort = AbortHandle()
        try:
            proc = await asyncio.to_thread(run_contained, [command, *args], timeout=timeout_s,
                                           cwd=cwd, env=env_dict, abort=abort)
        except asyncio.CancelledError:
            # Esc, ^C, a cancelled turn: the worker cannot be cancelled, but the tree can be
            # ended, which is what lets the worker return and the process exit (SITE-1).
            abort.abort()
            raise
```

Tests: D.1 `test_abort_from_another_thread_ends_the_tree_and_returns` (fake wait blocked; a thread calls
`abort.abort()` after 0.1 s; POSIX `killpg` + belt recorded / win32 `taskkill` + `terminate_job` + belt; the
call RETURNS a `CompletedProcess` within `INTERRUPT_REAP + 0.5`; `close` once) and
`test_abort_before_attach_kills_at_attach` (abort called before the spawn returns — drive it from the
spied `ProcessTree.attach` — the kill is recorded and the call returns). D.2
`test_abort_ends_a_real_tree_promptly`: root + non-`setsid` grandchild on a helper thread, `abort()` at
0.3 s, both dead within `DEADLINE`, the thread joins within 2 s. Site:
`test_a_cancelled_exec_ends_its_command` — `task = asyncio.create_task(api.exec("sh", ["-c", …sleeper…]))`,
`await asyncio.sleep(0.5)`, `task.cancel()`, `pytest.raises(CancelledError)`, the sleeper (marker file)
dead within `DEADLINE`. Mutant to kill: delete `abort.abort()` in `api.exec` → the site case must go red.

Prose: `run_contained`'s docstring gets one paragraph ("A CALLER ON ANOTHER THREAD"); `api.exec`'s docstring
says a cancelled turn (Esc, ^C in `aelix -p`) now ends the command and the process exits at once, where on
`main` a ^C reached the command through the terminal (0.02 s) and here, without the handle, would have
waited the command's whole remaining life (28.58 s measured). The ADR amendment records it in the exec-site
paragraph; §I's "exec cancellation on Esc" bullet is struck (it landed). CHANGELOG's exec bullet gains
"Esc / ^C now ends the command".
