## A. Decision

**Owner, 2026-09-06 (choice B for #231's open question):** a `/settings` toggle *"@ menu: respect
.gitignore"*, **default ON**. Off → the fd enumerator is asked for `--no-ignore` (the walk has no
ignore rules anyway). `_EXCLUDE_DIRS` stays applied on both arms regardless. Implemented as a global
setting `respect_gitignore` / `respectGitignore` (absent reads `True`), a **live** bool row, and one
callable plumbed from `run_tui` into `FileMentionCompleter`, read fresh on **every** enumeration.

1. **`--no-ignore`, not `--no-ignore-vcs`** (M1–M4). `--no-ignore` restores what root and nested
   `.gitignore`, `.git/info/exclude`, `.ignore`, `.fdignore` and the global ignore file hid;
   `--no-ignore-vcs` leaves `.ignore`/`.fdignore` in force, so it never reaches the walk's behaviour.
   It subsumes `--no-ignore-parent`. Neither touches `--exclude` — but the causality matters, because
   getting it backwards invites deleting the exclude block: **`_has_excluded_component` is what makes
   the two sets equal** (tokens removed and cap lifted, fd's 32 079 paths filter to exactly the walk's
   12 621, symdiff 0), while **the `--exclude` tokens are the budget** keeping the off arm inside
   `--max-results` (12 621 of 20 000 with them, 32 079 without) — M17. Honest one-line statement of
   "off": *everything the ignore files hid, from this tree and its parents, minus the shared exclude
   list* — not "what git ignores".
2. **Global scope; the getter reads `_global_settings`, never the merged view.** Not the
   self-elevation argument of `features_agents` (nothing is granted; the menu inserts a path string).
   "Write global, read merged" makes this row **lie** when a project `.aelix/settings.json` sets the
   key: measured on `check_for_updates`, which has that shape — with a project override of `False`,
   `set_check_for_updates(True)` leaves the getter `False`, so `/settings` prints "→ on" and redraws
   "off" (M10). The #84 class exactly.
3. **`live=True`, by a PULL mechanism — the liveness is in the cache key, not a shell mirror.** The
   completer holds a `Callable[[], bool]`; `_get_tree`'s key becomes `f"{base}\x00{int(respect)}"`.
   Keyed, a flip takes effect on the **next** enumeration; unkeyed the menu is stale a full TTL
   (2.05 s, M8). The flip is live wherever the fd arm answers; on the walk arm both values give the
   *same menu* because the walk applies no ignore rules, and the chosen value is honoured the instant
   an `fd` appears mid-session — same completer object, no restart (M19). Mirroring through
   `_apply_live_setting` is not merely awkward but unavailable: the completer is constructed inline
   inside `merge_completers([...])` and never bound to a name (M18).
4. **Label `Gitignore in @ menu`.** `_open_settings` pads the label column to `max(len(label)) + 2` —
   today 24 (longest, `Autocomplete max items`, 22) — so any label ≤ 22 is free, while the owner's
   phrase (26) would shift the value column of all 23 rows (M11). Capitalised-word-initial like all 22
   existing labels; `select` filters on a case-insensitive substring of the rendered line, so
   `gitignore` reaches it. The owner's sentence does **not** survive in the help either — that panel
   is one unwrapped line cut at the pane width (M20) — so the help is written to 78 cells and the rest
   lives in the README, the ADR amendment and the CHANGELOG.

Rejected: **making the walk honour the setting** (it applies no ignore rules, so "on" is already its
only behaviour; #231 measured why `pathspec` is wrong); **a `/toggle` command or `@`-menu keybinding**
(settings toggle by owner decision; one bit does not need two surfaces); **default OFF** (#231 §A(c)
rejected the wide menu for everyone, and the cap hazard applies verbatim to the off arm — default ON
keeps it a deliberate choice).

### B.2 `settings/settings_manager.py`

Getter/setter beside `get_check_for_updates`. The getter body must stay a **single attribute load**:

```python
    def get_respect_gitignore(self) -> bool:
        """Whether the ``@`` file menu skips files the ignore files hide. Default: True.

        Consumed by ``tui/shell.py``'s completer wiring, which hands this read to
        :class:`FileMentionCompleter` and calls it on EVERY enumeration, so a
        ``/settings`` flip is live (the tree cache is keyed by the flag).

        GLOBAL cell only, never the merged ``self._settings`` — NOT the
        self-elevation argument of :meth:`get_features_agents` (nothing is granted
        here; the menu inserts a path string), but honesty of the row: under
        write-global/read-merged a project ``.aelix/settings.json`` carrying this
        key makes the toggle a no-op on screen. Measured on ``check_for_updates``,
        which has that shape: with a project override of ``False``,
        ``set_check_for_updates(True)`` leaves the getter ``False``, so
        ``/settings`` prints "→ on" and redraws "off".

        Read on the COMPLETER WORKER THREAD (``ThreadedCompleter`` drains the sync
        generator in an executor — measured, the read landed on ``asyncio_0``,
        never ``MainThread``) while ``_open_settings`` writes from the loop
        thread. Benign for any candidate body, because ``reload()`` REBINDS
        ``self._global_settings`` rather than mutating it, so a reader gets an old
        or a new object, never a torn one (200 concurrent read/flip rounds, no
        error). What this pins is therefore COST, not safety: one attribute load,
        never ``get_global_settings()``/``get_settings()``, which ``deepcopy`` the
        whole 43-field tree — 8.67 µs against 0.018 µs, once per keystroke.
        """

        value = self._global_settings.respect_gitignore
        return True if value is None else bool(value)

    def set_respect_gitignore(self, enabled: bool) -> None:
        """Persist the ``@``-menu ignore switch (GLOBAL scope).

        Global-only for the same reason the getter is: a setting the getter
        refuses to read from the project scope must never be written there.
        ``_save()`` only ENQUEUES — the caller must ``await flush()``
        (``_open_settings`` does).
        """

        self._global_settings.respect_gitignore = bool(enabled)
        self._mark_modified("respect_gitignore")
        self._save()
```

### B.3 `tui/completion.py`

`_fd_enumerate` gains a keyword-only flag. The token goes **right after `--color never`, before the
`--exclude` block**, so that block and the `--max-results` tail both stay contiguous (rev 1's prose
and snippet disagreed; the snippet was wrong):

```python
def _fd_enumerate(fd_bin: str, base: Path, *, no_ignore: bool = False) -> list[str] | None:
    ...
    argv = [fd_bin, "--type", "f", "--type", "d", "--type", "l", "--hidden", "--color", "never"]
    if no_ignore:
        argv.append("--no-ignore")
    for excluded in _EXCLUDE_DIRS:
        argv += ["--exclude", excluded]
    argv += ["--max-results", str(_TREE_ENUM_CAP)]
```

Docstring clause (M1/M2/M4/M17): *"``--no-ignore`` (#238, off by default) lifts every ignore file fd
consults — root and nested ``.gitignore``, ``.git/info/exclude``, ``.ignore``, ``.fdignore``, the
global ignore file, and the same files in PARENT directories of ``base``, which is why
``--no-ignore-parent`` is not also needed. ``--no-ignore-vcs`` is deliberately NOT used: it leaves
``.ignore``/``.fdignore`` in force. ``--exclude`` is unaffected either way, and the two roles are not
interchangeable: ``_has_excluded_component`` is what makes the off arm EQUAL to the walk's set, while
the ``--exclude`` tokens keep it inside ``--max-results`` — measured, 12 621 of the 20 000 budget with
them and 32 079 without, and with them dropped and the cap lifted those 32 079 filter down to exactly
the walk's 12 621. They are the budget, not the filter; do not drop them as redundant."*

`_enumerate_tree` takes the flag positionally-or-by-keyword with a `True` default, so every existing
call site and test stays green:

```python
def _enumerate_tree(base: Path, respect_gitignore: bool = True) -> list[str]:
    fd_bin = _fd_binary()
    cands = (
        _fd_enumerate(fd_bin, base, no_ignore=not respect_gitignore) if fd_bin is not None else None
    )
    if cands is None:
        cands = _walk_enumerate(base)
    return [p for p in cands if not _has_excluded_component(p)]
```

Its divergence list gains **one clause only** — the cap hazard is stated in the bullet §D.0 corrects
and must not be restated: *"``respect_gitignore=False`` (the ``/settings`` toggle, #238) closes the
ignore divergence in the OTHER direction: the fd arm is asked for ``--no-ignore``, and the walk arm
needs no change because it never applied ignore rules. See the cap bullet above for what that costs."*

```python
    def __init__(self, get_cwd, max_results: int = 30, *,
                 respect_gitignore: Callable[[], bool] | bool = True) -> None:
        ...
        # A CALLABLE, read on every enumeration — that is the whole of what makes
        # the /settings row live (#238). A snapshot bool would need a restart.
        self._respect_gitignore = (
            respect_gitignore if callable(respect_gitignore) else (lambda: respect_gitignore)
        )

    def _get_tree(self, base: Path) -> list[str]:
        try:
            respect = bool(self._respect_gitignore())
        except Exception:  # noqa: BLE001 — a faulty settings source must not break a keystroke
            respect = True
        # The flag is part of the KEY, not just an input: keyed, a /settings flip
        # is answered by the NEXT keystroke; unkeyed the menu is stale for a full
        # TTL (measured 2.05 s). Flipping back reuses the other entry. This
        # callable runs on the completer WORKER thread (ThreadedCompleter), so it
        # must stay cheap and non-blocking — see get_respect_gitignore.
        key = f"{base}\x00{int(respect)}"
        ...
        tree = _enumerate_tree(base, respect)
```

The `len(self._tree_cache) > 4` bound is **left alone**: rev 1 widened it to `> 8` on the reasoning
that "the old bound held one cwd where it used to hold two", which is wrong both ways (4 entries held
four cwds and now hold two at both values) and the bound is unreachable in production anyway — a
session completes against one or two cwds, at most 4 entries, and the guard fires only *above* 4.
