## 이 레포에서 실제로 물린 규칙

- **`gh run list --branch main --limit 1`은 CI가 아닐 수 있다.** 머지 직후 `Dependency Graph`
  워크플로우가 CI보다 먼저 끝나서, 그걸 "main CI 통과"로 읽을 뻔했다. `--json workflowName`으로
  이름을 보거나 run id를 고정해서 기다릴 것.
- **`--continue`는 mtime 최신을 집는다.** fork한 다음 `--continue`하면 **fork본**으로 간다.
  라이브에서 경합 시나리오를 다시 만들려다 이것 때문에 프롬프트가 안 떴다. 원본을 겨누려면
  `--session <path>`로 명시할 것. (열어 뒀던 설계 질문의 실측 답이기도 하다.)
- **경합 프롬프트의 기본 커서는 플래그에 따라 다르다.** `--continue`/`--resume`은 fork,
  `--session <파일>`은 읽기 전용이 기본이다(그 파일을 콕 집어 말한 사람에게 다른 파일을
  기본값으로 주지 않는다). 드라이버로 선택지를 고를 때 이걸 모르면 엉뚱한 걸 고른다.
- **main 체크아웃에 untracked로 써 둔 파일이 fast-forward를 막는다.** 결정 문서를 main 쪽에
  쓰고 워크트리에서 커밋했더니 머지가 거부됐다. 내용이 같은지 `diff`로 확인하고 지웠다.
- **워크트리에는 `AGENTS.md`가 없다**(`.gitignore:65`). 에이전트에게는 절대경로로 준다.
- **서브에이전트는 TTY가 없어 TUI를 띄워 볼 수 없다.** 수정 패스가 정직하게 그렇게 적었고,
  대화형 확인은 내가 pty로 직접 했다. TUI 변경은 CLAUDE.md 9대로 사람이(=메인 루프가) 본다.
- **pty 드라이버는 `os.waitpid(pid, WNOHANG)`로 재야 한다** — 좀비가 `os.kill(pid,0)`에
  답하므로 "안 끝났다"는 거짓 경보가 난다. 이번에도 드라이버에 그 처리를 넣었다.

## 반증된 것 — 다시 믿지 말 것

- **"`filelock.ReadWriteLock`으로 읽기 전용을 서빙하면 된다"** — 아니다. 두 가지 이유로 틀렸다.
  (1) filelock 4.0.1의 `ReadWriteLock`은 **SQLite 기반**이다(`_read_write.py:6,247-249`,
  `sqlite3` 없으면 `None`). flock이 아니라 DB 파일과 저널이 생긴다. (2) 더 결정적으로,
  reader/writer 락은 정의상 동시 writer를 배제하므로 **소유자를 굶긴다** — 읽기 전용이
  존재하는 바로 그 상황을 못 섬긴다. 지금은 읽기 전용이 **락을 잡지 않고**,
  `ReadOnlySessionStorage` 래퍼가 쓰기를 막는다.
- **"의존성 하나 추가는 무게표가 전부다"** — 아니다. 진짜 비용은 **우리 에러 경로가 넓어지는
  것**이고, 그건 **선언한 범위의 가장 오래된 버전**으로 재야 보인다. `filelock>=3.12,<5`에서
  3.12~3.20은 flock 없는 마운트에 `NotImplementedError`를 던진다(soft 폴백은 3.25.2부터).
  `OSError`가 아니라 우리 핸들러를 통과해 나가서, torch·virtualenv·tox가 이미 filelock 3.13을
  핀해 둔 환경 + NFS 세션 디렉터리면 **aelix가 아예 뜨지 않았다.** 지금은 세 문을 다 잡는다.
- **"직접 구현하면 O_EXCL + pid + mtime 하트비트가 필요하다"** — 아니다. 그건 **pi의 우회**다.
  pi가 `proper-lockfile`에 `stale`/`update`를 다는 건 Node에 OS 락 API가 없어서다. Python에는
  `fcntl.flock`과 `LockFileEx`가 있어 커널이 프로세스 사망 시 놓아 준다. 하트비트도 stale
  회수도 필요 없다. (이 세션의 첫 권고가 이 오해 위에 있었다. 실측 후 뒤집었다.)
- **"pi가 이 문제를 안 고치기로 했다"** — 아니다. pi 이슈 #9596·#8848·#8177·#8334가 전부
  같은 결함이고 **전부 신규 기여자 자동 close 봇에 닫혔다**. 메인테이너 판단이 기록된 게 아니다.
  pi mainline에는 지금도 크로스 프로세스 잠금이 없다(`jsonl/repo.ts:98`의 `openSessions`는
  한 프로세스 안에서만 걸리는 Map). 잠금은 `experimental/session-worker.ts:533`과
  `experimental/micro/sessions.ts:44`에만 있고, 둘 다 **거부**한다. fork로 넘기지 않는다.
- **"두 writer를 다 살려 두면 데이터만 지키면 된다"** — pi #8334가 짚은 비용이 하나 더 있다.
  두 writer가 sibling branch를 쓰면 provider에 보내는 **prefix가 매 턴 바뀌어 프롬프트 캐시가
  깨진다.** "꼬리 재읽기만으로 두 터미널 다 쓰게 두기"안의 실질적 약점이고, 갈라놓는 쪽을
  지지하는 근거다.
- **"락은 세션 파일 자체에 걸면 된다"** — Windows `LockFileEx`는 **강제** 락이라 세션 파일을
  잠그면 읽기 전용 뷰어의 `read()`가 거기서만 실패한다. 그래서 `<session>.jsonl.lock`
  사이드카다. POSIX에서는 release 후에도 사이드카를 **지우지 않는다** — 잠긴 파일을 unlink하면
  waiter가 inode별로 갈려 상호배제가 깨진다(upstream의 의도된 선택). 세션 디렉터리에 빈
  `*.jsonl.lock`이 쌓이는 건 정상이고 "청소"하면 안 된다.

## 라이브로 확인한 것 (CLAUDE.md 9·10)

두 프로세스, 실제 모델(openrouter), 격리된 `--session-dir`:

- 경합 프롬프트가 설계대로 렌더링된다(3지선다, `↑/↓ · Enter · Esc`).
- 읽기 전용: `READ-ONLY` 배너, 입력하면 거부 + 이유.
- **`/fork`가 읽기 전용을 푼다** — 풀린 뒤 실제 모델 호출이 성공했다(리뷰가 잡은 blocker).
- **fork가 히스토리를 물려받는다** — "아까 뭐라고 하랬지?"에 모델이 `SEED`로 답했다.
  표시만이 아니라 provider 요청에도 들어간다는 뜻이다.
- 원본 파일은 4줄 그대로, 전 과정에서 무변경.
- 비대화형 경로: 락 보유 중에 `-p`를 치면 exit 1 + 세 플래그 안내.
- `chmod 000 <session>.jsonl.lock` → 소유권을 통과시키지 않고 실제 `errno 13`을 보여 준다
  (수정 전에는 degrade되어 "네가 소유자다"로 통과했다).
