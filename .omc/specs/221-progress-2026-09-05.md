Facts, measured:

1. **Every site leaks the grandchild on POSIX** (A, C, D, E: `survivors=1`). CPython's `run()` kills the
   root only. This is the POSIX half of #221; it is a leak, not a hang.
2. **The Windows half is not measurable here.** On win32 CPython follows `process.kill()` with an
   unbounded `process.communicate()` — the reader threads block in `ReadFile` until every holder of the
   pipe's write end exits, i.e. until the leaked grandchild's 60 s sleep ends, or forever for a daemon.
   The windows leg of the new real-process test measures it (`warnings.warn` of the elapsed).
3. **B is a second shape, and it is Pi #5303/#5753's.** The root exited **0** at once with `done\n` on
   stdout, and `subprocess.run` still raised `TimeoutExpired` 3.3 s later, because `communicate()` waits
   for pipe EOF and the backgrounded grandchild held the write end. So today a successful
   `api.exec("sh", ["-c", "helper &; echo done"])` is reported as `code=124 killed=True` after its whole
   timeout, and on Windows it hangs the `to_thread` worker until the helper exits. Pi fixed this on
   2026-06-15 (`utils/child-process.ts` `waitForChildProcess`: after `exit`, drain the pipes until they
   fall idle for 100 ms, re-armed per chunk, then resolve).

## 2. `process_group=0` and the controlling terminal (rule 10, a spawn-kwarg consequence)

`scratchpad/221/pty_probe.py`: the parent runs under a fresh pty (so it IS the foreground process
group), spawns `sh -c 'read x < /dev/tty; echo got:$x'` two ways, and reads `ps -o stat` after 1 s:

```
same-group       rc=None ps_stat='S+'
process_group=0  rc=None ps_stat='T'
```

A child in a new process group inside the same session **is stopped by `SIGTTIN` the moment it reads
its controlling terminal** (`T`), while the same command in our group waits in the foreground (`S+`).
ADR-0238 measured that a `process_group=0` child can *open* `/dev/tty` (`HAVE_TTY`); it did not measure a
*read*. Consequences for this issue are in the spec (§A.4: the git site); the consequence for #202's
`!command` site (a pinentry/`pass` prompt would stop, not prompt) is recorded in the handoff as a new
issue, not fixed here.

## 3. CPython facts the helper rests on, measured here (py3.12.13, darwin) before implementation

```
$ .venv/bin/python - <<'PY'   (scratchpad/221 fact-check; source in the session transcript)
=== subprocess.run() timeout branch ===
        except TimeoutExpired as exc:
            process.kill()
            if _mswindows:
                # Windows accumulates the output in a single blocking
                # read() call run on child threads, with the timeout
                # being done in a join() on those threads.  communicate()
                # _after_ kill() is required to collect that and add it
                # to the exception.
                exc.stdout, exc.stderr = process.communicate()
            else:
                # POSIX _communicate already populated the output so
                # far into the TimeoutExpired exception.
                process.wait()
            raise
read1 #1 -> 10B at 0.01s; #2 -> 10B at 0.52s; #3 -> b'' at 1.02s (EOF)
stdout type: BufferedReader has read1: True
posix Popen has _handle: False
send_signal src has poll(): True
```

- The issue's quotation of `run()` is verbatim for 3.12 (and 3.11: the branch is unchanged since 3.7).
- `BufferedReader.read1(65536)` on a pipe **returns what is available** (10 bytes at 0.01 s, the next 10 at
  0.52 s) and `b""` at EOF — so a chunked reader thread observes output BEFORE EOF, which is what makes an
  idle timer meaningful. `read(65536)` would block until 65536 bytes or EOF.
- A POSIX `Popen` has no `_handle`; `_retained_handle` returns `None` there (its documented contract).
- `Popen.send_signal` polls before signalling (bpo-38630): the belt `proc.kill()` after a `killpg` that has
  already ended the root does not re-signal a reaped pid.

## 7. Implementation review measurements (2026-09-05, 4 lenses + mutation lane + 2 skeptics per finding)

Recorded here because product prose cites them (spec §K has the resolution table).

- **SITE-1 — `^C` at the exec surface.** A process running `asyncio.run(await asyncio.to_thread(<runner>,
  [python -c 'time.sleep(30)'], timeout=None))`, SIGINT to its process group at 1.5 s (what a terminal `^C`
  does): `main`'s shape (`subprocess.run`, child in our group) → `parent_exited_after_sigint=0.02 s`,
  survivors 0 — the tty's SIGINT reached the child. `run_contained` (own session) → **28.58 s** (the
  child's whole remaining sleep): the signal never reached the child, the worker kept waiting, and
  `Runner.close` → `shutdown_default_executor(THREAD_JOIN_TIMEOUT=300)` → `concurrent.futures.thread.
  _python_exit`'s unbounded join held the process. Closed by `AbortHandle` (§K.1).
- **SITE-2 — the stdin cases were vacuous.** Under pytest's default `--capture=fd`, fd 0 IS `/dev/null`, so
  a child that INHERITS stdin also reads `''`: the main-shape mutant passed `test_exec_gives_the_command_no_
  stdin` (`1 passed in 0.05s`). Planting readable bytes on fd 0 for the call makes inheritance observable
  (real implementation → `''`; mutant → `'SHOULD NOT BE READ\n'`).
- **MUT-2/T2 — `test_no_controlling_terminal` was vacuous.** `.venv/bin/python -c "os.open('/dev/tty')"` on
  this harness → `[Errno 6] Device not configured`: the runner has no controlling terminal, so the child's
  ENXIO is inherited whatever the spawn kwargs; under `process_group=0` the case stayed green without a pty
  and failed only under one. The session id discriminates without a tty: `start_new_session=True` → child
  sid ≠ harness sid; `process_group=0` → equal.
- **M9/E4 — the post-kill drain and its re-arm were unpinned.** With the re-arm deleted, a fake root silent
  for the whole 0.5 s timeout whose kill releases `b'RELEASED'` lost it 4/5 runs (`stdout=b''`); with the
  stamp present 5/5 collected. A tail written synchronously inside `kill()` is a race the reader wins ~half
  the time (4/10, 8/10 in two harnesses) — the pinned case releases it from a thread 20–50 ms after the kill.
- **M10 — rev 1's join shape** rebuilt: `leaked-reader bound: 6.024 s` against the case's 8.0 s bound
  (green); the bound is now 3.5 s.
- **M16 — `all` → `any`** in `_drain` truncates stdout when stderr EOFs first; nothing asserted it.
- **DOC-2 — git's no-terminal message on darwin** is `fatal: could not read Username for '…': Device not
  configured` (rc 128, 0.078 s); `No such device or address` is Linux's `strerror(ENXIO)`.
- **HC3 —** `subprocess.run`'s POSIX timeout branch leaves `.stdout`/`.stderr` **`None`** when nothing was
  read (`_check_timeout` passes `output=None`; measured `stdout=None stderr=None` for a silent child); the
  win32 branch re-`communicate()`s and attaches bytes. Revision 2 had the platforms backwards.
- **DOC-7 — the attach race.** The design review's POSIX lane measured 400/400 `containment_spawn_kwargs()`
  spawns attaching `contained=True` with immediate `ProcessTree.attach` (`attach_contained_False=0
  getpgid_ProcessLookupError=0`): CPython disables the `posix_spawn` path when `process_group`/`setsid` is
  requested and the `_posixsubprocess` child does its `setsid`/`setpgid` before `exec`.
