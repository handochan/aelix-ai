## 0. Baseline — measured on `main` `7fa6796`

`_LocalBashOperations.exec`'s `_drain_to_the_end` reads `state.exited_at`; when it is `None` (no leg
killed anything — the root simply exited) it does `await eof.wait()`, unbounded. EOF arrives only when
the LAST holder of the write end closes it, and `stderr=STDOUT` means one pipe for both.

| probe | `main` |
| --- | --- |
| root exits 0, helper holds the pipe 4 s, `timeout=10` | `exec` returns at **4.036 s**, rc 0 (`probe_main.py` D) |
| same + a `LATE` line 0.5 s after the exit | **4.550 s**, `b'EARLY\nLATE\n'` |
| **`timeout=1.0`**, helper holds 4 s | **4.044 s**, rc 0, `timed_out=False` — the tool's own deadline bounds nothing on this path (`probe_timeout.py`) |
| `timeout=10`, helper holds 13.9 s | **13.939 s** — 39 % past the deadline the model asked for, i.e. there is no ceiling at all |
| chatty holder (writes every 50 ms) for 5 s, any timeout | **5.07 s** |
| pinned case 8 (`…_still_drains_a_short_lived_holders_tail`) | GREEN, warns **0.535 s** darwin / **0.812 s** on the gating windows py3.12 leg |
| case 8b (abort in the window) | GREEN, warns **2.031 s** darwin / **2.312 s** win32 |
| case 8c (turn cancel in the teardown) | GREEN, warns **2.030 s** |
| `pytest tests/tools tests/pi_parity -q` | **688 passed**, 20.57 s |

Two defects, not one. The reported one is the wait; the second is that **`timeout` does not bound the
success path at all** — `nohup server &` holds the call for the helper's life with no ceiling of any
kind, and a model that asked for `timeout=1` waits four seconds and is told the command succeeded
within its deadline.

A third fact decides what the user-facing text may claim: **a backgrounded program's stdout is a pipe,
so it is block-buffered and typically flushes only when it exits.** Measured (`rev2/probe_buffering.py`,
the §E command through a real `Popen` of the resolved shell): `now` reaches the pipe at **+0.003 s** and
`started` at **+4.018 s** — the helper's whole output, not its tail, arrives at its death.

Pi's `utils/child-process.ts::waitForChildProcess` (`/tmp/pi-src` @ `da840b6`): after `exit`, finalize
when both streams ended OR after `EXIT_STDIO_GRACE_MS = 100` of idle, re-armed by every `data` event,
with no cap. `run_contained` (#221) is that rule plus a cap: idle `EXIT_DRAIN_SECONDS = 0.1` from
`max(last_chunk_at, exited_at)`, `drain_until = exited_at + DRAIN_CAP_SECONDS (2.0)`, further bounded by
the original deadline floored one grace past the exit.

## A. Decision

> **Owner, 2026-09-06 (choice A):** the SUCCESS path adopts Pi's idle rule — return once the pipe has
> been idle `EXIT_DRAIN_SECONDS` after the root exited, re-armed by every chunk; the helper keeps
> running; output it writes after the return is not captured (Pi does the same). An abort landing in
> that now-short window still kills nothing — the watcher stays disarmed before the drain (#222 F1
> order; #230's policy, decided the same day).

**Adopted: `run_contained`'s rule and its constants, whole.** Idle 0.1 s armed at
`max(last_chunk_at, root_exited_at)`, cap `root_exited_at + 2.0`, and — when the call has a timeout —
`min(that, max(started_at + timeout, root_exited_at + 0.1))`. One definition of "a drain" in this repo:
the cap arithmetic moves into `_process_tree.py` as `_exit_drain_cap` and both sites call it. That is
also why #230 lands first (§G): it edits the same ten lines of `run_contained`'s exit leg.

Measured, the three candidate caps (`probe_proto.py`, same shell, same children):

| shape | `main` (EOF) | Pi (idle, no cap) | **adopted** (idle + 2.0 + deadline) |
| --- | --- | --- | --- |
| quiet holder 4 s, `LATE` at exit+0.5 s, `timeout=10` | 4.550 s, `LATE` kept | **0.125 s**, `LATE` cut | **0.128 s**, `LATE` cut |
| chatty holder (50 ms) 5 s, `timeout=10` | 5.073 s | **5.077 s — the idle rule is defeated** | **2.025 s** |
| chatty holder, `timeout=None` (`default_timeout=0`) | 5.060 s | 5.062 s | **2.024 s** |
| chatty holder, `timeout=1.0` | 5.069 s | 5.104 s | **1.002 s** |
| silent holder, pipe held 13.9 s, `timeout=10` | 13.939 s | 0.153 s | **0.126 s** |

- **Pi's uncapped rule is ruled out by the middle rows** — #221 review DOC-1 reproduced at this site: a
  holder that never falls idle never lets go. The bash tool has `api.exec`'s escape hatch too
  (`default_timeout=0` disables the knob; `timeout=None` reaches `exec`), so the idle rule would be the
  only bound and it is not one. **"the remaining timeout only" dies on the same row** (no timeout → no
  cap; the shipped default would make the cap 600 s). **"`DRAIN_CAP_SECONDS` only" dies on the fourth
  row** — a `timeout=1.0` call still came back at 2.025 s; the deadline term is what makes the tool's
  knob mean anything here. **Keeping EOF** is the issue.

**Arming from `max(last_chunk_at, exited_at)` and not from `last_chunk_at` alone** is load-bearing here
too (#221 PI-1). A root that writes, goes quiet 0.30 s and exits, with the helper writing 0.05 s after
the exit: adopted → **0.491 s, `b'EARLY\nLATE\n'`**; armed from the last chunk only → **0.380 s,
`b'EARLY\n'`** (`probe_arm.py`). The grace is measured from the EXIT.

**Nothing else in the teardown moves.** The watcher is still disarmed before the drain, so an abort in
the window fires into nothing: measured with a chatty tail keeping the window open, `rc=0`,
`timed_out=False`, **helper ALIVE** (`probe_abort.py`). #230's policy is unchanged, and its window is
now at most 2.0 s wide instead of the holder's lifetime.

**No cost on ordinary commands.** `echo hi` ×10: median **6.7 ms** on `main`, **6.1 ms** adopted (max
7.9 ms both) — the loop ends on `eof.is_set()` first, so the grace is only ever paid by a call that has
a holder. 2 MiB in 2048 flushed writes: **2 097 152 bytes, 0.022 s**, byte-identical to `main`
(`probe_latency.py`). **What the model loses is not just a tail:** stdout being block-buffered (§0), in
practice it sees **none** of a backgrounded server's output. That is Pi's behaviour and the owner's
choice; it goes into the ADR, the CHANGELOG and the flipped case's docstring with the workaround named
(`nohup … > dev.log 2>&1 &`, or run it unbuffered).

## B. Code changes

### `packages/aelix-ai/src/aelix_ai/utils/_process_tree.py` — TWO changes

**B.4 — `_exit_drain_cap`, next to the constants**, with `run_contained`'s exit leg calling it instead
of spelling it inline. Add it to `__all__` (the list is "exactly what the sites import"), between
`_end_the_tree` and `_retained_handle`.

```python
def _exit_drain_cap(exited_at: float, *, started_at: float, timeout: float | None) -> float:
    """The absolute end of a post-EXIT drain — one definition, two sites.

    ``DRAIN_CAP_SECONDS`` past the exit, and no later than the deadline the
    caller asked for, floored one ``EXIT_DRAIN_SECONDS`` past the exit so a root
    that exits at ``deadline - 1 ms`` still keeps its own tail (#221 review
    POSIX-2/CS8).

    A non-positive ``timeout`` is deliberately NOT special-cased. It reads as a
    deadline already past, so the floor hands it ``exited_at +
    EXIT_DRAIN_SECONDS`` — which is exactly what :func:`run_contained` does
    today, and keeping it is what makes this a byte-identical extraction rather
    than a behaviour change at a landed site. Neither caller can produce one
    (``_resolve_call_timeout`` returns a positive value or ``None``; ``api.exec``
    maps ``timeout_ms=0`` to ``None``), and ``proc.wait(0)`` does NOT "only
    raise" — CPython reaps with ``WNOHANG`` before it checks the remaining time,
    so an already-exited child returns from it (measured: 25 µs; under GIL load
    ``run_contained(timeout=0)`` took the exit leg 40/40) (#232 critique TL-4).
    """

    cap = exited_at + DRAIN_CAP_SECONDS
    if timeout is not None:
        cap = min(cap, max(started_at + timeout, exited_at + EXIT_DRAIN_SECONDS))
    return cap
```

**B.5 — `_PipeReader` must stop pinning the caller's callback when it detaches.** Today `run` caches
`on_chunk = self._on_chunk` in a frame local before the loop, and a reader parked in `read1` on a
helper's pipe keeps that frame — so the lambda → `_deliver` → `on_data` chain survives the return, and
at `create_bash_tool`'s `execute` (`on_data=chunks.append`, truncation only after the join) that is the
command's FULL raw output. Measured: five successful calls each backgrounding a 60 s silent holder
pinned **20 MiB**; one 8 MiB command pinned **8 MiB**; `main` pinned nothing only because it did not
return. Clearing it from inside the detached branch does NOT work — that branch runs only when a chunk
arrives and a silent holder never writes again (measured inert for exactly the `nohup server &` shape).
The release must come from the CALLER's thread, and the loop must hold no local:

```python
    def run(self) -> None:
        ...
        # NOT a cached ``self._on_chunk``: a reader parked in ``read1`` on a
        # helper's pipe keeps its frame, and #232 makes that the ORDINARY end of
        # a successful call — a local would pin the caller's ``on_data`` graph
        # (at the bash tool, the command's whole raw output) for the holder's
        # life. Only the BOOL is cached (#232 critique AD-3).
        has_on_chunk = self._on_chunk is not None
        ...
                if has_on_chunk:
                    on_chunk = self._on_chunk
                    if on_chunk is not None:
                        on_chunk(chunk)
                    on_chunk = None  # released before the next blocking read
                else:
                    self.chunks.append(chunk)

    def detach(self) -> None:
        ...
        self._detached = True
        # The caller's thread drops the callback graph HERE, so it goes whether
        # or not the holder ever writes again (#232 critique AD-3).
        self._on_chunk = None
        self.chunks = []
```

The `has_on_chunk` bool is load-bearing, not stylistic: with a bare `is not None` test, an in-flight
chunk arriving after `detach` cleared the attribute would fall into `self.chunks.append` and re-fill the
list `detach` just emptied. With it, that chunk is dropped — which strengthens `detach`'s "RETAINED
AFTERWARDS IS AT MOST ONE IN-FLIGHT CHUNK" to "nothing" at the bash site. `run_contained`'s readers pass
no `on_chunk` and take the unchanged branch. Measured: **0 MiB pinned across 5 calls** (silent and
chatty holders); `tests/process_tree tests/tools tests/pi_parity` **786 passed** with B.5 under `main`'s
drain rule, and **783 passed / 3 failed** under the adopted rule where the three are exactly C.1/C.4/C.5.

### `packages/aelix-coding-agent/src/aelix_coding_agent/tools/bash.py`

`_LocalBashOperations.exec` only. Import `_exit_drain_cap`. Four edits (+24 lines net, measured on the
prototype):

1. `started_at = time.monotonic()` immediately before the `subprocess.Popen`, with `run_contained`'s
   CS5 reason in the comment: the deadline the cap is measured against must be the same origin the
   `proc.wait(timeout)` below enforces.
2. `_root_exited_at: float | None = None` beside `_timed_out`. It is **not** `state.exited_at`:
   `_ReadState.exited_at` is documented as *the kill instant*, `_mark_the_kill` stamps only the first
   of the three kill legs, and `_drain_to_the_end` reads its `None`-ness to decide which cap applies.
   Folding the ordinary exit into it would make the timeout/abort label logic unreadable and the kill
   drain unreachable.
3. `_wait` stamps the exit **on the worker thread**, not after the `await` resumes:

```python
        async def _wait() -> int | None:
            nonlocal _timed_out

            def _wait_and_stamp() -> int:
                # On the WORKER thread, one statement after ``wait`` returns:
                # the 0.1 s grace is measured from the exit, and a loaded loop
                # can take milliseconds to resume this coroutine — the same
                # argument ``_mark_the_kill`` makes about the ladder's cost.
                nonlocal _root_exited_at
                code = proc.wait(timeout)
                _root_exited_at = time.monotonic()
                return code

            try:
                return await asyncio.to_thread(_wait_and_stamp)
            except subprocess.TimeoutExpired:
                ...  # unchanged
```

4. `_drain_past_the_kill(exited_at)` becomes `_drain_after_the_exit(armed_from, *, cap)` — the same
   loop, the cap passed in rather than computed from `KILL_DRAIN_SECONDS` inside — and
   `_drain_to_the_end` picks the arming instant and the cap:

```python
        async def _drain_to_the_end() -> None:
            killed_at = state.exited_at
            if killed_at is not None:
                await _drain_after_the_exit(killed_at, cap=killed_at + KILL_DRAIN_SECONDS)
                return
            # The root exited on its own (#232). Pi's idle rule under
            # ``run_contained``'s cap: the helper it backgrounded keeps running
            # and whatever it writes after this returns is not captured.
            # ``or time.monotonic()``: no leg stamped anything only if ``_wait``
            # raised something neither ``except`` catches (#233's window), and a
            # drain armed at "now" is the honest fallback there.
            exited_at = _root_exited_at or time.monotonic()
            cap = _exit_drain_cap(exited_at, started_at=started_at, timeout=timeout)
            await _drain_after_the_exit(exited_at, cap=cap)
```

The `await asyncio.sleep(0)` at the end of the drain, the four-`finally` order (watcher → drain →
detach → close), `_deliver`/`delivering`, `_mark_the_kill` and every kill leg stay exactly as #222/#234
left them. **The yield's TEXT does not move; its STATUS does** — it is now the only thing that delivers
a chunk queued behind a drain that ended on the timeout or the cap, on the success path as well as the
kill legs (§C.7, mutation (h)). Comments that say the success path drains to EOF are rewritten in place,
`(#232)` cited.

**C.3 — new, pure, in `tests/process_tree/test_run_contained.py`** (beside `test_the_deadline_caps_the_drain_but_keeps_one_grace`,
which is where this arithmetic already lives, and in the component that owns the function):
`test_the_exit_drain_cap_bounds_by_the_deadline`. **Five** arms of `_exit_drain_cap`: `timeout=None` →
`exit + 2.0`; a generous timeout → `exit + 2.0`; a tight one → `started + timeout`; a root that exits
**after** the deadline → floored at `exit + 0.1`; and **`timeout=0.0` → `exit + 0.1`, the same floor** —
the arm that keeps this an extraction. `Popen.wait(0)` reaps with `WNOHANG` before it checks the
remaining time, so a `timeout=0` call reaches the exit leg rather than the timeout ladder (measured
0/300 idle, **40/40 under GIL load**, i.e. what a loaded CI runner does), and `tests/process_tree/` has
no `timeout <= 0` arm at all (`grep -rnE "timeout\s*=\s*-?0(\.0+)?([^.0-9]|$)" tests/process_tree/` →
nothing). Without this arm, special-casing `timeout <= 0` as "no deadline" would silently loosen
`run_contained`'s cap from `exit + 0.1` to `exit + 2.0` and no case would notice. Deterministic, no
processes; this is what kills the cap mutations without a timing race.

**C.4 — repair case 8b, and the script it shares with 8c.** Under the new rule the case as written
measures nothing: `exec` returns at ~0.1 s and the abort at 0.3 s lands **after** it (§H row 12).
Neither existing knob repairs it, and both were measured. A longer `hold` makes the existing tail
*quieter*, not chattier — it is one write after `time.sleep(hold)` — so the drain still ends on the idle
