## 이 레포에서 실제로 물린 규칙

- **리베이스는 숫자를 낡게 만든다, 그리고 스위트를 빨갛게 만들 수 있다.** #310을
  `fad2e28`에서 `96f93c0c` 위로 재스택하자 lock이 542→552 앵커가 되고 모호 앵커가
  18→19가 되면서 `tests/test_citation_drift.py`의 `_ANCHORS_TOO_GENERIC_TO_GATE = 18`
  리터럴이 낡아 **스위트가 빨갰다**(`assert 19 <= 18`). 그 래칫은 락의 `stats`가 아니라
  리터럴이라(자기 천장을 못 올리게 하려고 그렇게 만든 것이다) 리베이스마다 사람이 올린다.
  리베이스 뒤 **ruff+types+citations만 돌리고 넘어가면 이걸 못 본다** — 나는 실제로
  그 세 개만 돌리고 지나갔고, 레인 에이전트의 전체 스위트가 잡았다.
- **그래서 리베이스 뒤에는 커밋 메시지의 수치도 다시 재야 한다.** #310의 커밋·독스트링·
  ADR이 "542 anchors / 20 before / 18 after"를 들고 있었고 재스택 후 전부 거짓이 됐다.
  고치는 방식은 **모든 숫자에 SHA를 붙이는 것**이다(`fad2e28에서`, `96f93c0c에서`,
  `이 트리에서`). 다음 리베이스에서 또 낡지 않는다.
- **인용 lock 충돌은 4단계 그대로가 맞다.** (1) 충돌은 upstream 쪽을 통째로 취하고,
  (2) `--check`가 부르는 대상 줄을 **sed로 직접 읽어** 인용 산문과 맞는지 확인하고,
  (3) `--fix`, (4) `git diff citations.lock.json`으로 바뀐 키가 방금 읽은 것뿐인지 대조.
  이번엔 한 걸음 더 붙였다 — **리베이스 전 브랜치의 lock과 앵커 텍스트를 바이트 비교**해서
  "새로 주장된 것이 없다"를 보였다(#309의 13개 앵커 전부 동일, 사라진 11개는 같은 앵커의
  옛 줄 번호). 이게 가장 싸고 강한 증거다.
- **ADR 번호는 배치 안에서 충돌한다.** 세 레인이 전부 0246을 만들었다. 재검증 패스가
  잡았고, 머지 순서에 맞춰 0246/0247/0248로 나눠 줬다. **배치를 시작할 때 번호를
  미리 배정하는 편이 낫다.**
- **`docs/decisions/README.md`의 ADR 색인은 최근 항목을 오름차순으로 덧붙인다**
  (…0243, 0244, 0245, 0246…). 내림차순으로 넣었다가 두 번 고쳤다. 그 아래 옛 블록이
  내림차순(0226, 0225, …)이라 헷갈린다. **게이트가 없으므로 사람이 본다.**
- **CHANGELOG·README 충돌은 양쪽을 다 남긴다.** 이번 배치의 충돌은 전부
  "두 레인이 각자 새 줄을 같은 자리에 추가"였고, 지난 배치가 필요로 했던
  토큰 단위 3-way 병합은 필요 없었다(같은 행을 둘이 고친 경우가 없었다).
- **게이트 스크립트는 워크트리 자기 것으로 부른다**(이월, 여전히 유효).

## 반증된 것 — 다시 믿지 말 것

- **"서브에이전트는 TTY가 없으니 TUI 라이브 확인은 메인 루프 몫이다"** — **틀렸다.**
  `os.forkpty()`는 **자식에게 새 pty를 준다.** 부모가 TTY를 갖고 있을 필요가 없다 —
  메인 루프도 TTY가 없고, 그래서 메인 루프의 드라이버가 동작하는 것이다. #194 레인의
  서브에이전트가 직접 pty 캡처 4회(두 트리 × 두 세션)를 돌려 메인 루프의 바이트 단위
  수치를 재현했다(`✖` 앞 원시 SGR `\x1b[1;31m` 포함). **TUI 라이브 확인은 위임할 수 있다** —
  캡처를 위임하고 판정(사용자에게 이게 맞아 보이는가)만 들고 있으면 된다. 이 전제가
  지난 세 배치를 한 에이전트 뒤에 직렬화시켰다.
- **"CI가 빨가면 내 변경의 문제"** — 이번 배치는 **두 번 모두 아니었다.**
  #194의 ubuntu py3.12 실패는 **#261**(2 MiB 꼬리 유실 간헐 flake)이었고 그 브랜치는
  `tools/` 아래 파일을 **하나도** 건드리지 않았다(그 이슈에 관측치를 남겼다 — py3.12에서도
  나고 8,192 = 8×1024 부족). #309의 Windows 실패 셋 중 하나는 `tests/process_tree/`의
  벽시계(#313·#315 계열)로, 같은 테스트가 같은 날 다른 세 브랜치 CI에서 통과했다.
- **"그러니 Windows 실패는 다 flake"** — 아니다. #309의 나머지 **둘은 진짜였다.**
  새 테스트가 픽스처로 `echo`를 썼는데 Windows에서 이 도구가 쓰는 셸은 **PowerShell**이라
  CRLF가 나왔다(그 run 자체가 증거다 — 같은 파일의 다른 테스트가 `$(seq 1 100)`을
  전개하면서 동시에 `echo`에서 CRLF를 내는 것은 PowerShell뿐이다). **실패 테스트가 내
  변경이 건드린 표면인지부터 본다**는 규칙이 두 방향으로 다 작동했다.
- **"그 `\r`는 #317의 잔여다"** — 내가 그렇게 브리핑했고 **틀렸다.** #317(`huge + LF + CR`)은
  줄이 **둘** 있어야 성립한다 — 들어맞는 짧은 마지막 줄과, 자리를 내주느라 버려지는 윗줄.
  Windows 테스트가 만난 것은 줄이 **하나**고 버려지는 것이 없으며 fragment 폴백이 설계대로
  꼬리를 돌려준다. **세 번째 것**이고 이미 트리에 적혀 있다: 헬퍼가 `\r`를 남기는 것은
  그게 `read`의 헬퍼이기도 해서 받은 바이트를 왕복시켜야 하기 때문이고, `!cmd` 레코드는
  `_normalise_trailing_terminators`(`cli/repl.py:138`)로 접지만 **모델 대면 도구에는
  그 가드가 없다.** 이 비대칭은 열린 채로 남는다.
- **"Codex 교차 리뷰를 돌리면 결과가 나온다"** — 이번엔 **넷 다 ChatGPT 사용 한도에
  걸려 최종 보고 없이 끊겼다**(재시도 가능 시각 09-24). 그래도 하나가 죽기 전에 실질적인
  반례를 냈고(내가 재측정해 #309의 잔여 표를 만들었다), 나머지 셋은 아무것도 못 냈다.
  **"교차 리뷰 없음"과 "돌렸는데 한도로 끊김"은 다른 문장이고**, 네 커밋 전부 후자로 적었다.
  `codex exec`는 `run_in_background` **한 번에 한 레인**으로, `< /dev/null`을 붙여 띄운다
  (`( … ) &`를 한 Bash 호출 안에 넣으면 런처가 끝날 때 같이 죽는다 — 실제로 한 번 죽였다).
- **"공유 스크래치패드는 에이전트별로 나뉜다"** — 아니다. **세션 단위**다. #309 레인이
  `<scratchpad>/msg.txt`에 쓴 초안을 #311 레인이 덮어썼다. 병렬 에이전트에는 각자
  `/tmp/<task>-<n>/`을 지정한다.

## 이 배치를 돌린 방식

지난 배치와 같다 — worktree 4개 병렬, 레인마다 **구현 → 독립 리뷰(보고만) → 수정 →
독립 재검증**, 그 위에 Codex. 값이 난 지점도 같았다(리뷰어에게 고치지 말라고 못박은 것,
새 테스트를 수정 전 코드에서 빨갛게 만들어 보라고 시킨 것, 범위를 이슈로 밀어낸 것).

이번에 **새로 배운 것 셋**:

1. **재검증 패스가 두 레인을 fail로 떨어뜨렸는데 둘 다 코드가 아니라 기록이었다**
   (#309의 "호출자 여섯", #310의 사보타주 표 7/4). 게이트 넷이 전부 green인 커밋에서
   나온 판정이다. 기록을 대조하는 패스는 코드를 대조하는 패스와 **다른 것을 잡는다**.
2. **리베이스 자체가 결함을 만든다.** 위 "이 레포에서 실제로 물린 규칙" 첫 두 항목.
   배치의 마지막 레인이 가장 많이 리베이스되므로 가장 많이 상한다.
3. **브랜치를 스택으로 쌓으면 브랜치 CI가 커밋별 CI가 된다.** `fix/194`의 tip이
   main+311+194, `fix/309`가 +309, `fix/310`이 +310이므로, 네 브랜치 CI가 그대로
   main의 네 커밋에 대한 CI다. main으로 ff 할 때 앞 run이 취소되는 것을 감수해도
   **각 커밋이 green이었다는 증거가 남는다.**
