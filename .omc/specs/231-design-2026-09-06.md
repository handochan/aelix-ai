**Revision 2** answers a nine-finding critique (`231-critique-resolution-2026-09-06.md`). Four of its

## 0. Baseline — what is true on `main` (measured, darwin 25.4.0, py3.12, `/tmp/wt-231/.venv`)

`_enumerate_tree`'s docstring claims fd and the walk "produce the SAME set of matchable paths on
every machine", and `_has_excluded_component`'s claims its predicate is "applied to BOTH the `fd`
and `os.walk` outputs". **Both are false.** Five ways, four of them measured (probes in
`…/scratchpad/231/`, numbers in §H):

1. **The shared exclude predicate is applied to fd only.** `_enumerate_tree` post-filters fd's
   output and returns `_walk_enumerate(base)` unfiltered, and the walk prunes *directory names*
   only — it never filters a file. So a FILE whose name is in `_EXCLUDE_DIRS` is offered by the
   walk and hidden by fd. Needs no git repo and no `.gitignore`: on a plain tree the symmetric
   difference is `['.git', 'build', 'src/dist']`. The common instance is `.git`, a plain gitdir
   *pointer file* in every linked worktree and every submodule — measured on this issue's own
   worktree, walk 1458 vs fd 1457, the one path being `.git` (M11).
2. **VCS ignore is fd-only, and not uniformly.** The issue's table reproduces with the managed fd
   (`~/.aelix/agent/bin/fd`, **10.4.2**, not 10.5.0): walk six paths, fd the same **minus**
   `ignored-by-git.md`. The gitignore family (root and nested `.gitignore`, `.git/info/exclude`, the
   global `core.excludesFile`) applies only *inside* a repo; `.ignore` and `.fdignore` apply
   **anywhere**, nested and from a directory *above* the base (M3/M3b). And it is *git's* ignore
   machinery, not the VCS's: fd lists a file named by `.hgignore` inside an `.hg` repo (M12).
3. **Symlinks.** fd's argv is `--type f --type d`, so a symlink is neither: on a tree with a dir
   link, a file link, a broken link and a self-loop, the walk returns all four and **fd returns
   none of them**. Not in the issue; found in this lane.
4. **Non-UTF-8 names.** fd decodes utf-8/replace → `'caf<0xFFFD>.py'`; the walk gets its names from
   `os.walk(str(base))`, i.e. `os.fsdecode` → `'caf\udce9.py'`, a **lone surrogate**, which is the
   exact value `_fd_enumerate`'s own docstring says it declined to hand prompt_toolkit. **Not
   measured end to end**: APFS refuses the filename (`OSError 92`), and encoding that str raises
   `UnicodeEncodeError` — so whether the walk arm *renders* differently or *raises* is unknown.
5. **The cap is spent differently.** `_TREE_ENUM_CAP = 20000` bounds *both* arms (fd through
   `--max-results`), but only the walk spends that budget on ignored paths, and only the walk loses
   whole unreached subtrees (`os.walk` descends depth-first in `os.scandir` order). Measured: an
   ignored 22 000-file `target/` beside twelve real source files → walk 20000 paths, **ten of the
   twelve gone**, a **two-row** `@` menu where fd gives twelve (M13). Silent: truncating is
   *faster*, and nothing logs.

And it is live on the owner's box in the worst direction: `shutil.which('fd')` → `None` while
`~/.aelix/agent/bin/fd` **exists**, so `_fd_binary()` returns `None` and the TUI uses the walk.
**How big that is, is a property of a checkout, not of this repository.** On the owner's working
copy — nine agent worktree copies of the repo under `.claude/worktrees/` (10249 of its 12618 walk
paths, 81 %) plus `.omc/state`/`.omc/sessions`/`.omc/recovered-91` (871) — the completer
fuzzy-matches **12618** paths instead of **1482**: `@completionpy` spends 3 of its 8 rows on stale
worktree copies and **never offers the real `…/tui/completion.py`**, and `@settingsjson` returns 8
rows of `.omc/state/sessions/**` where fd returns none. On a **clean clone of the same commit both
arms return the same 1457 paths** — and still do after `uv sync` and a pytest run, because
everything this repo ignores (`.venv`, `__pycache__`, `.pytest_cache`, `.ruff_cache`, `dist`,
`build`) is already in `_EXCLUDE_DIRS`, which both arms apply (M5c). It also drifts: the same walk
measured 12606 earlier the same day.

## A. Decision

**(a) Tell the truth, (b′) use the fd Aelix already downloaded, and close the two divergences that
cost one line each.** Concretely:

1. **Docstrings state the real contract** (module, `_fd_binary`, `_fd_enumerate`, `_enumerate_tree`,
   `_has_excluded_component`, `_walk_enumerate`), drafted verbatim in §B so nothing is transcribed
   from memory. The predicate half of the old sentence was *not* "always true": it was applied to
   fd only, and item 4 below is what makes it true.
2. **`_fd_binary()` looks in the agent bin dir *first*, then PATH** — the order
   `ensure_tool`/`get_tool_path` already give `find` (and `grep`, for `rg`), and the order Pi's
   `getToolPath` uses ("Check our tools directory first"). Measured: with a copy on PATH *and* a
   managed copy present, PATH-first would make the `@` menu and the `find` tool run **different
   binaries** (M1d). Pi-shaped in the same breath — Pi resolves fd through its own managed
   `~/.pi/agent/bin` and has *no* fuzzy fallback without it; the completer was Aelix's one consumer
   that ignored the binary sitting next to it. This shrinks the walk population to machines that
   never ran `find` — the fallback ADR-0193 intended. It does not shrink it to nothing, and it is
   not a speed win everywhere (M14).
3. **`--type l` is added to fd's argv.** Measured with item 4 applied: on a tree carrying both
   symlinks *and* excluded-name entries, fd's set is then **exactly** the walk's, for +0.1 ms. One
   token removes divergence #3 instead of documenting it.
4. **`_has_excluded_component` is applied to the walk arm too** — one line in `_enumerate_tree`.
   This is what makes the "shared predicate" sentence true rather than re-asserted. It also stops
   the menu offering the `.git` pointer file in every linked worktree and submodule, and it is what
   earns item 3 its "exactly" (M4b). Cost: 3.9 ms over 12618 paths (10–11 ms on a nine-lane-loaded
   machine), behind the 2 s TTL cache and `ThreadedCompleter`.

Rejected, with the evidence:

- **(b) make the walk apply fd's ignore rules with `pathspec`.** fd uses the `ignore` crate: root
  and nested `.gitignore`, `.git/info/exclude`, `.ignore`, `.fdignore`, the global
  `core.excludesFile` — all five measured to bite here, and not on the same terms (§0.2). A
  root-`.gitignore`-only approximation would make the docstring differently false, and `pathspec`
  reaches the TUI only through `aelix-agent-core`.
- **(c) `fd --no-ignore`, making fd match the walk.** Exact (zero symmetric difference) and the
  wrong direction: every fd user gets the wide menu, and fd starts spending the 20000 cap on ignored
  trees — precisely the silent-truncation failure §0.5 measures.
- **`ensure_tool('fd')` at TUI mount** (Pi does this). Network at startup, against `--offline`
  posture. Follow-up issue, §G.
- **Telling the user which enumerator is in use** (a statusline hint). Scope.

The divergence is not eliminated by any of this. Two of five are closed in code; VCS ignore, the
non-UTF-8 rendering and the cap asymmetry are *documented* and the population that meets them is
reduced. That is the decision, and the ADR amendment says it in those words.

## B. Code changes — `packages/aelix-coding-agent/src/aelix_coding_agent/tui/completion.py`

**`_fd_binary()`** — managed bin dir first, then PATH; lazy import and fail-soft, both for stated
reasons:

```python
def _fd_binary() -> str | None:
    """The ``fd`` executable, or ``None``.

    Looked for in the agent bin dir FIRST (the copy ``ensure_tool`` downloads for
    the ``find`` tool), then on PATH as ``fd``/``fdfind`` — the order
    ``get_tool_path`` gives ``find``/``grep`` and Pi's ``getToolPath`` gives Pi,
    so the ``@`` menu and the ``find`` tool can never run different binaries.
    Not ``get_tool_path`` itself: its PATH arm is an unbounded
    ``subprocess.run([cmd, "--version"])`` — measured 5.3 s against a PATH ``fd``
    that sleeps — on a path whose own fd spawn is bounded at ``_FD_TIMEOUT``.
    ``shutil.which`` spawns nothing. Not memoized: it is consulted once per
    (TTL-cached) enumeration, a test that installs/removes ``fd`` is reflected
    immediately, and a mid-session ``find`` download is picked up at the next TTL
    expiry.
    """

    try:
        # Function-local so ``get_bin_dir`` stays a LIVE lookup: the tests
        # monkeypatch ``cli.config.get_bin_dir`` and a module-level
        # ``from … import`` would bind the name here, silently ignoring the patch
        # (M8b). NOT a cycle guard — importing ``cli`` reaches no ``tui`` module
        # and ``tui/statusline_store.py`` already takes this edge at module level.
        # (``util/shell_env.py`` is lazy for a REAL cycle: bash → shell_env →
        # cli.config → repl → bash.)
        from aelix_coding_agent.cli.config import get_bin_dir

        managed = shutil.which("fd", path=get_bin_dir())
    except Exception:  # noqa: BLE001 — a faulty config must not break a keystroke
        managed = None
    return managed or shutil.which("fd") or shutil.which("fdfind")
```

Resolution goes through `cli.config.get_bin_dir()` rather than `util.shell_env.get_shell_env()`'s
PATH: both find the same binary (M1b), but `get_shell_env()` builds a whole environment dict for one
directory and is itself the module whose `cli.config` import guards a real cycle. Drop the
`# noqa: PLC0415` the first draft carried — measured, `PL` rules are not in this repo's ruff
`select`, so it asserts a rule that does not fire.

**`_enumerate_tree()`** — the predicate moves out of the fd branch so it runs on whichever arm
answered:

```python
    fd_bin = _fd_binary()
    cands = _fd_enumerate(fd_bin, base) if fd_bin is not None else None
    if cands is None:
        cands = _walk_enumerate(base)
    return [p for p in cands if not _has_excluded_component(p)]
```

**`_fd_enumerate()`** — argv gains `"--type", "l"` next to `--type f --type d`. Nothing else
changes (same `run_contained` call, same kwargs — the test seam pins them).

**Docstrings.** The load-bearing sentences, drafted here so the implementer copies a true one:

- **`_enumerate_tree`** — *"The two enumerators do **not** offer the same list. `_EXCLUDE_DIRS` is
  applied to both (below) and always holds. What differs: git's ignore rules are fd-only — inside a
  git repo fd hides what `.gitignore` (root and nested), `.git/info/exclude` and git's global
  excludes file hide; outside a repo none of those apply, but fd still honours `.ignore` and
  `.fdignore`, even from a parent directory — and the walk applies no ignore rules at all. An
  undecodable filename also arrives differently (U+FFFD from fd; a lone surrogate from the walk,
  whose rendering is unmeasured). `_TREE_ENUM_CAP` bounds both arms, but only the walk spends that
  budget on paths the VCS ignores; where the real tree itself exceeds the cap both arms truncate and
  fd's kept set is not stable run to run (1747 of 20000 paths differed between consecutive runs)."*
- **`_has_excluded_component`** — keep "the single source of truth for the exclude contract", and
  say it is applied at one site to whichever enumerator answered, *"which #231 made true: it used
  to run on fd's output only, so a FILE named like an excluded directory — the `.git` pointer file
  in every linked worktree — was offered by the walk and hidden by fd."*
- **`_walk_enumerate`** — *"The cap is a hard stop in walk order, not a sample: `os.walk` descends
  depth-first in `os.scandir` order, so once one large subtree exhausts the budget every directory
  not yet reached is missing — no warning, and no latency signal, because truncating is faster. It
  bites hardest on a tree the VCS ignores that `_EXCLUDE_DIRS` does not name (`target/`, `vendor/`,
  `Pods/`, `.terraform/`, `_build/`), which fd never emits and so never pays for; measured on #231,
  an ignored 22 000-file `target/` beside twelve real source files left the `@` menu two rows where
  fd gave twelve, and which two survived was `os.scandir` order. Top-level directories still appear,
  so the drill-in listing looks healthy while fuzzy `@` cannot reach their contents. An
  excluded-name FILE still costs a slot: it is filtered by `_enumerate_tree`, after the cap."*
- **Module header** — *"fd is only ever a speed upgrade, never a hard dependency"* loses its first
  half and keeps its second: measured (M14), fd trades a ~8 ms spawn for a walk that scales with the
  tree, so it **loses** below roughly 5 000 paths and wins on a large or ignore-heavy one. Replace
  with: *fd is never required; it is faster only once the tree is large or heavily ignored, and — the
  real point — it offers a **different** list.*
- **`_fd_enumerate`** — add the `--type l` clause and the U+FFFD half of the non-UTF-8 sentence
  (its current text about declining surrogates stays; it is true and it is now half of a documented
  asymmetry).

**Bounds and hygiene.** Every case is `tmp_path` + `monkeypatch` only — no subprocess, no network,
no `git`, nothing to clean up beyond pytest's own tmp. `PATH` is neutered with `monkeypatch.setenv`
so a developer's real `fd` cannot leak in. Expected added runtime **< 60 ms**. One win32 caveat the
negative assertions must survive: `shutil.which` searches the process CWD *before* the directory
handed to `path=` (unconditionally on 3.11; on 3.12 whenever `NeedCurrentDirectoryForExePath`),
so cases 1–3 must `monkeypatch.chdir(tmp_path / "cwd")` into an empty directory rather than trust
pytest's invocation dir. (The `fd` vs `fd.exe` arms of case 2 are safe either way: neither 3.11 nor
3.12 matches a bare `fd` on win32.)

**The `get_bin_dir()` seam for cases 1–5 is `monkeypatch.setattr(aelix_coding_agent.cli.config,
"get_bin_dir", …)`** — patch the *defining* module, never `completion`: §B's import is
function-local, so `monkeypatch.setattr(completion_mod, "get_bin_dir", …)` raises `AttributeError`
(measured). Do not reach for `HOME`: `tests/tui/conftest.py`'s autouse `_isolate_agent_dir` sets
`AELIX_CODING_AGENT_DIR`, which `get_agent_dir()` prefers over `Path.home()`, so a `setenv("HOME",
…)` case measures `None` on every leg. `monkeypatch.setenv("AELIX_CODING_AGENT_DIR", …)` also works
for cases 1–3, but case 4 needs `get_bin_dir` to *raise* and no env value can (measured: `''`, `~`,
`~/x`, `/////`, `~nouser/x`, HOME unset — all return a string), so one seam serves all five.

**Why the suite cannot see the managed fd — measured.** That same autouse fixture points
`AELIX_CODING_AGENT_DIR` at `tmp_path/"agent"` for every test under `tests/tui`, so after (b′)
`get_bin_dir()` inside a completion test is a fresh, *non-existent* per-test directory. With the §B
body installed over `_fd_binary`: **17 calls → 17 bin-dir lookups → 0 hits**, 15 distinct bin dirs,
none existing; the same 17/0 over the whole of `tests/tui`; and exporting
`AELIX_CODING_AGENT_DIR=$HOME/.aelix/agent` for the run does not change it (`monkeypatch.setenv`
wins). **No existing case changes behaviour and none spawns a real fd.** The suite is
host-independent on this axis by construction, not by luck.

Mutation claims in this table were **not** run as a mutation suite; each is a reading of what the
case asserts. The three worth running before the commit are the ones whose cases are green on main
— 3, 7, 9 — and §F says so.

>   Three smaller disagreements went with it. The shared exclude list now really applies to both
>   arms — without `fd` the menu had been offering the `.git` pointer file in every worktree, and
>   any file named `build`/`dist`/`node_modules`; the cost of that consistency is that a root-level
>   `build` *script* stops being offered on the walk arm too, matching what `fd` already did.
>   `fd` was asked for files and directories only, so it dropped every symlink the walk listed —
>   fixed, and the two sets now match exactly on a symlink tree. And one disagreement is bigger than
>   it looks and is documented rather than fixed: both enumerators stop after 20 000 paths, but only
>   the walk counts the files git ignores toward that limit, so in a repo with a large ignored build
>   tree the fallback can run out of budget inside it and never reach your real source directories
>   (measured: an ignored 22 000-file `target/` next to twelve real source files gave the walk two
>   menu rows where `fd` gave twelve). An undecodable filename also still reaches `fd`'s list as `�`;
>   what the walk arm does with it is untested (no filesystem here can hold such a name). Nothing
>   you type is ever passed to the subprocess, and `fd` is still never required. See ADR-0193 and
>   [#231](https://github.com/handochan/aelix-ai/issues/231).

No `docs/guides/` page covers `@` completion; none is added.

## G. Risks, open questions, out of scope

- **This changes what the owner sees.** After (b′) the `@` menu no longer fuzzy-matches
  git-ignored files on any machine that ever ran `find`; after §A.4 it no longer offers `.git` or a
  file named `build`/`dist` on the walk arm either. That is the point, it is measured, and it is in
  the CHANGELOG. The drill-in (`@build/`) still reaches them.
- **OWNER QUESTION (the one thing this lane cannot decide).** (b′) makes the `@` menu narrower on
  the owner's own box, and the owner is the user whose checkout has the ignored population. Is
  "`@` should show what git ignores" ever the wanted behaviour — i.e. does this want a `/settings`
  toggle rather than a silent narrowing? The design proceeds on "no"; the one-token reversal is
  `--no-ignore` (rejected, §A) and the durable answer is the toggle below.
- **The divergence survives.** Two machines still get two lists. A `/settings` toggle ("`@` menu:
  respect .gitignore") would end it for real — **file as a follow-up**, not here.
- **Non-UTF-8 names are documented, not fixed**, and the open question is "renders differently, **or
  raises**": encoding the walk's lone surrogate raises `UnicodeEncodeError` (measured), and APFS
  refuses the filename (Errno 92), so end-to-end behaviour needs a Linux leg. **File a follow-up
  issue**, cite this design.
- **The cap truncates the fallback silently** (§0.5). Value unchanged here; behaviour now
  documented. Follow-up: make the walk prefer breadth, or surface truncation to the user, so the
  fallback degrades visibly. (b′) shrinks but does not remove the affected population — after it the
  walk is what `--offline` / never-ran-`find` machines get, exactly the air-gap population ADR-0193
  wrote the fallback for.
- **`ensure_tool('fd')` at TUI mount** — Pi does it; Aelix would be doing network at startup.
  **Follow-up issue**, decided against here.
- **Divergence from Pi, stated once** since the design leans on Pi elsewhere: Pi's fd argv is
  `--type f --type d --follow --hidden --exclude .git` — no `--type l`, and it *follows* symlinked
  directories. Aelix lists links and follows none. No ADR (ADR-0235).
- **Menu overwrites the statusline** — already filed as **[#133](https://github.com/handochan/aelix-ai/issues/133)**
  (OPEN, item 1, owner-triaged post-beta, ADR-0194 live-terminal caveat). Attach the §E capture to
  that issue; **do not open a duplicate** and do not touch the renderer here.
- **Nothing exercises the managed-bin-dir branch except the new unit cases.** No CI leg installs fd
  (the stub is the only fd on CI), *and* the autouse agent-dir isolation makes `get_bin_dir()` an
  empty tmp dir in every TUI test — so (b′)'s branch has exactly the coverage §C gives it: cases 1
  and 2 resolve *through* the new lookup, case 3 pins that PATH still answers without it, case 4
  pins its exception arm. Its only end-to-end proof is the §E live check. That is also why case 7
  uses the stub rather than a real binary.
- **Not in scope:** the fuzzy scorer, the TTL cache, `ThreadedCompleter`, the value of
  `_TREE_ENUM_CAP` (its documented behaviour is in scope; its number is not).
