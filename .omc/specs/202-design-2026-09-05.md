## A. Decision

**One containment primitive, in the package everything else can import.**

- New module **`packages/aelix-ai/src/aelix_ai/utils/_process_tree.py`**.
  `aelix-ai` is the bottom of the import direction and `_resolve_config.py`
  lives there. `aelix_coding_agent/tools/_process_tree.py` becomes a re-export
  shim so `bash.py`, `_subprocess.py` and their tests keep their imports.
- **POSIX: the tree is the process group we created.** Spawn with
  `start_new_session=True` (rpc child, unchanged) or `process_group=0` (hooks,
  `!command` — a new group in the **same session**, so the controlling terminal
  is kept for credential helpers). Kill with `killpg` on the pgid captured at
  attach. A group **misses any descendant that itself calls `setsid()`** —
  every tool child, every MCP server, and after this change every hook shell
  and `!command` shell spawned by an rpc child. That is by design: the
  descendant walk that reaches them is `reaper.py`'s (ADR-0197 finding I2) and
  this spec does not re-adopt `killpg` as a substitute for it.
- **Windows: the tree is a Job Object.** Spawn with
  `creationflags=CREATE_NEW_PROCESS_GROUP`; immediately after spawn assign the
  child to a job created with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` when the
  site asks for it. Children of members inherit membership (no `BREAKAWAY_OK`),
  so the job reaches `setsid`-equivalents and members whose parent has already
  exited (the #9129 shape) — **Windows containment is strictly stronger than
  POSIX's**, and the ADR says so instead of claiming symmetry. Hard kill =
  `taskkill /T /F` (best effort, while the root is alive) then
  `TerminateJobObject`. Soft kill = `CTRL_BREAK_EVENT` to the child's process
  group; the rpc child installs a `SIGBREAK` handler (the Windows twin of its
  SIGTERM one).
- **`close()` is a release.** POSIX: no signal, ever. win32: `CloseHandle(job)`,
  which ends remaining members **only** for a tree attached with
  `kill_on_close=True` — the rpc child ("one child per task"), not hooks or
  `!command`, which keep today's success-path behaviour everywhere.
- **Fallback when no job could be attached**: `taskkill.exe /T /F /PID`
  resolved from `%SystemRoot%\System32`, bare `taskkill` if that is missing.
  No `TerminateProcess` leg — `/T /F` already ends the root.
- **Never `killpg` a group whose leader is not the pid we spawned.** `attach()`
  verifies `os.getpgid(pid) == pid`; a caller that forgot the spawn kwargs has
  the child in *our* group and gets `contained=False` (root-only kills).

Not changed: `aelix_agents/` (`print_channel.py:969`, `rpc_channel.py`'s
`reap()`/`kill_tree()`, `reaper.py`) — new issue (§H). `tools/bash.py` /
`tools/_subprocess.py` keep `kill_process_tree(pid)` and receive only the
`taskkill.exe` path resolution and the Darwin zombie-leader fallback.

## B. `aelix_ai/utils/_process_tree.py` — the API

```python
__all__ = ["ProcessTree", "containment_spawn_kwargs", "kill_process_tree"]

CREATE_NEW_PROCESS_GROUP = 0x0000_0200   # subprocess.CREATE_NEW_PROCESS_GROUP — literal: the name is win32-only
CTRL_BREAK_EVENT = 1                      # signal.CTRL_BREAK_EVENT — same reason (and SIGHUP on POSIX: never sent there)

def containment_spawn_kwargs(*, new_session: bool = False, platform: str | None = None) -> dict[str, Any]:
    """The kwargs a spawn passes so its child is a tree this module can end.

    POSIX -> {"start_new_session": True} when new_session, else {"process_group": 0}
            (setpgid(0,0): a new group in the SAME session — the controlling tty survives,
             which is what a credential helper behind ``!command`` needs).
    win32 -> {"creationflags": CREATE_NEW_PROCESS_GROUP} (both).
    A caller that already passes ``creationflags`` must OR them; none does.
    """

class ProcessTree:
    """One child this process just spawned, and everything descended from it.

    ``attach`` IMMEDIATELY after the spawn call returns, before any ``await``:
    on win32 the job is assigned then, and only descendants spawned AFTER the
    assignment inherit membership. The pid must be one this process spawned
    with ``containment_spawn_kwargs``; nothing else is safe to ``killpg``.
    """

    pid: int
    contained: bool        # POSIX: the child leads the group we asked for; win32: a job holds the tree
    job: int | None        # read-only; the win32 job handle, None elsewhere / when not contained

    @classmethod
    def attach(cls, pid: int, *, kill_on_close: bool = False, handle: int | None = None,
               platform: str | None = None, api: _Win32Api | None = None) -> "ProcessTree": ...

    def soft_kill(self, *, whole_group: bool = False) -> None:
        """Ask the tree to stop. Never raises.
        POSIX: SIGTERM to the child (``os.kill``); to the group when ``whole_group`` and contained.
        win32: CTRL_BREAK_EVENT to the child's process group (group-wide by construction; ``whole_group``
               is accepted and ignored). Needs a shared console and CREATE_NEW_PROCESS_GROUP; otherwise it
               fails silently and the caller's grace elapses into ``hard_kill``.
        """

    def hard_kill(self) -> None:
        """End the tree unconditionally. Never raises.
        POSIX: killpg(pgid, SIGKILL) when contained, else os.kill(pid, SIGKILL).
        win32: taskkill.exe /T /F /PID (best effort, root still alive so /T can walk) then
               TerminateJobObject(job, 1) when contained. Without a job: taskkill only.
        """

    def close(self) -> None:
        """Release. Idempotent. POSIX: nothing. win32: CloseHandle(job) — KILL_ON_JOB_CLOSE ends
        remaining members only when attached with kill_on_close=True."""

def kill_process_tree(pid: int, *, platform: str | None = None) -> None:
    """The pid-only hard kill (#105's API; bash.py / _subprocess.py).
    POSIX: killpg(getpgid(pid), SIGKILL); on ProcessLookupError (Darwin zombie leader — measured)
           killpg(pid, SIGKILL), since every caller spawned pid with start_new_session=True.
    win32: taskkill.exe /T /F /PID via the same resolver. No job — there is no handle to have.
    """
```

`pid <= 0` → `ValueError` from `attach`, `kill_process_tree`, and every method
(win32/F9: a group id of 0 is a console-wide broadcast).

### B.1 Why `os.kill`, never `proc.terminate()` / `proc.kill()`

`Popen.send_signal` (POSIX) begins with `self.poll()` — a `waitpid(WNOHANG)`
that can reap a just-exited child out from under asyncio's watcher, which then
reports 255 (`reaper._signal_child`, measured `{255: 60}`). The sites signal
through the tree by pid/pgid instead, with `returncode is None` read
immediately before every **soft** kill and no `await` between.

### B.2 PID / PGID recycling — the accepted hazard, per site

- `attach()` captures the pgid once, right after spawn. On Darwin `getpgid`
  raises for a zombie leader whose group is alive (measured), so
  `ProcessLookupError` at attach means `pgid = pid` — the group the spawn
  kwargs asked for.
- `soft_kill` is always guarded by the caller's `returncode is None`.
- `hard_kill` on the escalation path is **not** guarded by root liveness: the
  leader-dead / descendants-alive shape is the one it exists for. The bound on
  a stale number, per site: rpc — `_await_exit` timed out, so the last 50 ms
  poll saw `returncode is None`; hooks — at most the 1.0 s soft grace; `!command`
  — synchronous `Popen`, nothing has waited, the zombie pins the number. A
  non-empty group cannot have its id reused (Linux `attach_pid(PIDTYPE_PGID)`
  holds a reference; BSD likewise); an empty one has nothing to kill, and the
  residual case — number recycled *and* the new holder made itself a leader,
  inside that bound — is accepted and stated in the ADR.
- `close()` never signals on POSIX, so the seconds-wide window at the rpc
  caller (`_shutdown`: reap → `drain(2.0)` → `stop()`) carries no kill.
- win32 with a job has no pid hazard: the handle names the job.
- The pid-only `kill_process_tree` is called from `bash.py:300-330` and
  `_subprocess.py` while the child is unreaped (`wait(timeout)` raised, or the
  abort watcher fired). Its Darwin fallback `killpg(pid)` therefore targets the
  zombie's still-pinned number.

### B.3 The win32 seam (`_Win32Api`) and the kernel32 implementation

Every win32 side effect goes through one Protocol so dispatch is testable from
a POSIX box **without emitting a real signal** (win32/F14):

```python
class _Win32Api(Protocol):
    def create_job(self, *, kill_on_close: bool) -> int: ...   # CreateJobObjectW(NULL, NULL) + SetInformationJobObject; raises OSError
    def assign(self, job: int, pid: int, handle: int | None) -> None: ...  # AssignProcessToJobObject(job, handle or OpenProcess(SET_QUOTA|TERMINATE, pid)); raises OSError
    def terminate_job(self, job: int) -> None: ...            # TerminateJobObject(job, 1); raises OSError
    def close_handle(self, job: int) -> None: ...
    def ctrl_break(self, pid: int) -> None: ...               # os.kill(pid, CTRL_BREAK_EVENT); raises OSError
    def taskkill(self, pid: int) -> None: ...                 # subprocess.run([<resolved taskkill>, "/T", "/F", "/PID", str(pid)], capture_output=True, check=False); FileNotFoundError on the resolved path retries the bare name
```

`_KernelApi` implements it and is constructible **only** when
`sys.platform == "win32"` (else `RuntimeError("inject an api")`). Signatures
follow `tests/process_probe.py::_load_kernel32` — `restype`/`argtypes` set for
every function (a `HANDLE` is pointer-sized; the default `c_int` restype
truncates on Win64). The pyright idiom is `prompt_file.py:206-229`'s
(`WinDLL` / `get_last_error` carry `# pyright: ignore[reportAttributeAccessIssue]`).
`import ctypes` at module top; `ctypes.WinDLL` reached lazily. Structs are
module-level `ctypes.Structure`s with `SIZE_T = ULONG_PTR = ctypes.c_size_t`:

```
JobObjectExtendedLimitInformation = 9 ; JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE = 0x2000
PROCESS_SET_QUOTA = 0x0100 ; PROCESS_TERMINATE = 0x0001
JOBOBJECT_BASIC_LIMIT_INFORMATION { LARGE_INTEGER PerProcessUserTimeLimit; LARGE_INTEGER PerJobUserTimeLimit;
  DWORD LimitFlags; SIZE_T MinimumWorkingSetSize; SIZE_T MaximumWorkingSetSize; DWORD ActiveProcessLimit;
  ULONG_PTR Affinity; DWORD PriorityClass; DWORD SchedulingClass }            # 64 bytes, LimitFlags at 16
IO_COUNTERS { ULONGLONG x6 }                                                   # 48
JOBOBJECT_EXTENDED_LIMIT_INFORMATION { Basic; IoInfo; SIZE_T ProcessMemoryLimit; SIZE_T JobMemoryLimit;
  SIZE_T PeakProcessMemoryUsed; SIZE_T PeakJobMemoryUsed }                     # 144 on x64 (verified with ctypes on LP64)
```

These match the MCP SDK's `mcp/os/win32/utilities.py` (`win32job`), which is
the same design; ours is ctypes because `pywin32` arrives only with `mcp`, a
dependency `aelix-ai` must not take (AGENTS.md §1).

`CreateJobObjectW(NULL, NULL)` yields a **non-inheritable** handle, and the
stdlib inherits only handles in its explicit `handle_list`, so `close()` is the
last handle. `weakref.finalize(self, api.close_handle, job)` releases an
abandoned tree. The `handle` argument: sites pass the stdlib's retained process
handle (`Popen._handle`; asyncio `proc._transport.get_extra_info("subprocess")._handle`,
both `int`-able) so `assign` never re-derives one from a pid; `OpenProcess` is
only the fallback when `handle is None`.

`attach()` on win32: `job = api.create_job(kill_on_close=…)`; `api.assign(job,
pid, handle)`; on `OSError` from either, close what was created and set
`contained=False` — `hard_kill` then takes the taskkill-only path. Nested jobs
are supported since Windows 8; a refusal on the runner is the measurement.

### B.4 The assignment window

Between `CreateProcess` and `AssignProcessToJobObject` the child runs. On the
asyncio spawn the window spans the transport's pipe-connection round trips —
measured on POSIX 0.3 ms idle, 1.05 ms median / 1.65 ms max under load; a shell
reaches its first `fork` at ~2 ms. Unmeasured on the proactor loop.
`CREATE_SUSPENDED` cannot close it (`Popen` closes the thread handle before
returning). Belt-and-braces: win32 `hard_kill` runs `taskkill /T /F` **before**
`TerminateJobObject`, while the root is alive, so `/T` walks to a descendant
that escaped the window through its live parent link. Stated in the ADR.

### B.5 `taskkill` resolution

`os.path.join(os.environ.get("SystemRoot") or r"C:\Windows", "System32", "taskkill.exe")`;
on `FileNotFoundError` retry `"taskkill"`; every `OSError` suppressed. Pi
`7af2d27d` does the same resolution.
