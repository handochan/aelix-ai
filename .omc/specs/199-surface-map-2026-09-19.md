# #199 surface map: child sessions, tool use, token usage, cost

This map is read-only research. It is not a design. The Aelix baseline is `main` `e1fef5f`, read from `/Users/handochan/dev/aelix-ai`. `/tmp/wt-294` was not opened. The Pi baseline is `~/dev/pi` `origin/main` `36b60d2`, read with `git show` and `git grep` only.

Paths are relative to `packages/aelix-coding-agent/src/` unless marked otherwise. `core/` means `packages/aelix-agent-core/src/aelix_agent_core/`, and `ai/` means `packages/aelix-ai/src/aelix_ai/`. Nothing was run against a live model. Anything not checked in code is marked **UNVERIFIED**.

## 1. Spawn path

### 1.1 Who reaches the channel

There are two doors, and both end in `aelix_agents/runtime.py` `_SubagentRuntimeImpl._run`:
- The model-driven door is `aelix_agents/extension.py` `AgentsExtension._execute`. In single mode it calls `runtime.spawn_granted(...)` and then `render_subagent_result(result)`. In parallel or chain mode it calls `batch.run_batch(...)` and then `aggregate.render_batch_result(...)`. The approved call comes from `self._pending.pop(ctx.tool_call_id)`, a `PendingSpawn` filed by the `tool_call` hook `_on_tool_call`.
- The user-typed door is `/agents run`. `aelix_coding_agent/tui/commands.py` `_agents_handler` calls `runtime.spawn(resolved, task)`, and that method takes consent itself.

`_run` then does the following:
- It checks admission inside an await-free block. The checks are the drain gate, `_admit_live` (`MAX_LIVE_CHILDREN=4`) and the per-prompt budget (`MAX_DELEGATIONS_PER_PROMPT=12`, model door only).
- It mints `spawn_id = _new_id()`, which returns `f"sub-{uuid.uuid4().hex[:12]}"`.
- It inserts a `RunningChild` into `self._children`, builds a frozen `SpawnPlan` and calls `await channel.run(plan, child=child, on_stream=_emit)`.
- In its `finally` it pops the row and publishes one terminal `SubagentProgress`.

The channel is always a `PrintChannel`. `__post_init__` builds `PrintChannel(model_registry=host.model_registry, parent_model=host.model)` when `channel is None`. `AgentsExtension.channel` defaults to `None`, and the `cli/entry.py` call site passes no channel (§8).

### 1.2 Print channel (production): `aelix_agents/print_channel.py`

**argv** comes from `build_child_argv`:
```
[sys.executable, "-m", "aelix_coding_agent", *profile_to_argv(child_profile, prompt_path=..., oneshot=True, task=..., parent_model=...),
 "--permission-mode", mode, *child_trust_argv(child_cwd, parent_cwd), "--no-agents"]
```
- **`--no-session` comes from product-core.** `aelix_coding_agent/agents/resolver.py` `profile_to_argv` sets `prefix = ["--mode", "json", "-p", "--no-session"] if oneshot else ["--mode", "rpc"]` and appends `f"Task: {task}"` in oneshot mode only. The same function renders the `/agents show` dry run. Its docstring says the dry run exists "so the rendered command is the same command P2 will run".
- Profile flags come from `profile_to_flags`. The model is the profile's `--model/--provider`, or the parent's live model when the profile names neither (`child_model_flags` → `parent_model_flags`).
- Tools go through `narrow_tools`, which computes the requested set ∩ the parent's live grant ∩ `ALL_TOOL_NAMES`, minus `{"agent"}`.
- `-nc` is clamped by `narrow_context_files`. The flags then cover skills, extensions and thinking, plus `--append-system-prompt-file` or `--system-prompt-file` pointing at a temp file. `prompt_file.write_prompt_file` creates that file with mode 0600 inside a 0700 directory, and it is removed on every exit path.
- `child_trust_argv` returns either `[]` or `["--no-approve"]` (`aelix_agents/trust.py`).
- **Nothing forwards `--session-dir`, `--session`, or the parent's session id or path.**

**cwd** is `plan.cwd = resolve_child_cwd(cwd, host.cwd())`. That is the resolved parent cwd, or a model-chosen subdirectory contained inside it. Paths outside the parent, paths with control characters and non-directories are refused.

**env** comes from `build_child_env`, which is `dict(os.environ)` with four edits:
- `AELIX_SUBAGENT_DEPTH` is set.
- `AELIX_STDIN_TIMEOUT` is set to `"1"`.
- `AELIX_MCP_CONFIG` is popped.
- `PYTHONPATH` gets the source root prepended.

Everything else is inherited on purpose, which means an `AELIX_CODING_AGENT_SESSION_DIR` set on the parent reaches the child (`cli/config.py` `ENV_SESSION_DIR`).

**stdio and protocol** (`PrintChannel.run` → `_stream_and_reap`):
- stdin is `DEVNULL`.
- stdout is a pipe opened with `limit=STREAM_LIMIT_BYTES` (8 MiB). It is read in 64 KiB chunks, reassembled by `stream.LineAssembler` (4 MiB per-line budget; oversized lines are dropped and counted), and folded by `reduce_line` into `_StreamState`.
- stderr goes to `StderrRing`, which keeps 64 KiB.
- The child writes `--mode json`. When `session is not None`, `modes/print_mode.py` `run_print_mode` first emits a best-effort, typeless header, `json.dumps(_metadata_to_dict(await session.get_metadata()))`. After that it writes one `dataclasses.asdict` event per line.
- The reducer consumes `agent_start`, `turn_start`, `message_end`, `tool_execution_start`/`_end` and `agent_end`. `message_end` is the sole source of the summary and the usage. The header has no `type` key and is ignored (`reduce_event`).

**Process ownership**:
- The spawn is `asyncio.create_subprocess_exec(..., **containment_spawn_kwargs(new_session=True), preexec_fn=pdeathsig_preexec())`. On POSIX that gives the child its own session; on Windows it gives `CREATE_NEW_PROCESS_GROUP`.
- `ProcessTree.attach(pid, kill_on_close=True)` runs, and the row is marked `row.tree_owned = True`.
- The reaper is detached and awaited under `asyncio.shield`, and `stop_all` joins it.
- `AgentsExtension._on_session_shutdown` stops children on `/new`, `/fork`, `/resume` and exit, so a child never outlives the parent session it was spawned from.

### 1.3 RPC channel: `aelix_agents/rpc_channel.py`

`build_rpc_child_argv` builds:
```
[sys.executable, "-m", "aelix_coding_agent", *profile_to_argv(..., oneshot=False),   # "--mode","rpc" + flags; task DROPPED
 "--no-session", "--permission-mode", mode, *trust, "--no-agents"]
```
The code comment reads: "Without it every delegated child writes a session file the user never started and then finds in their /resume picker". ADR-0201 recorded this as measured: without the flag the child writes `~/.aelix/sessions/…jsonl` "even with `AELIX_CODING_AGENT_DIR` pointed elsewhere".

- **env** comes from `build_rpc_child_env`, which is `build_child_env` minus `AELIX_STDIN_TIMEOUT`.
- **Protocol:** `aelix_coding_agent/rpc/rpc_client.py` `RpcClient` spawns the child. stdin is the JSONL command channel.
  - `_listener` is subscribed through `client.on_event` before `start()`.
  - The task is delivered as a `prompt` command via `prompt_and_wait(plan.task, collect=False)`.
  - The accumulator stops at the terminator (`if not state.saw_agent_end`).
  - `_shutdown` runs `close_stdin()`, waits up to 5 s (`STDIN_EOF_EXIT_SECONDS`), reaps, drains for 2 s and calls `client.stop()`.
- **Ownership:** `RpcClient` owns the process and its tree. The row only borrows them (`row.tree_owned = False`).
- There is no stdout header in RPC. The child's session file and id are available over the wire through `get_state` (`rpc/rpc_mode.py`: `session_file=harness.session_file`, `session_id=state.session_id`).

## 2. What comes back and how the parent aggregates it

**`SubagentUsage`** (`aelix_coding_agent/subagent_contract.py`) has the fields `input`, `output`, `cache_read`, `cache_write`, `cost`, `tokens` and `turns`. They are filled from `_StreamState` by `stream._reduce_message_end`, once per assistant `message_end`:
- **Cumulative sums:** `input`, `output`, `cache_read` and `cache_write`. Reads accept both spellings, and non-finite values are skipped.
- **`cost`:** the sum of `usage.cost.total` (or a flat `cost`). If that sum is 0, `print_channel.apply_cost_fallback` prices the summed tokens once, at envelope time. It uses the **last** `provider`/`model` and **the ModelRegistry** (`registry.find`, which includes models.json). It is best-effort and never fails a run.
- **`turns`:** the count of assistant `message_end` events, including errored auto-retry attempts.
- **`tokens`:** "Context LEVEL, not a sum — last message wins". It is the last non-zero `total_tokens`.

**`envelope.build_result`** produces a `SubagentResult` with these fields: `id`, `profile`, `ok`, `status` (`ok`, `error`, `timeout`, `aborted` or `declined`), `summary`, `truncated`, `usage`, `error`, `exit_code`, `stop_reason`, `elapsed_ms`, `dropped_tools`, `details`, `dropped_lines`, `tool_trail`, `permission_mode`, `model` and `provider`. `id` is the spawn id.
- `summary` goes through the `_select_summary` fallback chain: `error_message` (when not ok) → the sanitized stderr tail (when not ok) → `state.summary` → stderr → `"(no output)"`. `cap_summary` then caps it at `output_cap` UTF-8 bytes and appends the marker `"[Output truncated: … Full output preserved in tool details.]"`.
- `details` is **uncapped**: the full `state.summary`, plus the raw stderr tail on failure (`_build_details`).
- `tool_trail` is at most 4096 bytes (`render_tool_trail`), one sanitized line per call ending in `ok`, `FAILED` or `(no result)`.

**Single mode**, `aelix_agents/tool.py` `render_subagent_result`, returns:
```
ToolResult(content=[TextContent(text="\n\n".join([body, *notes, _usage_line(result)]))], details=result.details, is_error=not result.ok)
```
- The notes are `Error: …` (when the error is not already in the body), the dropped tools and the dropped-line count.
- `_usage_line` renders `[agent <profile> · <model> · <status> · <posture> · N turns · X in / Y out · $C · E s]` within a 76-cell budget. When space runs out it **drops turns, then tokens, then cost, then elapsed** (`_USAGE_DROP_ORDER`). Cost is not guaranteed to appear even in the text.
- The spawn id, tool_trail, exit code, stop reason, cache tokens and the `tokens` level are never in the content.

**Batch mode**, `aggregate.render_batch_result`, returns:
- **content:** a header, then one `[k/N status] summary` block per member (in submitted order) with notes and a per-member `_usage_line`, then the not-run line, then `[total] … X in / Y out · $C · W s wall`.
- **details:** `_join_details`, which joins `--- [k/N] <profile> ---\n<details>` sections.
- **is_error:** true if any member failed or `not_run > 0`.

**`aggregate.roll_up_usage`** sums `input`, `output`, `cache_read`, `cache_write`, `cost` and `turns`, and takes `tokens = max(...)`. Its only caller is `render_batch_result`, which feeds the `[total]` text line. `panel.py` states the same rule for the live aggregate. Single mode never rolls up, and no data consumer of the rollup exists anywhere.

**`output_cap`** defaults to 51,200 bytes (`agents/profile.py` `AgentProfile.output_cap: int = 51200`; `envelope.DEFAULT_OUTPUT_CAP = 51200`).
- It is applied per child in `build_result`. Both channels pass `plan.output_cap if not None else profile.output_cap`. `_run` never sets `SpawnPlan.output_cap`, so the profile value always applies.
- There is **no cap per call**: an 8-task parallel batch can put roughly 8 × 51,200 bytes of summaries into one toolResult.
- In chain mode, step k's summary (including the marker) plus its tool trail are placed into step k+1's task. The total is bounded by `chain.MAX_TASK_BYTES = 65536`, and the trail is dropped first.

**`/agents run` door**: `tui/commands.py` `_render_subagent_result` commits a Rich `Panel` (status, model, permission, turns, tokens, cost, elapsed, and a "Full output: N bytes" note) **to scrollback only**.

## 3. What the parent session persists today

This is the trace for one `agent` call:
1. The model's `AssistantMessage` carries a `ToolCallContent` with id `tool_call_id`, name `agent`, and args `{profile, task|tasks, mode, cwd, timeout_ms}`. It is persisted at its own `message_end`, before the tool runs. The path is `core/harness/core.py` `emit` → `await self._session.append_message(final_message)`. **The task text is therefore on disk.**
2. The `agent` tool declares `execution_mode="sequential"` (`tool.create_agent_tool`), which makes the whole batch sequential. `core/loop.py` `_execute_tool_calls_sequential` then does, for each tool:
   - `msg = _to_tool_result_message(tc.tool_call_id, result)`
   - emit `ToolExecutionEndEvent(result=result)`; this event carries `details` to listeners
   - `_emit_tool_result_message` → `message_end` → persisted **immediately after this tool finishes**.
3. `core/loop.py` `_to_tool_result_message` is `ToolResultMessage(tool_call_id=…, content=list(result.content), is_error=…, timestamp=time.time())`. **`details` is dropped and `tool_name` stays `""`.** `ai/messages.py` `ToolResultMessage` has only `tool_call_id`, `content`, `is_error`, `timestamp`, `tool_name` and `role`, with no `details` and no `usage`. `core/session/entries.py` `_message_to_dict` uses `asdict`, so the line on disk carries exactly those keys.

What is on disk after a call:
- the capped summary or summaries
- the notes and the usage footer, **as text only** (fields may have been dropped by the budget)
- `is_error`

What is not on disk:
- `details`
- the spawn id
- usage as data (cache tokens, context level)
- tool_trail, exit_code, stop_reason and stderr
- the child's transcript
- anything from `/agents run`

**Where `details` lives in memory:**
- the `ToolResult` returned by `_execute`
- `ToolExecutionEndEvent.result`, which reaches the TUI live renderer, the parent's own `--mode json` stdout (via `_dataclass_to_dict`) and RPC event consumers
- `tool_result` / `after_tool_call` hook patches (`core/loop.py` `_apply_after_override`), which can replace it but still never persist it

**Why it is not persisted (#168):**
- `ToolResultMessage` has no field for it.
- `details: Any` cannot cross as JSON as-is; `edit`'s details are a dataclass.
- Under ADR-0242 §A.1.3 (#294 design), a new optional key on a `message` entry is dropped by every released fork.

**Is there a stable per-child run id?**
- **The parent's `tool_call_id`.** It is persisted twice: in the toolCall block and on the toolResult. There is one per `agent` call, not one per child. It is **not guaranteed unique within a session file**. The Google adapter falls back to `f"{fn_name}_{_tool_call_counter}"` with a process-global counter that resets on restart (`ai/providers/_google_shared.py`).
- **Batch index or chain step.** It is bound at member creation (`batch._member(batch, index, …)`) and passed to `_on_event(index, progress)`. It is persisted only as the text `[k/N …]` in batch content.
- **Spawn id `sub-<12hex>`.** It is minted in `_run` after admission (members 5–8 of a batch get theirs in wave 2). Refusal and decline envelopes also mint a fresh `_new_id()`. It is carried on `SubagentResult.id` and `SubagentProgress.id` and is **never persisted or rendered**.
- **The child's own session id.** None exists today: a `--no-session` child has a `MemorySessionStorage` uuid that nobody reads.
- **`/agents run` door.** It has only the ephemeral disclosure key `f"run:{_new_id()}"`.

## 4. Session stats (`/cost`, `/stats`, footer, RPC `get_session_stats`)

**How the numbers are computed:**
- `core/harness/core.py` `AgentHarness.get_session_stats` passes `messages = list(self._state.messages)` to `core/harness/_session_stats.py` `aggregate_session_stats`.
- For each `AssistantMessage` it adds `usage.input`, `output`, `cache_read` and `cache_write`. Cost comes from `_message_cost`: a provider-resolved cost if one exists, otherwise a re-price from the message's own `provider`/`model` via **`ai/models.py` `get_model`**. That is the static generated catalog (`_PROVIDER_MODELS`) and does **not** include models.json models. An unpriceable message makes `cost_known=False`.
- `tokens.total` is `input + output + cache_read + cache_write`, a **flow**. That is a different meaning from `SubagentUsage.tokens`, which is a level.
- A `ToolResultMessage` only increments `tool_results`.
- `_cost_is_complete` reads `self._session.get_branch()`. After a compaction it returns False, and the display then shows the cost as a lower bound.

**What the numbers do not include:** `_state.messages` is the current branch's in-memory message list. `CustomEntry` records are **not messages**. `core/session/context.py` `build_session_context` and `build_display_messages` skip `custom` entries, so no entry-based record is seen by stats today. Child usage exists only as text in toolResult content, which stats never parses.

**Consumers:**
- `tui/commands.py` `_cost_handler`
- `tui/stats_dashboard.py` `build_session_tab` (via `format_session_cost`)
- the footer, via `tui/shell.py` `_refresh_context_usage` → `context.set_usage_stats(input, output, cost)`
- RPC `rpc/rpc_mode.py` `_session_stats_to_dict`, the Pi wire shape with explicitly enumerated keys
- the TUI-only cross-session History store `tui/stats_history.py` (`get_agent_dir()/stats-history.jsonl`), written by `shell.py`

Headless children never write History.

**Plug-in points that keep delegation vocabulary out of the kernel.** The kernel gate is `tests/agents/test_p2_band_boundaries.py` `test_kernel_has_no_subagent_surface`. Any behaviour change in a kernel file also needs an ADR line in `_KERNEL_CHANGE_ALLOWLIST` (`test_kernel_untouched_vs_merge_base`). `harness/_session_stats.py`, `harness/core.py`, `loop.py`, `session/entries.py` and `session/jsonl_*` are already listed.
- (a) **Pi-parity tool-reported usage.** Add `usage` to `ai/tools.py` `ToolResult`, copy it in `_to_tool_result_message`, add it to `ToolResultMessage`, and sum it in `aggregate_session_stats`. The kernel then learns "tool usage", not "delegation". The drawback is ADR-0242 §A.1.3: released forks drop the new key. Also, `ai/` is outside the band gate; whether any gate freezes `ai/messages.py` is **UNVERIFIED**.
- (b) **A neutral usage-ledger `CustomEntry`** (e.g. an `aelix.`-prefixed type named for usage, not for delegation) that the stats code sums. It survives forks (§A.1.3 table), but `get_session_stats` would have to read entries rather than `_state.messages`.
- (c) **Coding-agent-side addition in every consumer.** The TUI, RPC and footer would each add the rollup. The kernel stays untouched, but there are at least four sites to keep consistent.
- (d) **A generic hook** that lets an extension contribute to the stats.

**Ways double counting (or over- and under-counting) can happen:** see Hazards 8–11.

## 5. Failure, timeout, cancel, retry: what the parent records today

| Case | Code path | Envelope | Persisted in the parent |
| --- | --- | --- | --- |
| Spawn fails (exec, OSError) | `PrintChannel.run` `except Exception` | `status=error`, `error=str(exc)`, zero usage | toolResult text, `is_error` |
| Early child exit (no model or key, unknown tool) | child returns 1 before `run_print_mode` (`cli/entry.py`: no model at `format_no_model_selected_message`, no key at `format_no_api_key_found_message`) | stderr tail is the summary | text only. **No stdout bytes at all**, not even the header |
| Model error, exit 0 | `build_result` tightens on `stop_reason in ("error","aborted")` | `error` | text |
| Child dies mid-turn | `no_terminator` (guarded by `dropped_lines == 0`) | `error` + `STREAM_ENDED_EARLY` | text |
| Timeout | `_stream_and_reap`: `timed_out` → `_reap` (SIGTERM, grace, SIGKILL) → drain ≤ `POST_EXIT_DRAIN_SECONDS`=2 s → `outcome="timeout"` | partial summary (last **complete** text-bearing `message_end`) + usage of completed messages only | text |
| `stop` / `stop_all` | `row.stopped` → `outcome="aborted"` | partial summary | text |
| **Cancel (Ctrl+C = `turn_task.cancel()`)** | channel `_eager_abort` + `raise`; `batch._run_parallel` `gather` propagates; **no envelope is built** | none. Only `child.stream` (memory) holds partial usage when `_run`'s `finally` publishes the terminal snapshot; `apply_cost_fallback` never runs | **Nothing.** `harness/core.py` abort path: "keeps abort off the session write path". An aborted `AssistantMessage` is added in memory only; the persisted toolCall is left without a toolResult. Completed parallel siblings' envelopes are lost too |
| Declined consent | `envelope.declined_result` | `declined`, zero usage | text (model door) / Panel only (`/agents run`) |
| Did not start (live cap, budget, batch deadline, `TaskTooLarge`) | `runtime._error_result` / `batch._refusal_envelope` + `MemberOutcome.never_started` | `status="error"`, a fresh `_new_id()` | text `[k/N did not start]` |
| Chain stops at the first failure | `_run_chain` `break`; `not_run` count | none for the unrun steps | text "NOT RUN" line |
| Retry | none at the delegation level (no retry code in `aelix_agents/`); a model re-issue is a new `tool_call_id`. Inside the child, harness auto-retry is on by default: failed attempts count in `turns`, and their usage is `null` when the counters are zero (`stream._reduce_message_end`) | n/a | n/a |

`details` is never persisted in any of these cases. `message_update` deltas are ignored by design, so a timed-out, still-streaming assistant turn contributes neither text nor usage. The child's auto-compaction LLM calls produce no `message_end` and are never counted. **UNVERIFIED:** whether any provider bills an errored attempt with non-zero usage.

## 6. Session placement if `--no-session` were simply removed

**Where the file would land.** `cli/entry.py` sets `sessions_root = parsed.session_dir or get_session_dir()`. `get_session_dir` reads the `AELIX_CODING_AGENT_SESSION_DIR` env var, and when neither is set the repo default is `"~/.aelix/sessions"` (`core/session/jsonl_repo.py` `JsonlSessionRepo.__init__`). The child then calls `repo.create(JsonlSessionCreateOptions(cwd=str(Path.cwd())))` and writes `<root>/<_encode_cwd(child_cwd)>/<ts>_<uuid4>.jsonl`. `JsonlSessionStorage.create` writes the header at once (0600 file, 0700 dir).
- The child's `--session-dir` is **not forwarded** (§1.2), so a parent run with `--session-dir X` would get children in `~/.aelix/sessions`. The owner's 2026-09-19 live check used exactly `--session-dir <scratch>`.
- The env-var form **is** inherited, so the two ways of choosing a root behave differently.
- When the child's cwd is the parent's cwd (the default), it lands in the **same bucket as the parent**. A model-chosen subdirectory cwd lands in that subdirectory's bucket instead.

**Would `aelix --continue` pick the child?** `cli/entry.py` runs `repo.find_most_recent(cwd)`. That function filters `*.jsonl` directly in the bucket (directories are skipped) through `_is_valid_session_file` (`type == "session"` plus a non-empty id), sorts by **mtime DESC**, and takes the first. A child file passes that filter. Timeline:
1. The parent appends the toolCall assistant message.
2. The child's file is created and appended throughout the run.
3. The parent appends the toolResult right after the tool returns (sequential path), which makes the parent newest again.

So `--continue` resumes the **child**:
- during any running delegation, for example from a second terminal
- after a **Ctrl+C-cancelled** delegation until the parent writes again, because the abort path persists nothing (§5)
- after a parent crash or kill mid-delegation
- **permanently**, in the subdirectory's bucket, for subdirectory-cwd children

Early-exit children (§5 row 2) leave **header-only valid files**, and the parent cannot learn their path because they wrote no stdout.

**Would `/resume` mix child sessions in?** Yes.
- `tui/shell.py` `/resume` runs `repo.list(JsonlSessionListOptions(cwd=cwd))` and then `by_recent_activity`, which uses `cli/session_labels.py` `session_activity_epoch` (last activity, then `created_at`, then mtime). The only exclusion is the current file.
- The startup `--resume` picker (`cli/entry.py` `_resume_session_startup` → `repo.list(...)` → `_prompt_resume_choice`) does the same.
- Rows are labelled by the first user message: `Task: …` for print children, the raw task for RPC children. That is up to 12 per prompt.
- Resolving an id prefix (`_resolve_session_metadata`: the cwd first, then a global `repo.list()` over every top-level dir under the root) can match a child.

**What hides a file.** `list` and `find_most_recent` only look at `*.jsonl` directly inside `<root>/<bucket>/` and skip subdirectories. `_list_session_dirs` returns only top-level directories. Because the child writes `<its root>/<encoded cwd>/…`, a child file ends up **invisible to every picker** as long as its root is not a plain `<root>` that a user would use. Two examples:
- a directory nested inside a bucket, such as the 2026-09-15 sketch `--session-dir <parent bucket>/children/…`
- a root outside the user's sessions root

**UNVERIFIED:** `tests/agents_ext/test_reduce_consumes_real_print_mode_output.py` asserts that no header is written under `--no-session`, but code reading shows a `MemorySessionStorage` session is attached, so `{id, created_at}` would be written. This was not checked against a real child.

## 7. `/fork`, `/resume`, `import_from_jsonl` and deletion versus a parent→child link

- **`/fork` and `/clone`** (`tui/commands.py` → `core/runtime/agent_session_runtime.py` `AgentSessionRuntime.fork`) call `repo.fork(source, ForkOptions(cwd, entry_id, position="at", parent_session_path=metadata.path))`.
  - `repo_utils.get_entries_to_fork` returns the path to the root, so only entries on the branch are copied. They are decoded and then re-encoded with `entry_to_json`.
  - A `CustomEntry.data` link survives **verbatim**. Unknown keys on header, entry, message or content block are **dropped** by released forks (#294 design §A.1.3 table).
  - The fork then **shares** the child file (child files are not copied), so two parent sessions point at one child. A link stored as a relative path resolves only while the fork stays in the same bucket, which it does because `fork` uses `metadata.cwd`.
  - A fork taken before the link entry does not carry it.
  - `/tree` moves (`set_leaf_id`) leave the link in the file but off the current path.
- **`/resume`** (`switch_session`) and `--session` open the parent file.
  - `build_session_context` skips `custom` entries, so the link never enters the model context. A `CustomMessageEntry` **would**, because it is turned into a `UserMessage` by `create_custom_message`.
  - Replay (`tui/shell.py` `_display_messages` → `build_display_messages(branch)` → `EventRenderer.replay`) skips `custom` entries too, so the link is **invisible on replay** unless the TUI reads entries itself.
  - An absolute child path breaks if `~/.aelix` moves or the parent was opened from another root.
- **`import_from_jsonl(path)`** copies **only that one file** into `<root>/<encode(cwd)>/<basename>` (`copy_file`). Children are not brought along: a relative link dangles, and an absolute one points back at the source machine or directory.
- **Deletion:** `JsonlSessionRepo.delete` removes one file (`fs.remove(path, force=True)`). There are **no product callers** (grep over `packages/*/src`), so deletion is manual `rm`. There is no cascade, no garbage collection and no retention policy for any session today. Deleting a parent orphans its children. Deleting a child leaves a dangling link, and a forked sibling may still point at that child.
- **Two terminals, #137:** `append_entry` reparents onto the process-local `_current_leaf_id`. A second writer on the parent orphans a whole turn. Link records inherit the same exposure.
- **Within one process:** `Session.append_custom_entry` reads `parent_id=await self._storage.get_leaf_id()` **outside** the storage lock. With `LocalFileSystem.append_file`, which never yields, an append runs atomically. With a yielding `FileSystem` (like the #294 interleave test fixture), two concurrent appends become siblings and one falls off the path. `ExtensionAPI.append_entry` → `harness._action_append_entry` is fire-and-forget (`loop.create_task`), so its order relative to the toolResult append is not fixed. `ExtensionAPI.append_entry` raises `AgentHarnessError` when no session is attached. The awaitable alternative is `ctx.session_manager.get_session().append_custom_entry(...)`, obtained from a hook's `ExtensionContext`; `execute()` only receives `ToolExecutionContext`.

## 8. Both channels

**RPC is not used in production (#123).**
- `AgentsExtension.channel: SubagentChannel | None = None`, and `cli/entry.py` builds `AgentsExtension(posture=…, agent_dir=…, cwd=…, project_trusted=…)` without a channel.
- `_SubagentRuntimeImpl.__post_init__` therefore builds a `PrintChannel`.
- No `RpcChannel` references exist outside `rpc_channel.py`, apart from comments.
- #123 records that there is no production wiring, that the roughly 25 tests are scripted stubs, and that no real-model smoke has been run (W3). It also records `agent_end` with no correlation id: one child per task, reuse impossible.

**Differences that matter for recording:**

| --- | --- | --- |

## 9. TUI

**Live `agent` card.**
- `tui/render.py` `EventRenderer._render_tool_end("agent", result, is_error)` is the generic path. It shows the content text with a dim gutter, truncated to `tool_card_max_lines`, and the hidden lines are available through `/expand N`.
- The only `details` reads in the TUI are `edit` (`details.diff`) and `bash` (`_bash_exit_code`). **Nothing renders `details` for `agent`, live or on replay.** The envelope's "Full output preserved in tool details" marker therefore cannot be followed from the TUI.
- The descriptor path (`_render_with_descriptor`) needs a `tool_name`, and a persisted toolResult has `tool_name=""`.
- Live progress (the statusline row, the batch aggregate row and the widget panel from `aelix_agents/progress.py` and `panel.py`) is ephemeral and cleared in `_execute`'s `finally`.

**Replay** (`EventRenderer.replay`) receives `build_display_messages(branch)`. There is no `details` and no `tool_name`, and `custom` entries are skipped. The docstring already lists these gaps (#168).

**`/agents run`** commits a Panel with the note "Full output: N bytes (the summary above is capped)" but does not render the text.

**Where a link could be shown** (none exists today):
- (i) an `agent` branch in `_render_tool_end` that reads the live `result.details`
- (ii) replay reading the branch's `CustomEntry` records next to the toolResult with the matching `tool_call_id`, or reading `details` once #168 lands; it would also need `tool_name` restored
- (iii) an `/agents` subcommand that lists or opens child sessions read-only (for example by replaying the child file)
- (iv) a short id line in the `content`

Option (iv) costs parent-context tokens and cuts against owner condition 3, "결과만" (only the result goes to the parent).

## Hazards and open questions for the design

1. **A link placed only in `details` is not durable.** `_to_tool_result_message` drops `details` (#168), replay cannot see it, and `/agents run` has no `ToolResult` at all. The link needs its own persisted record: an `aelix.`-prefixed `CustomEntry` (ADR-0242), not a `CustomMessageEntry`, because that one enters model context. The design must decide whether #168 lands with #199.
2. **Removing `--no-session` alone puts children in the parent's bucket.** `find_most_recent` (mtime) then resumes a *child* after Ctrl+C, a crash or mid-delegation, and permanently for subdirectory-cwd children. `/resume` and the startup picker list up to 12 `Task: …` rows per prompt. The design must choose a root that pickers never scan.
3. **`--session-dir` is not forwarded** while `AELIX_CODING_AGENT_SESSION_DIR` is inherited. A scratch-dir or test parent sends its children to the user's real `~/.aelix/sessions`. A `--no-session` parent needs an explicit rule, probably that its children are not persisted either.
4. **Who picks the path.** If the child picks it, the parent learns it from the json header or `get_state`. Early-exit children then leave header-only files (written before `run_print_mode`) with no stdout to report them. If the parent pre-allocates, it can use `JsonlSessionRepo.create(id=…)` plus `--session <path>`, or pass a dedicated `--session-dir`. The existing flags allow both; a new flag would be a product-core change.
5. **The two argv sites disagree.** `resolver.profile_to_argv` is product-core and also feeds the `/agents show` dry run, whose contract is "same command". `build_rpc_child_argv` is in the extension. A child session flag must also keep the dry run truthful.
6. **Stable key.** `tool_call_id` is not unique on the Google adapter across restarts. The spawn id is minted late (after admission) and is not persisted. The batch index is only known in the executor. Records need a key, for example (parent session id, tool_call_id, index) or the spawn id written into both records. Readers fold "a start and a settle are two complete records … last-wins by a stable key" (#294 design §D).
7. **Cancel writes nothing.** No envelope is built, `apply_cost_fallback` never runs, siblings' finished envelopes are lost, and the parent keeps a toolCall with no result. Partial usage survives only in `child.stream` at `runtime._run`'s `finally` (inside a cancelled task). Recording cancelled or unknown spend, which §5 stage 2 requires, needs a write there or a start record before spawn.
8. **`tokens` means two things.** `SubagentUsage.tokens` is a context level (take the max), while `SessionStatsTokens.total` is a flow (in+out+cache). Adding one to the other inflates the total.
9. **Two price sources.** The envelope cost uses the registry fallback (models.json included, last model, priced once). `_session_stats._message_cost` uses the static `get_model` catalog. Re-pricing child tokens at stats time can disagree with the footer `$`, or turn `cost_known` False for custom models. The design must pick one authoritative number to record.
10. **Double counting.** It arises from:
    - start and settle records both carrying usage
    - at-least-once appends (ADR-0242: a raising append can still leave a complete line)
    - a per-member record plus a batch-total record
    - both the parent rollup and a walk over child session files
    - the #168 `details` and a `CustomEntry` both carrying usage
    - fork copies inflating cross-session sums (History tab per-project totals). Parent messages already have this last problem on fork.
11. **Undercounting that stays after #199.**
    - cancelled runs
    - null-usage failed attempts
    - child compaction calls
    - an in-flight turn at timeout
    - stats reading only the current branch's `_state.messages` (Pi reads every entry, every branch)
    - compaction making the parent cost a floor

    The design must decide whether child spend follows branch semantics or file semantics.
12. **Where the rollup lives.** It must not add "subagent" to the kernel. The options are (a) Pi-parity `ToolResult.usage`, dropped by released forks; (b) a neutral usage-ledger `CustomEntry`, which needs stats to read entries; (c) per-consumer code in the coding agent (TUI, footer, RPC, dashboard); (d) a hook. Every kernel edit needs an ADR allowlist line.
13. **Links across fork, import and delete.** A fork copies the link and shares the child file. Import copies only the parent. There is no delete path or retention policy. Absolute versus relative paths trade off moving the root against import.
14. **A resumed child session is not the child.** Resuming a child file with `--session` runs it as an ordinary session. The clamp (`--permission-mode`), tool narrowing, `--no-agents` and the depth env are argv/env state and are not in the file, and the system prompt file is deleted. The design must decide whether child files are view-only.
15. **`output_cap` default.** 51,200 bytes per child and no cap per call means about 400 KB of parent context for 8 parallel children. The owner asked to review the default together with #199.
16. **Honesty of the truncation marker.** "Full output preserved in tool details" is false after the call and on every TUI surface today. #199 or #168 either makes it true, as a persisted `details` or a link to the child file, or it has to change.
17. **Write mechanics.** `ExtensionAPI.append_entry` is fire-and-forget and raises with no session. Awaiting `Session.append_custom_entry` is safe with `LocalFileSystem` only because the append never yields. `parent_id` is read outside the lock. #137 (second writer) still applies to the parent file.
18. **RPC.** Recording must work on both channels (owner memo), but RPC has no production caller and no real-model smoke. Its discovery path is `get_state` rather than the header, and it has a separate `--no-session` site. The design must decide whether RPC parity is tested with stubs only.
