# #230 — the abort handle finishes at the reap, and an abort in that window ends the call instead of the tree (design, **revision 2**, 2026-09-07)

`run_contained` releases its `AbortHandle` only in the call's `finally`, so between the root's reap and
the end of the post-exit drain the handle is still armed. An `abort()` landing there sends
`tree.hard_kill()` — on POSIX a `killpg(SIGKILL)` at the group of an **already-reaped leader**, killing
the helper an rc-0 command backgrounded on purpose, after which the call returns `returncode == 0`
anyway. In production that abort is `ExtensionAPI.exec`'s `except asyncio.CancelledError`: an ordinary
Esc, ^C, or cancelled turn.

**What revision 2 changed.** 21 findings, 10 with a measured refuter pass (see
`230-critique-resolution-2026-09-06.md`, whose "do not re-raise" list is binding). Five substantive
moves: the timeout-leg disarm is **gated on the reap** (`_end_the_tree` can return with the root
alive); a **fourth case** was added because §B leaves the `finally`'s disarm with no coverage anywhere
in the repository; **C.3 was re-anchored** to the root's own exit and its stdout pin rewritten (the
drafted form has already cost this repo two windows legs); scope grew by a **docstring-only edit in
`api.py`**, the only reference documentation an author has for this; and the CHANGELOG grew a **second
edit**, because `[Unreleased]` already carries a sentence this falsifies.

control  chatty holder, no abort   rc=0 helper ALIVE  window 2.004 / 2.005 / 2.004 s   killpg []

BUG      silent, abort at +0.05 s  rc=0 helper DEAD   abort()->True  killpg [(<reaped root pid>, 9)]  3/3

The window is **exactly the post-exit drain**: `EXIT_DRAIN_SECONDS` (0.105 s) when the helper is
silent, `DRAIN_CAP_SECONDS` (2.004 s) when it keeps writing — long precisely when a pipe holder
outlives the root, which is the helper `kill_on_close=False` exists to keep. Same on Debian/3.12.14,
2/2. Two facts bound what the late abort does: `proc.kill()` is **inert** after the reap (CPython's

rung; and with the helper also gone `os.killpg` raises `ProcessLookupError` (3/3 darwin, 2/2 linux),
swallowed by `hard_kill`'s `suppress(OSError)`. The late abort is therefore either **silent** or
**exactly the harm this issue names**.

## A. Decision

### A.1 The owner's decision, and what it makes true

> **OWNER, 2026-09-06 (choice A):** an abort that lands AFTER the root has exited — in the post-exit
> drain window — must NOT kill the helper the command deliberately backgrounded.

That is already the module's stated contract (`run_contained`'s docstring: "on the SUCCESS path a
helper the command deliberately backgrounded, which `kill_on_close=False` and a releasing `close()`
are there to preserve") and the promise `ExtensionAPI.exec`'s docstring makes to extension authors —
measured false there too on `main`, which is why §D.8 exists. #230 makes the text true rather than
adding a new promise.

### A.2 What changes

1. **`abort._finish()` moves to the reap.** Success path: the instant `proc.wait(timeout=)` returns.
   Timeout path: the instant `_end_the_tree` returns **and only if the root was actually reaped**
   (§B.3). It stays in the `finally` too (idempotent); C.5 pins that.
2. **`_drain` learns clause (d): the caller aborted** — keyed on `.aborted`, never `._finished`, so it
   fires on every leg.

`abort()` in the window then returns **`False`** — the documented "there was nothing to send it to" —
sends nothing, and the call returns promptly with the real `returncode` and the bytes read so far.

### A.3 Why (2) and not (1) alone — measured

**A2, `_finish()` only:** correct but slow. Chatty holder, abort 0.5 s in: helper ALIVE, but the call
ran **1.4965 / 1.4983 / 1.5035 s** past the abort to the 2.0 s cap. The full shape returns
**0.0016–0.0076 s** after it (3/3 darwin, 2/2 linux). The caller pressed Esc; the worker has no reason
to hold a `to_thread` slot for another 1.5 s — `Runner.close` joins the default executor for 300 s and
`concurrent.futures.thread._python_exit` joins it again unbounded, the exact ceiling `AbortHandle`
exists for.

**What the caller then reports: nothing.** Measured through the REAL `ExtensionAPI.exec`
(`refute-PD-2/probe_exec_docstring.py`, swapping `api_mod.run_contained` — the seam that method's own
docstring declares): the awaiting caller sees `CancelledError` and **no `ExecResult` at all** — no rc,
no output, no `killed` flag — on `main` and on the fix alike, unblocked **0.0001 s** after
`task.cancel()`, 4/4 each. The only observable difference is the helper afterwards: `main` **DEAD
4/4**, fix **ALIVE 4/4**. Design question (2) has a flat answer: the payload the drain collects after
an abort has no reader, so ending the drain early costs nothing and buys the worker thread back.

**A4, kill anyway** — rejected by the owner, and incoherent: the call has already bound
`returncode = 0`, so it would report a success while killing what that success left behind (rc 0 +
helper dead, 6/6). **A5, guard `hard_kill` by root liveness** — rejected: `hard_kill`'s docstring
states the opposite invariant on purpose ("leader dead, descendants alive is the shape this exists
for") and the timeout ladder depends on it. A narrower variant, a `returncode` test in `abort()` itself,
is sound and still rejected — §A.5.

### A.4 The rule, stated uniformly — and its one cost

**An `abort()` ends the CALL as fast as it can; after the reap it ends nothing else.** Clause (d) fires
whenever `aborted` is true, including for an abort that *did* kill during the wait. That is a real
change on one shape: a holder OUTSIDE the tree (a `setsid` descendant, a job escapee), which the kill
does not reach and which therefore keeps the drain running:

```
main     rc=-9  stdout 86 / 87 B   drain ran 2.004 / 2.008 s past the abort
fix      rc=-9  stdout 12 / 13 B   returned  0.0007 / 0.0009 s past the abort
```

~74 bytes dropped, 2 s of worker life returned — to a caller that has unwound (A.3). For a holder
INSIDE the tree the kill EOFs the pipes and clause (a) already ended the drain
(`test_abort_ends_a_real_tree_promptly` stays green).

That is a rule about **`abort()`**. The interrupt leg (`except BaseException`) still ends the tree from
inside the same drain; §G names the single caller where that is reachable and why it is left alone.

### A.5 The residual armed window, and the larger one before it

Between `proc.wait()` returning and `abort._finish()` taking the lock the handle is still armed. The
width is a **load series**, and revision 1 quoted its middle as the figure (row 18): 0.125 µs idle,
1.48 µs in-situ, **0.055 ms median / 0.103 ms max with another thread running Python** — the production
shape, since `ExtensionAPI.exec`'s aborter *is* the asyncio loop thread. **Quote 0.055 ms, never
"microseconds".**

**What the residue exposes is the same bug, not a different hazard.** Revision 1 called it "the
PID-reuse hazard `ProcessTree.close` already states". Measured with the residue widened by a hook so an
abort lands in it deterministically (row 24): the group is **non-empty**, its sole member is this run's
own helper, `killpg` is delivered and the helper dies while the call returns rc 0 — 3/3 darwin, 2/2
linux. `ProcessTree.close`'s hazard is the **other** branch, the helper gone and the group empty, where
`killpg` answers ESRCH and nothing is killed (3/3, 2/2) and a stranger would need the pid space to wrap
inside the residue against a floor of **85.63 s** (row 26). On win32 reuse is impossible: the retained
handle names the process and the job handle the job, both held until the `finally`. So **narrowed
10³–10⁴×, not closed** — an aborter spin-triggered on the reap landed in it **17 of 20** runs on the §B
build and killed the helper 17/17 (row 25).

**Two closures measured; neither taken.** Holding the handle's lock across the wait blocks `abort()`
for the command's whole life. A `returncode is not None` test in `AbortHandle.abort()`, returning
`False` before the ladder, is **sound but worth ~2.5 µs** (row 23): `Popen._wait` publishes
`returncode` before returning on both arms (CPython 3.12.13 source), the suite stays green, and it
does suppress the reaped-arm kill without disarming the live-root one. What it costs is the
`_finish()` move's own cover: **with the guard in, mutant (a) — deleting the success-path
`abort._finish()` — passes every pin C.1 and C.3 carry, 3/3**, against helper DEAD 3/3 without it.
Two mechanisms for one fault, and the one the tests name stops being tested. Rejected for that, not
for unsoundness.

**The head of the window is BEFORE the reap, and nothing here closes it.** `returncode` is published by
the run thread itself, so everything between the root's real exit and that publication is armed however
early `_finish()` sits: **0.712 ms median** at `timeout=None` and **19.477 ms median (33.249 max)** with
a `timeout`, because `Popen._wait(timeout=)` busy-loops with a delay doubling to a 0.05 s cap (rows
21–22). End-to-end with §B applied, an abort 2 ms after an rc-0 root's exit under `timeout=10.0` still
killpg's the group and kills the helper **6/6**; at 20 ms, 2/6. `ExtensionAPI.exec` reaches that path
whenever the caller passes `timeout_ms`. **So this takes the window from 0.105–2.004 s down to ≲54 ms,
not to zero.** Closing the rest needs a reap the handle observes itself, or an `abort()` that tests tree
liveness; not taken, and recorded in §G as a decision rather than left to rediscovery.

### A.6 Race, unchanged (design question 4)

An `abort()` arriving **during `proc.wait`** or **during `_end_the_tree`** finds the handle armed and
fires the ladder — deliberately, unchanged. On win32 `_kill` holds the lock across a `taskkill` bounded
at 5 s, so the new `_finish()` can block behind it that long; not new in TOTAL (the `finally`'s
`_finish()` pays the same today) **but under §B.2's order the suspension is also charged to
`state.exited_at`, and so to `drain_until`**. Inert for a different reason than revision 1 gave:
whenever that contention exists `aborted` is already true, so clause (d) ends the drain before the
origin is read. Stated, not pinned (mutation row (h)).

One more arrival is unchanged, deliberately: an `abort()` in the **post-kill** drain when
`_end_the_tree` returned with the root still alive. That reap is bounded (`REAP_GRACE_SECONDS`) and can
expire — its own "a root that outlives `reap` is a live ORPHAN — not a zombie" — so the disarm is gated
on `proc.returncode is not None` and the handle stays armed there, as on `main`. Measured: **1 of 10**
arrivals at that line in the fakes file is unreaped
(`test_timeout_with_a_wedged_root_costs_reap_grace_not_forever`), **0 of 3** with real children.

### A.7 The two sites now agree — on the leg axis, which is the right one

#222 settled the same window at the bash tool by disarming the abort watcher **before** the drain
(pre-merge review F1, pinned by `test_an_abort_during_the_exit_path_drain_keeps_the_helper`; #234 kept
that order). Revision 1 explained the remainder as "same policy, different delivery" and put the axis
at the SITE. Wrong: the axis is the **leg**.

* **Abort-signal leg.** The bash tool's watcher is cancelled before `await _drain_to_the_end()`, so the
  signal is inert and the drain runs to EOF for a caller still listening that does get its
  `ExecExitResult`. `run_contained` has no such leg — its only handle-passing caller is
  `ExtensionAPI.exec`, whose abort *is* the task cancellation.
* **Task-cancellation leg.** Both sites kill nothing, and what happens to the drain depends only on
  where the `CancelledError` lands — measured (`rev2/pd4_probe.py`, plain asyncio, 3/3 each): delivered
  **while suspended inside** the drain's await it cuts it at **0.02 s**; delivered **before** the
  `finally` is entered it does not, and the drain runs to completion (0.5011 s) with the caller still
  getting its `CancelledError`. The repo pins that second arrival at the bash tool
  (`test_a_turn_cancel_in_the_watcher_teardown_keeps_the_helper_and_still_detaches`: "`TAIL` still
  arrived … the cancellation does not truncate the output"). §B gives `run_contained` the *first*
  behaviour for every arrival in the window, because its drain is a synchronous loop on a worker thread
  no `CancelledError` reaches — clause (d) is the substitute.

Same policy — kill nothing — with one asymmetry, stated by leg rather than by site.

**C.3 `test_an_abort_in_the_exit_drain_keeps_the_backgrounded_helper`** — `test_run_contained_real_processes.py`, **appended at the end** (§0). New source constant `ROOT_WITH_A_CHATTY_HOLDER`.
**Both ends of the window anchor to the ROOT**, because timing the abort off the announce lets the case
go vacuous on a slow runner: measured, the helper's first byte lands **+0.0050 / +0.0073 / +0.0089 s**
after the reap (n=15, darwin idle) — ~92 ms of margin inside `EXIT_DRAIN_SECONDS` — and an injected
0.095 s helper delay makes the unanchored shape pass on `main` 4/4 while pinning nothing.

1. The helper writes a `chatting` flag immediately AFTER its first pipe byte and the root waits on it
   before writing its line and exiting, so at the exit instant the drain is provably held open by an
   already-writing holder, independent of interpreter start-up. The root writes a `leaving` flag
   immediately before exiting. The flag idiom is `ROOT_WITH_A_LATE_TAIL`'s, whose docstring states why
   ("`os.getppid` does not change on Windows when the parent dies").
2. `_registrar`'s `on_announce` keeps its documented job — registering the pids so the abort cannot
   beat the fork — but only **arms** a daemon watcher; the watcher waits for `leaving` and fires at
   **+0.2 s**. Bound `DRAIN_CAP_SECONDS + 5`.
3. The root writes `b"done\n"` through **`sys.stdout.buffer`** (+`flush()`), never `print` — the file's
   own rule (`ROOT_WITH_A_LATE_TAIL`'s docstring, `test_run_contained_real_processes.py:396-401`),
   because `create_stdio` builds `sys.stdout` with `newline = NULL` under `MS_WINDOWS` and a
   `newline is None` wrapper writes `os.linesep`. Not hypothetical — row 34 is the windows leg of run
   33959649661 failing on exactly this construct, twice.
4. The pin is **`b"done\n" in result.stdout`, NOT `startswith`** — under the handshake the helper's

## D. Docs

**D.1 `AbortHandle` class docstring — two paragraphs, not one.**

*(a) "WHAT IT DOES, AND WHAT IT DELIBERATELY DOES NOT"* currently ends "…after which the call's
ordinary exit path **drains under its idle rule** and returns a `CompletedProcess` … to a caller that
has already stopped listening". Clause (d) removes exactly that drain. It becomes: the blocked
`proc.wait` returns because the root is dead, and the call then returns **at once** with the kill's
returncode and the bytes read so far — the drain does not run, because `abort()` also means "I have
stopped listening" (clause (d), #230). A holder outside the tree loses its tail: **87 B → 13 B**.

*(b) the closing sentence*, the one that hides the window:

> `_finish` runs at the REAP — the instant `proc.wait` returns on the success path, and the instant
> `_end_the_tree` returns on the timeout path *if it reaped* — not merely in the call's `finally`. The
> difference is the post-exit drain, and on `main` it was the whole bug (#230): the handle stayed armed
> for `EXIT_DRAIN_SECONDS` (0.105 s measured) or, with a holder that keeps writing, `DRAIN_CAP_SECONDS`
> (2.004 s), and an `abort()` there sent `killpg(SIGKILL)` at the group of a leader this call had
> already reaped — killing the helper an rc-0 command backgrounded on purpose, 3/3, while the call
> still returned `returncode == 0`. After the reap `abort()` returns `False`, sends nothing, and ends
> the drain instead (clause (d)). A residue of arm remains between the wait's return and the lock —
> 0.125 µs idle, **0.055 ms median / 0.103 ms max when another thread is running Python**, which the
> aborting thread here is — and before it the root is dead-but-unpublished for 0.712 ms
> (`timeout=None`) to ≈54 ms (a `timeout` given, where `Popen._wait` polls at a 0.05 s cap). What an
> `abort()` reaches in that residue is NOT a stranger: the helper is alive, so the group is non-empty
> and its id cannot be recycled (this module's PID/PGID paragraph) — it is this same bug, 10³–10⁴×
> narrower than the drain it replaces, and a reap-synchronised aborter still landed in it 17 times in
> 20. `ProcessTree.close`'s hazard is the OTHER branch — the helper gone too and the group EMPTY, where
> `killpg` answers ESRCH and a recycled number would need the pid space to wrap inside the residue
> against a floor of 85.6 s. On win32 the retained handle rules reuse out entirely.
