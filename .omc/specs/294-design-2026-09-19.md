## §0 Baseline — measured on `main` `e1fef5f`

(`uv run --no-sync python <probe>` from the repo root; the critic re-ran it with the same result, ids differ). Output:

```

[2] fork raised: SessionError Failed to append session entry c5487a19: [Errno 28] No space left on device (injected)
```

1. **An unknown entry `type` costs every entry below it.** `entry_from_json` raises `ValueError` on an unknown `type`;
   `_parse_entry_line` wraps any exception as `invalid_entry`; `_load_jsonl_storage` skips the line **and then prunes every
   entry whose parent chain passes through it** (ADR-0208's orphan pass). This is what beta.1 and beta.2 do, forever —
   they are released. The same happens for an unknown message `role`, a missing required key, and a changed JSON type of a
   key the decoder reads (§A.1.3b).
2. **A fork interrupted part-way leaves a truncated session that `--continue` then resumes.** `fork` / `fork_from` call
   `JsonlSessionStorage.create` (header) then `append_entry` per entry; `find_most_recent` sorts by mtime and sniffs only
   the header. `import_from_jsonl` has the same shape through `LocalFileSystem.copy_file`, which truncates the destination
   in place (`O_TRUNC`) and then `shutil.copyfile`s onto it — a failure mid-copy leaves a half file, and when that basename
   already existed the complete file that was there is gone.
3. **One failed append loses every turn after it on the next load.** `_append_line` never sets `_needs_newline` on failure,
   so the next append is glued onto the fragment; the fused line does not parse, and every later entry descends from the
   entry inside it → pruned. The harness makes this reachable: the `message_end` path catches every append exception and
   logs it at DEBUG (`harness/core.py`, "session.append_message raised on message_end"), so the turn continues and keeps
   appending. Separately, `append_file` / `write_file` ignore `os.write`'s return value — a short write silently drops the
   tail of the line with no exception, which ends the same way.

Also true today (fact, not a defect to fix blindly): on Windows `os.open` without `O_BINARY` returns a **text-mode**
descriptor, so every session line Aelix writes there ends in `\r\n` (the stdlib adds `O_BINARY` by hand for this reason —
`tempfile._bin_openflags`, `_pyio.FileIO.__init__`). Readers use universal newlines, so nothing breaks today; §A.4 makes
the bytes identical on every platform.

What already holds (do not re-fix): the header check is strict; an unparseable line is skipped whole, never salvaged
(ADR-0208); an unterminated tail is healed with a leading `\n` on the next append; a **complete but unterminated** final
line is kept (ADR-0208 — pi v4 drops it; see §D); files are 0600 / dirs 0700 (ADR-0208 Track S2).

## §A Decisions

### A.1 The record-evolution rules (the part #199 depends on)

1. **The entry `type` set is closed** at the ten on disk today: `message`, `thinking_level_change`, `model_change`,
   `compaction`, `branch_summary`, `custom`, `custom_message`, `label`, `session_info`, `leaf`. A new kind of record is a
   `CustomEntry` (`type: "custom"`, `customType`, `data`) — every released Aelix decodes it and keeps its descendants. A
   record that must reach the model or the transcript is a `CustomMessageEntry` instead.
2. **The message `role` set inside a `message` entry is closed** at `user` / `assistant` / `toolResult`.
3. **Everything that must survive goes inside `CustomEntry.data`.** Every released Aelix drops unknown header, entry,
   message and content-block keys when it forks (`fork` / `fork_from` decode into dataclasses and re-encode with
   `entry_to_json`); only `CustomEntry.data` survives a fork verbatim. Measured by the critic on `main`:

   | unknown key at | survives a released fork |
   | --- | --- |
   | header (`futureHeaderKey`) | no |
   | entry (`futureKey`) | no |
   | message (`futureMsgKey`) | no |
   | content block (`futureBlockKey`) | no |
   | `CustomEntry.data` (`futureDataKey`) | **yes** |

   So a known type MAY gain an optional key only when losing it on a fork is acceptable (readers ignore unknown keys —
   pin that), and required keys are never removed or renamed. Required keys today: `message.message`;
   `thinking_level_change.thinkingLevel`; `model_change.provider`+`modelId`; `compaction.summary`+`firstKeptEntryId`+
   `tokensBefore`; `branch_summary.fromId`+`summary`; `custom.customType`; `custom_message.customType`+`content`+`display`;
   `label.targetId`; plus `id`/`timestamp` on all. The header may gain keys (same fork caveat); **`version` stays `3`** —
   any other value makes every released Aelix refuse the whole file (`_parse_header_line`).
3b. **Never change the JSON type of a key the released decoder reads:** `message` is an object; `message.content` is a
   list of objects (a string — pi's own `UserMessage` shape — drops the line); `tokensBefore` is an int; `parentId` and
   `leaf.targetId` are a string or null; `display` is a JSON bool (`"false"` reads as `True`).
3c. A first-party `CustomMessageEntry.content` is a plain string (list content is decoded as raw dicts and handed untyped
   to `create_custom_message`).
4. **First-party record kinds use a `customType` in the `aelix.` namespace** (e.g. `aelix.child_session` — #199 names its
   own). Extensions pick their own `customType` through `append_entry`; the prefix keeps the two from colliding
   (`custom_type` is only ever a renderer dict key and a display label — no parsing). The one existing first-party type,
   `bash_execution` (`cli/repl.py` `handle_user_bash`), predates the rule and keeps its name. Documented, not enforced.
5. **A reader ignores a `customType` it does not know and `data` keys it does not know.** (Already true — pin that
   `build_session_context` / `build_display_messages` skip `custom` entries.)
6. **Payloads are JSON values**: lists not tuples, finite floats, no dataclasses — in `data`, `details`, `content` and
   message fields. JSONL serializes with `json.dumps` (tuples come back as lists; `NaN` is written bare, which Aelix reads
   back and strict readers such as pi's do not). A backend MAY reject a non-JSON payload; JSONL now does, as
   `SessionError("invalid_entry")` before any byte is written (§A.3). Memory does not serialize and accepts it.
   **Corrected after review (B1):** JSONL refuses only what it cannot *convert* — what `json.dumps` cannot encode
   (dataclass, `set`, `bytes`, circular reference) and, after the lead round, a non-dataclass `message` that
   `entry_to_json`'s `asdict` rejects. Tuples, non-string keys, `NaN` and `±Infinity` are still written as
   `json.dumps` writes them and come back changed; ADR-0242 rule 7 states it that way.

### A.2 One storage call = one line = one `append_file` call

`append_entry` and `set_leaf_id` each append **exactly one** `\n`-terminated JSON object with **exactly one**
`FileSystem.append_file` call (the healing `\n`, when needed, is part of that same call). "One write" means one
`FileSystem` call; `LocalFileSystem.append_file` may issue several `os.write` syscalls after a short write, and under a
second writer (#137, not solved here) another line could land between them. Drop the "≤ PIPE_BUF atomicity" docstring
claims in `fs.py` / `jsonl_storage.py` while rewriting them — `PIPE_BUF` is a pipe/FIFO guarantee, not a regular-file one.
A caller that needs several entries for one operation must make **every prefix of the log a valid session** — the file can
end after any line. `Session.move_to(entry, summary)` writes a `leaf` line then a `branch_summary` line; the prefix that
stops between them is valid (leaf moved, summary missing), so it stays as is (pi v3 parity) — do not touch `session.py`.

### A.3 A failed or short write never corrupts the next one

- `LocalFileSystem.append_file` and `write_file` loop until every byte is written (`os.write` may return short); a zero
  return raises `OSError(errno.EIO, …)` so the loop cannot spin.
- `JsonlSessionStorage._append_line`: serialize first (`json.dumps`); a `TypeError` / `ValueError` there raises
  `SessionError("invalid_entry", …)` with nothing written and `_needs_newline` untouched. Then on **any** exception from
  the write (`BaseException` — a second Ctrl-C between two `os.write` calls, a `CancelledError` in an awaiting
  `FileSystem`, ENOSPC) set `self._needs_newline = True` and re-raise, translating only `OSError` to
  `SessionError("storage", …)`. The in-memory state is untouched on failure (the entry is added only after the write) —
  keep it that way and pin it.
- What a failed append leaves on disk is one of three things, and the ADR says so: **absent** (the next append adds a
  blank line, which the loader filters and does not count as a skip); **a fragment** (skipped on load as its own
  unparseable line; nothing is pruned because nothing in memory descends from it); **a complete line** (the failure hit
  after the last JSON byte, e.g. at `os.close`) — kept on load with `recovery is None`, as an off-path sibling when later
  appends happened, or as the resumed leaf when it was the last write. Nothing is lost in any case; the third is
  at-least-once, and it is pinned so nobody later "fixes" it into a truncation.
- Do **not** truncate the fragment away (`ftruncate` to the pre-append size): with a second writer on the file (#137)
  that cuts the other writer's bytes.

### A.4 Whole-file writes are published atomically; the bytes are the same on every platform

- **Binary descriptors.** Every `os.open` in `LocalFileSystem` that writes session bytes (`append_file`, `write_file`, the
  `copy_file` temp) adds `getattr(os, "O_BINARY", 0)`. The bytes on disk are then the bytes Aelix wrote, LF only, on every
  platform. Windows files written before this are CRLF; they still load and append (universal newlines on read; a file
  torn between `\r` and `\n` reads as terminated) — pin mixed endings with a test that builds a CRLF file by hand.
- `FileSystem` Protocol gains `async def rename_file(self, source: str, destination: str) -> None` (pi `renameFile`):
  atomically replace `destination` with `source`, same directory. `LocalFileSystem.rename_file` = `os.replace`.
- `LocalFileSystem.write_file`: create/truncate at 0600 with `_tighten_if_loose` (as today, so a stale temp is reused
  safely), write every byte. **No fsync** (process-crash level, like appends). Docstring: it is the staging half of a
  publish.
- A private publisher in `jsonl_storage.py`, e.g. `_publish_file(fs, path, content)`: temp = `f"{path}.tmp"` (pi parity;
  destinations are unique per create/fork; the name does not end in `.jsonl`, so `list` / `find_most_recent` never see
  it); `await fs.write_file(temp, content)`; `await fs.rename_file(temp, path)`; on **any** exception remove the temp
  best-effort (`fs.remove(temp, force=True)` under `contextlib.suppress(OSError)`) and re-raise; translate `OSError` to
  `SessionError("storage", f"Failed to create session {path}: {exc}")` as `create` does today. Serialize every line
  before staging, so a non-JSON payload raises `invalid_entry` with no file written.
- `JsonlSessionStorage.create(fs, file_path, *, cwd, session_id, parent_session_path=None, entries=())` — new keyword
  `entries: Sequence[SessionTreeEntry] = ()`. It publishes header + one line per entry **in one publish**, then returns an
  instance whose entries are those entries and whose leaf is the fold of `_leaf_id_after_entry` over them. Bytes must be
  identical to what header-then-append produced (critic verified with a patched probe).
- `JsonlSessionRepo.fork` and `fork_from` pass their entries to `create(..., entries=...)` instead of looping
  `append_entry`. Error type on failure stays `SessionError("storage")`; the difference is that no file is left.
- `LocalFileSystem.copy_file` (import), **exact spelling** (the critic measured `19 passed` for it; a byte loop through a
  text-mode fd breaks the spy test on every platform and translates LF→CRLF on Windows):
  1. temp = `f"{destination}.tmp"`; unlink a stale temp if present (`contextlib.suppress(FileNotFoundError)`);
  2. `os.open(temp, O_WRONLY|O_CREAT|O_EXCL|getattr(os,"O_BINARY",0), SESSION_FILE_MODE)`, then close;
  3. `shutil.copyfile(source, temp)` (binary, byte-exact; the spy test keeps its meaning — its `dst` is the temp, which
     exists at 0600);
  4. reopen the temp `O_WRONLY|O_BINARY`, `os.fsync`, close — **the only fsync in the store**: `copy_file` can replace an
     existing complete file, and a rename that outlives its data would leave it empty after power loss;
  5. `os.utime(temp, (src.st_atime, src.st_mtime))`, then `os.replace(temp, destination)`;
  6. on any exception unlink the temp best-effort and re-raise. Keep the parent-dir 0700 handling; never `copy2`/`copystat`.
- Durability level, stated in the ADR and docstrings: **process crash**. Appends and publishes are not fsynced (same as
  pi); `copy_file` is. No directory fsync. A crash between staging and rename leaves `<file>.tmp` (owner-only); it is
  never listed, the next publish to the same path overwrites it, and nothing sweeps it — say so in the ADR.
- **No rewrite-on-open.** Pi v4 rewrites a file with a torn tail when it opens it. Here a *reader* (a second terminal
  running `--continue`, `/resume`) can observe another writer's line mid-write; rewriting would publish a file without
  that line, and the writer's completed append then lands in the replaced inode — lost. Recovery stays non-destructive
  (ADR-0208).

### A.5 One conformance suite, every backend — `tests/session/test_storage_conformance.py`

A parametrized fixture yields a backend object with `storage` (fresh, empty), `async reopen()` (a new instance built only
from what the backend holds — JSONL: `JsonlSessionStorage.open` on the same path; Memory:
`MemorySessionStorage(entries=await s.get_entries(), metadata=await s.get_metadata())`), and `async prefix(k)` (a new
instance holding only the first `k` entries — JSONL: the durable file cut after header + `k` lines, written to a sibling
path and opened; Memory: the constructor with `entries[:k]`). Params: `["memory", "jsonl"]`. The module docstring says:
**a new backend is added by adding a param here, and it must pass unchanged** (pi does the same with SQLite), and it lists
what the suite deliberately leaves backend-specific (non-JSON payload rejection §A.1.6; when a dangling leaf is detected).

Groups (each a handful of focused tests; names say the contract):

- **protocol & metadata** — `isinstance(storage, SessionStorage)`; metadata has non-empty `id` / `created_at`, stable
  across calls and across `reopen()`.
- **ids** — `create_entry_id` returns a non-empty `str` not equal to any stored id (append many, check).
- **append / get** — `get_entry` returns an equal entry; unknown id → `None`; `get_entries` is insertion order and is a
  copy (mutating the returned list changes nothing).
- **leaf** — empty → `None`; after append → that id; `set_leaf_id(existing)` moves the leaf **and appends one `leaf`
  entry** (`parent_id` = previous leaf, `target_id`) visible in `get_entries`; `set_leaf_id(None)` → `None`;
  `set_leaf_id(unknown)` → `SessionError` code `not_found` and **nothing appended**; appending a `LeafEntry` directly sets
  the leaf to its target. A state whose folded leaf dangles raises `invalid_session` **no later than `get_leaf_id()`**
  (Memory raises at construction, JSONL at `get_leaf_id` — both allowed; build it via `prefix`-style construction from a
  hand-made entry list / file).
- **labels** — set, strip, latest wins, `None` / `""` / whitespace clears, unlabeled → `None`.
- **find_entries** — by type, insertion order, includes `leaf` entries for `"leaf"`, unknown type string → `[]`.
- **path to root** — `None` → `[]`; root-first; follows the branch after `set_leaf_id`; unknown leaf → `not_found`;
  missing parent in the chain → `invalid_session`.
- **round trip** — a catalogue covering **every member of `typing.get_args(SessionTreeEntry)`** with every optional
  field both set and unset (assert the coverage itself, so a new member fails here first), JSON-value payloads only
  (§A.1.6): nested lists/dicts, `None`, bools, ints, finite floats, non-ASCII, `"\n"`, `"\r"`, `" "`;
  user/assistant/toolResult messages using the content fields `tests/session/test_message_roundtrip_content.py` already
  proves total; `CustomMessageEntry` content as a plain string (and one list-of-dicts case). Each entry survives
  `get_entry` **and** `reopen()` equal.
- **durability** — after a mixed script (two branches, `set_leaf_id` moves incl. to `None`, labels set/cleared, a
  compaction, custom entries, a session name), `reopen()` gives equal `get_entries`, `get_leaf_id`, every label,
  `get_path_to_root(leaf)`, and `find_entries` for every type.
- **every prefix is a session** — for every `k` in `0..n` over that script: `prefix(k)` has `get_entries() ==
  entries[:k]`, `get_leaf_id()` resolves, `get_path_to_root(leaf)` does not raise; for JSONL additionally `recovery is None`.
- **custom entries** (backend-agnostic half of §A.1) — a `CustomEntry` with a never-seen `custom_type` and rich `data`
  round-trips; a message appended as its child survives `reopen()` and is on the path; `build_session_context` and
  `build_display_messages` over that path contain the message and nothing for the custom entry.
- **many appends** — N `append_entry` calls via `asyncio.gather`: all present after `reopen()`, in call order. (The
  real interleaving test is JSONL-only, §A.6.)

### A.6 JSONL write discipline and the rules' reasons — `tests/session/test_jsonl_write_discipline.py`

- **one call, one write, one line** — a spy `FileSystem` (subclass `LocalFileSystem`, record `append_file` calls): every
  `append_entry` (each catalogue entry) and `set_leaf_id` makes exactly one call whose content is one `\n`-terminated line
  (or `\n` + line + `\n` after an unterminated tail) holding exactly one JSON object, with no raw `\n` / `\r` inside even
  when `data` contains them; the file then has 1 + N lines; the file's bytes contain no `\r` (binary descriptors).
- **interleaving is serialized** — a `LocalFileSystem` subclass whose `append_file` does `await asyncio.sleep(0)` before
  writing; `asyncio.gather` N appends; every line parses, order is call order (the `asyncio.Lock` FIFO is what is tested).
- **short writes** — replace the `os` the fs module sees with a proxy (a `types.ModuleType` subclass delegating to the real
  `os`) whose `write` writes at most 7 bytes per call — do NOT patch the global `os.write`, pytest's capture uses it; append
  the catalogue; `reopen()` returns it all and every line parses.
- **a failed append does not cost the next one** — the §0 [3] scenario: turn-1 ok; turn-2's append writes half its line
  then raises `OSError`; `SessionError` code `storage`; `get_entries` / `get_leaf_id` unchanged; turn-3, turn-4 ok;
  reopen → turn-1, turn-3, turn-4, `recovery.skipped_lines` == the fragment's line only, `orphaned_entries == ()`.
  Twins: (a) the failure happens before any byte lands → the next appends load, `recovery is None`; (b) the failure is a
  `KeyboardInterrupt` after half the line → same outcome as the OSError case (it propagates as `KeyboardInterrupt`);
  (c) the whole JSON landed but not its `\n` → reload keeps it, `recovery is None`, it is off the path of the later
  entries (and when it was the last write, it is the resumed leaf).
- **a non-JSON payload** — a `CustomEntry` whose `data` holds a dataclass (and one with a `set`): JSONL raises
  `SessionError` code `invalid_entry`, the file is byte-identical to before, in-memory state unchanged. Same through
  `create(entries=[…])`: no file (no `.jsonl`, no `.tmp`).
- **a torn tail is discarded whole, at every cut point** — for every entry line `k` of a session file, let `J` be its JSON
  bytes (the file is LF-only now): for every `c` in `[1, len(J)-1]`, the file cut `c` bytes into `J` opens with exactly the
  entries before `k`, `recovery.skipped_lines == (k,)`, `orphaned_entries == ()`; one append then reloads with the new
  entry parented on the recovered leaf. Separately pin `c == len(J)` (the JSON complete, the `\n` missing): kept,
  `recovery is None`, the next append heals the tail (ADR-0208's kept case, pinned as a decision). If a full `[1, len-1]`
  sweep over every line is slow, sweep every line at a handful of offsets (1, 2, middle, len-2, len-1) — say which.
- **CRLF files still work** — a file built by hand with `\r\n` endings (what Windows Aelix wrote before this change) opens
  with all entries, takes an append, and reopens with all entries plus the new one; also the variant that ends in a lone
  `\r`.
- **whole-file writes are atomic** — for `JsonlSessionStorage.create`, `JsonlSessionRepo.fork`, `fork_from`, and
  `LocalFileSystem.copy_file`: inject failures that actually exercise the defect — a `write_file` that writes HALF the
  content via `super()` and then raises; a `rename_file` that raises; for `copy_file` an fs-module `shutil.copyfile`
  wrapper that writes half and then raises, and an fs-module `os` proxy whose `replace` raises. Each time: the call raises,
  **no destination file exists** (or, for `copy_file` over an existing destination, the old bytes are intact), **no
  `*.tmp` is left**, and `find_most_recent` for that cwd returns `None` (create/fork/fork_from). Success path: a full-copy
  fork's `get_entries` / leaf equal the source's, mode `0o600` on POSIX (skip on `win32`), no temp left; a stale
  `<dest>.tmp` left by an earlier crash does not block the next publish/copy.
- **why the rules exist (pins of the released loader and fork)** — a file with an unknown `type` line mid-tree loads
  without that line **and without its descendants**; same for an unknown message `role`; same for a known type missing a
  required key; same for `message.content` as a string. A released fork keeps an unknown `CustomEntry.data` key and drops
  an unknown entry-level key. Positive twin: every catalogue entry's wire dict with an extra unknown key decodes equal to
  the original; a header with an extra key opens. Failure messages point at ADR-0242.
- **the closed set** — the set of `type` defaults over `get_args(SessionTreeEntry)` equals exactly the ten names; the
  assertion message says what to do instead ("put the record in a CustomEntry with an `aelix.` customType — ADR-0242").

Use `tmp_path`; no network; no sleeps; Windows-safe (no POSIX-only calls outside a `sys.platform` guard; modes checked only
off Windows). Keep total runtime of the two new modules under ~5 s locally.
