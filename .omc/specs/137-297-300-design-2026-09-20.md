## §0 Baseline — all three defects reproduced on `47dfacd`, today

```
=== #137 two writers on one file ===
  every entry on disk          = ['A-turn-1', 'B-turn-1', 'A-turn-2']
  lines on disk (incl. header) = 4, all parse = True
  replay after reopen          = ['A-turn-1', 'A-turn-2']
  entries actually stored      = 3
=== #297 header over 512 bytes ===
  cwd length          = 156
  origin header bytes = 287
  fork   header bytes = 606
  _is_valid_session_file(origin) = True
  _is_valid_session_file(fork)   = False
  find_most_recent picks         = origin
=== #300 fork before the first user message ===
  first entry type/role = message/user

  entries in the 'empty' fork = 2 (expected 0)
```

#137 reproduces the issue body's measurement exactly: `A-1`, `B-1`, `A-2` all land, all four lines parse, and the replay
is `['A-turn-1', 'A-turn-2']`. B's turn is on disk and invisible forever.

The three are one lane because D1's fork path walks through the other two (D2). Order is **#297 → #300 → #137**: a fork
that `--continue` cannot find (#297) and a fork that copies the whole session (#300) would each make the #137 prompt

## §A The three root causes, read in the tree (not from the decisions doc)

### A.1 #297 — `_is_valid_session_file` truncates the header at 512 bytes

`session/jsonl_repo.py:339-364`. The sniff does `f.read(512)`, then `split("\n", 1)[0]`. A header longer than 512 bytes
yields a truncated first line, `json.loads` raises, the file is dropped as "not a session".

A fork header carries `cwd` **and** `parentSession`, and `parentSession` contains the encoded cwd a second time, so it is
roughly twice the origin's. Measured above: a 156-char cwd gives a 287-byte origin header and a **606-byte** fork header.

The full metadata read (`load_jsonl_session_metadata`, `session/jsonl_storage.py:369-388`) has **no** such cap — it goes
through `FileSystem.read_text_lines(max_lines=1)` (`session/fs.py:190-202`), which reads a whole line. So the two readers
of the same line disagree, and the sniff is the stricter one. Only the sniff is wrong.

### A.2 #300 — `entry_id=None` is overloaded

`session/repo_utils.py:58-59`: `if entry_id is None: return await storage.get_entries()` — "fork the whole session".

`runtime/agent_session_runtime.py:946`: `target_leaf_id = selected_entry.parent_id`. For the first entry in the file that
is `None`, and `:958-963` hands it straight to `ForkOptions(entry_id=target_leaf_id, position="at")`. "Fork before the
first message" therefore means "copy everything".

Two distinct intents collide on one `None`. Note `get_path_to_root(None)` **already** returns `[]`
(`session/jsonl_storage.py:706-707`) — the empty fork is one branch away, it is just unreachable.

No production caller passes `entry_id=None` on purpose; the six that do are tests plus `.omc/specs/294-measure.py`.
`fork_from` is the real whole-session copy and does not use `get_entries_to_fork` at all (`jsonl_repo.py:500-503`).

### A.3 #137 — the leaf pointer is process-local

`session/jsonl_storage.py:544` seeds `_current_leaf_id` at open; `:692` reassigns it after every append; `Session`'s
eleven `append_*` methods read it back through `get_leaf_id()` to parent the next entry
(`session/session.py:185,195,205,225,241,258,279,290`). Two processes each hold their own copy. The second writer parents
onto a leaf the first has already moved past, and the losing branch is invisible on the next load.

The issue body is right that `flock` on the fd fixes nothing — the bytes are fine. What has to become impossible is the
second **writer**, and that is what D1 decides.

## §B The design

### B.1 One rule

> **A session file has at most one live writer. Everything else either forks, or does not write.**

Enforced in two layers: an OS lock on a sidecar file (mechanism), and a storage wrapper that refuses writes (belt).

### B.2 The lock (D3)

`filelock.FileLock` on `<session>.jsonl.lock`, acquired with `timeout=0.25, poll_interval=0.05`.

**Sidecar, never the `.jsonl` itself.** On Windows `LockFileEx` is a *mandatory* byte-range lock over byte 0 of the file
it opened (`filelock/_windows.py:156-172`). Locking the session file directly would make a read-only viewer's `read()`
fail with a lock violation there and not on POSIX. `.jsonl.lock` does not end in `.jsonl`, so neither
`find_most_recent` nor `list` can see it (`jsonl_repo.py:248,310`), and filelock unlinks it on release on both platforms
(`_unix.py` / `_windows.py:203-213`).

**250 ms, not one non-blocking attempt.** filelock unlinks the lock file on release, so a release that lands between a
contender's `open()` and its `flock()` leaves the contender holding a dead inode; filelock detects it (`st_nlink == 0`)
and retries, but a single-shot `blocking=False` would surface that as a false "already open". A quarter second also
absorbs a legitimate handoff — the other terminal running `/resume` or `/new` at that instant. It is imperceptible at
startup and it removes a whole class of wrong prompt.

**No stale reclamation, no heartbeat, exactly as D3 says.** Verified in the 4.0.1 wheel, not from the docs:
`_unix.py:47-58` is `fcntl.flock(fd, LOCK_EX|LOCK_NB)`; `_windows.py:156-172` is `LockFileEx` with
`LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY` over a one-byte range, plus a reparse-point refusal. Both are
kernel-held: a `kill -9`, a closed laptop lid, a crashed terminal all release them. pi's `stale: 2_000 / update: 1_000`
heartbeat exists because Node has no OS lock API; we do not copy that.

**The no-`flock` filesystem.** `UnixFileLock` silently degrades to `SoftFileLock` (an `O_CREAT|O_EXCL` placeholder) when
the filesystem answers `ENOSYS` — NFS without lockd, some FUSE mounts (`_unix.py:118-135`). A soft lock does **not** die
with the process, which is precisely the stale-lock problem D3 refuses to own. We therefore pass
**`fallback_to_soft=False`** and catch the resulting `OSError`: we degrade to *no ownership check at all* and print one
stderr line — `Warning: this filesystem has no file locking; a second terminal on this session cannot be detected.`
Refusing to start would lock a user out of their own sessions over a mount option; silently taking a stale-able lock
would hand them a file nobody can open until they delete it by hand. Saying so is the only honest third option.

### B.3 "Open read-only" does **not** take a read lock — and the decisions doc's sketch cannot work

D3's sentence "`filelock.ReadWriteLock.acquire_read/acquire_write` is how 'open read-only' is served" rests on a factual
premise that does not hold in filelock 4.0.1. Two measurements from the wheel:

1. `ReadWriteLock` is **SQLite-backed**, not `flock`-backed: `filelock/_read_write.py:6` imports `sqlite3`, `:247-249`
   says "Cross-process read-write lock backed by SQLite", and `filelock/__init__.py:28-36` sets `ReadWriteLock = None`
   when the interpreter has no `sqlite3`. It is a different mechanism from `FileLock`, with a database file, journals,
   and its own failure modes.
2. More decisive: **a reader/writer lock excludes a concurrent writer by definition.** Terminal A owns the session and is
   writing. B's `acquire_read` would either block or fail for as long as A keeps its write lock — so the one situation
   "open read-only" exists for is the one situation it could not serve. If it somehow succeeded, it would starve the
   legitimate owner.

**Resolution: read-only takes no lock.** It opens the file, loads a snapshot, and never writes. That is already safe
here — appends are one `O_APPEND` line each (ADR-0242 §2), every line on disk parses, and `_load_jsonl_storage` already
skips a torn tail (ADR-0208). The viewer sees the session as of the moment it opened.

This keeps D3 whole: the dependency is still `filelock`, still MIT, still the OS lock, still no heartbeat. Only the
sub-mechanism for the read-only option changes, and it changes because of a measurement. If the owner wants a true
shared-reader lock instead, that is a different design and a `sqlite3` dependency in the kernel's lock path — say so and
it comes back.

**What makes read-only real:** `ReadOnlySessionStorage`, a `SessionStorage` wrapper that delegates the six read methods
and raises `SessionError("read_only", …)` from `append_entry`, `set_leaf_id` and `create_entry_id`. Without it
"read-only" is a promise the UI makes and nothing keeps.

### B.4 The prompt (D1)

Reuses `_prompt_one_shot_select` (`cli/entry.py:1632`) — the same one-shot `prompt_toolkit.Application` the project-trust
gate uses, which already returns `None` on Esc/Ctrl-C **and** when the `[tui]` extra is missing.

```
This session is already open in another terminal.
  <path>

→ Fork and continue here (a new session file, same history)
  Open read-only (view only; this terminal cannot write)
  Cancel
```

- **Fork and continue** → `repo.fork(meta, ForkOptions(cwd, entry_id=<current leaf>, position="at",
  parent_session_path=meta.path))`, then acquire the lock on the **new** file. The new file is newest by mtime, so the
  next `--continue` lands on it — which is only true once #297 is fixed. This is D2's whole argument.
- **Open read-only** → `ReadOnlySessionStorage`, no lock, a banner and a footer marker.
- **Cancel** / Esc / Ctrl-C / no `[tui]` extra → exit 1 with the path and the three flags that get you past it
  (`--fork <path>`, `--session <other>`, `--no-session`).

Default cursor is **Fork and continue**, except when the user named an exact file (`--session` / `--fork`), where it is
**Open read-only** — they asked for *that* file and a fork is a different one.

### B.5 Where the lock lives, and who hands it over

| | |
|---|---|
| Owns the primitive | `aelix-agent-core` — `session/session_lock.py` (`SessionWriterLock`) and `session/read_only.py` |
| Owns the policy (prompt, wording, exit codes) | `aelix-coding-agent` — `cli/entry.py`, `tui/shell.py` |

The kernel gets a mechanism and no UI, which is the dependency direction AGENTS.md §1 requires.

`JsonlSessionRepo.open()` stays lock-free. It must: `--export` opens a session purely to render HTML
(`cli/entry.py:534-535`), and acquiring there would make `aelix --export` fail against a session you have open. The lock
is an explicit act by a caller that intends to write, never a side effect of opening.

Handoff points:

- **startup** — `cli/entry.py:2145-2161`, after the session is resolved and before the trust gate.
- **in-session swap** — `runtime/agent_session_runtime.py:443` `_finish_session_replacement`, the single seam every
  `/new`, `/resume`, `/fork` and `/import` passes through. Acquire the new file's lock **before** `_teardown_current`
  releases the old one where they differ; on failure the swap is refused and the old session is kept, because a swap
  that both released and failed to acquire would leave a live harness writing to a file it does not own.
  (`/new` and `/fork` create a fresh file and cannot contend; `/resume` and `/import` can.)
- **exit** — `runtime/agent_session_runtime.py:1076` `dispose`, plus a `finally` in `entry.py` for paths that never build
  a runtime. The kernel releases the OS lock on process death anyway; the explicit release is for the lock *file*.

**How the kernel asks without owning a UI.** `switch_session` opens the file itself (`:624-625`), so the contention is
discovered inside the kernel. `AgentSessionRuntime.__init__` therefore takes one more injected callback, exactly like the
`_rebind_session` it already holds:

```python
on_session_contended: Callable[[str], Awaitable[Literal["fork", "read_only", "cancel"]]] | None = None
```

`aelix-coding-agent` injects the prompt; `None` (tests, embedders, headless) means **refuse** —
`SessionError("storage", "session is already open in another terminal: <path>")`. `"cancel"` needs no new plumbing:
`switch_session`, `new_session` and `fork` already return `RuntimeReplaceResult(cancelled=True)`, and the callers already
handle it. The kernel learns "a file can be owned and someone else decides what to do about it", which is a mechanism;
the wording, the widget and the default cursor stay in the product band.

### B.6 #300's fix — a sentinel, not a third `position`

`repo_utils.py` gains:

```python
class _ForkFromRoot: ...
FORK_FROM_ROOT: Final = _ForkFromRoot()          # "fork at the root: an empty branch"
ForkEntryId: TypeAlias = str | _ForkFromRoot | None
```

`get_entries_to_fork` checks `entry_id is FORK_FROM_ROOT → []` before the existing `entry_id is None → get_entries()`.
`agent_session_runtime.fork` passes `selected_entry.parent_id or FORK_FROM_ROOT` (`or`, not `if is None`: `get_path_to_root`
already treats a falsy `parent_id` as root, `jsonl_storage.py:714`).

**Not a third `ForkPosition`.** `ForkPosition` is exported from `session/__init__.py:71,101` and mirrored by
`harness/hooks.py:805` as `Literal["before", "at"]` on the `session_before_fork` payload. A fork at the root is still,
from the user's side, `position="before"` — so the hook keeps telling the truth, and the discriminator belongs on
`entry_id`, which is the field that is ambiguous. All six existing `ForkOptions(cwd=…)` call sites keep working
unchanged.

### B.7 #297's fix — read the first line, with a derived cap

`_is_valid_session_file` becomes `f.readline(65536)` on the binary handle — at most 64 KiB, stops at `\n`. A line that
hits the cap without a newline is not a header and returns `False`.

64 KiB is derived, not picked: the header's two unbounded fields are `cwd` (`PATH_MAX` 4096 on Linux) and
`parentSession` (an absolute path whose directory component is the encoded cwd, so ~2×4096 plus a 60-byte filename),
plus fixed keys and JSON escaping. An order of magnitude over the worst case, and four orders under any file we would
want to read fully.

Behaviour that must not change, and does not: a header with no trailing newline still parses (ADR-0208 keeps a complete
but unterminated final line); a CRLF header written by pre-ADR-0242 Windows Aelix still parses, because the trailing
`\r` is whitespace to `json.loads` — the same reason it works today.

### B.8 What this does *not* do

- No tail-re-read-before-append. D1 makes it unnecessary, and pi issue #8334 names the cost it would not pay for:
  two writers on one file give the provider a different prefix every turn and **break the prompt cache**.
- No stale-lock reclamation, no heartbeat, no lease (D3).
- No migration of the two existing POSIX-only `fcntl` sites (`aelix_ai/oauth/auth_storage.py:55-57,184` — `_fcntl` is
  `None` on Windows and every call site returns before touching it — and `aelix_ai/settings/storage.py:10,16`, which
  mirrors it; ADR-0091, #46). They are a separate defect in a separate package; this lane would have to widen to
  `aelix-ai` to touch them. Recorded in ADR-0244 as explicitly out of scope, so the repo knowingly holds two locking
  idioms and that is on the record rather than discovered later.
- No "take over the other terminal's session" fourth option. D1 fixed three.

## §D The open decisions from `§남은 설계 결정`, resolved

### D.1 Non-interactive paths (`-p`, `--mode json`, `--mode rpc`) — **refuse**

A process that cannot ask must not choose data loss, and must not silently create session files in someone's loop.

Narrower than it sounds: contention only arises when a non-interactive run *targets an existing session*
(`--continue` / `--resume` / `--session`). A bare `-p` creates a new file and never contends. So the refusal is:

```
Error: this session is already open in another terminal.
  <path>
Use --fork <path> to branch it, --session <other> to pick another, or --no-session.
```

exit 1, on stderr, in `--mode json` as a structured error on the existing error channel. `--mode rpc` refuses at startup;
an in-session RPC switch onto an owned file returns an error result rather than killing the server.

A delegated child (`subagent_depth() > 0`) takes this path, which is right: a child that cannot own its own file must
fail where the parent can see it, not fork into a file the parent will never look at.

### D.2 Which file the next `--continue` picks after a fork — **the fork, by mtime, with no new code**

`find_most_recent` already sorts mtime DESC (`jsonl_repo.py:319-320`). A just-published fork is the newest file, so it
wins. That is already the intent; **#297 is the only reason it is not the behaviour**. Fixing #297 is the whole fix here.

One consequence to state rather than hide: if terminal A keeps writing the original after B forks, A's mtime passes the
fork's, and a *third* `--continue` lands on A's file — and then gets the prompt, because A holds the lock. That is
correct: `--continue` means "the session most recently worked in here". Pinned by a test.

### D.3 An explicitly named session (`--session` / `--fork` / `--session-dir`) — **same prompt, different default**

One rule, one widget, one test matrix: every path that opens a session **for writing** resolves ownership the same way.
A special case would mean a second code path with its own bugs, for a difference the user cannot see.

What does change is the default cursor: `--continue` / `--resume` default to **Fork and continue**; `--session` /
`--fork` default to **Open read-only**, because the user named that file and a fork is a different file. One constant,
one test.

`--session-dir` is orthogonal — it moves the sessions root, so the lock sidecar moves with the file. No special case.

### D.4 ADR-0242 §4 — see §F. The decision stands; its stated reason must be amended.

### D.5 Delegated child sessions (#199) — **locked, by the same code, with no special case**

A child file has exactly one live writer by construction: the parent publishes it once with
`JsonlSessionStorage.create` before the child exists (`aelix_agents/child_session.py:421,460`) and thereafter appends
only to its *own* session. The parent holds no lock on it, so the child — launched with `--session <that path>` — acquires
cleanly.

Locking them is still worth it, and free: it closes the case a human hits by opening a still-running child with
`--session <child file>`, which today gets only a warning (`cli/entry.py:3322-3356`) and then silently reproduces #137.

### E.4 The risk that is real, and the one that is not

- **Not a risk:** stale locks after a crash. Both backends are kernel-held (`§B.2`).
- **Real, and handled:** a filesystem without `flock`. filelock's default is to fall back to an `O_CREAT|O_EXCL` soft
  lock that *does* go stale. We turn that off (`fallback_to_soft=False`) and degrade to "no ownership check, and we say
  so", rather than inherit a stale-lock problem D3 explicitly refuses (`§B.2`).
- **Real, and accepted:** one more package on the supply-chain surface. Mitigated by zero transitive deps (nothing
  arrives behind it), a pure-python wheel (nothing is compiled at install time), and a maintainer whose other packages we
  already depend on through `uv`.

## §F ADR-0242 §4, and the new ADR

### F.1 ADR-0242 §4 must be amended — but not reversed

§4's last bullet is **"No rewrite-on-open"**, justified like this:

> Here a reader — a second terminal running `--continue`, or `/resume` — can see another writer's line mid-write;
> rewriting would publish a file without that line, and the writer's completed append would then land in the replaced
> inode and be lost.

Half of that premise changes. After this lane, an opener that takes the write lock is the file's **only** writer, so a
rewrite by that opener could not race anyone. The other half does not change at all: a **read-only** opener holds no
lock, the owner keeps appending underneath it, and a rewrite by the reader would destroy exactly the line described.
And on a no-`flock` filesystem (`§B.2`) there is no ownership at all.

So: **the decision stands, the reason is rewritten.** §4 gains a dated amendment — "not impossible any more, still not
done, and here is which opener could and which still could not" — and the "Not done here" bullet
*"A cross-process single writer (#137)"* is struck with a pointer to ADR-0244. ADR-0242 stays `Accepted`; it is not
superseded, because nothing it decided is reversed (`docs/00-conventions.md`: supersede on replacement, amend on
refinement).

Turning rewrite-on-open *on* is explicitly out of scope: it is a destructive operation, ADR-0208's non-destructive
recovery is a separate accepted decision, and nothing measured here asks for it.

### F.2 This lane needs its own ADR — **0244** (next free; index checked)

Four things in it are decisions of record, not implementation detail:

1. **A runtime dependency added to a shipped package** — the licence, the closure, and why `portalocker` and a
   hand-rolled lock both lost (§E, D3).
2. **A user-visible contract**: a second terminal is asked, not refused and not silently forked; a non-interactive one is
   refused (D1, §D.1). This is a deliberate divergence from pi, whose experimental track refuses outright — recordable
   under ADR-0235, which says divergences are recorded, not argued.
3. **A `SessionErrorCode` widening** (`"read_only"`), which ADR-0035 requires the owning ADR to carry.
4. **The scope line**: the two POSIX-only `fcntl` sites of ADR-0091 / #46 are *not* migrated here, so the repo knowingly
   holds two locking idioms until they are.

It also carries the `ReadWriteLock` correction from §B.3 so the next reader does not re-derive it from the decisions doc.

Proposed title: `0244-a-session-file-has-one-live-writer-and-the-second-terminal-is-asked.md`.

## §H Falsified — do not believe these again

- **"`filelock.ReadWriteLock` is an OS lock and serves the read-only option."** It is SQLite-backed in 4.0.1
  (`_read_write.py:6,247-249`) and is `None` without `sqlite3` (`__init__.py:28-36`) — and in any case a reader/writer
  lock excludes the owner, which is the one thing the read-only option must not do. Read-only takes **no** lock (§B.3).
- **"`filelock` on POSIX always uses `flock`."** It silently degrades to a stale-able `SoftFileLock` on a filesystem that
  answers `ENOSYS`, unless `fallback_to_soft=False` (`_unix.py:118-135`).
- **"Locking the `.jsonl` itself is fine."** On Windows `LockFileEx` is mandatory; a reader of byte 0 would fail there
  and nowhere else. Sidecar (§B.2).
- **"#297 is a 512-vs-larger-constant problem."** Raising the constant moves the cliff; reading the line removes it.
  `load_jsonl_session_metadata` has never had a cap, which is why the two readers of the same line disagreed at all.
- **"`entry_id=None` can just be made to mean 'empty'."** Six call sites — five tests and `294-measure.py` — depend on it
  meaning "the whole session". The ambiguity needs a second value, not a redefinition (§B.6).
