## #115 — the knowledge channel is not wired

### Verified at `b24a406`

| Claim | Verdict |
|---|---|
| `format_skill_invocation` has **0 production callers** | ✅ `harness/skills.py:16` (docstring), `:99` (def), `:547` (`__all__`), then tests only |
| `load_prompt_templates` has **0 production callers** | ✅ own module + two *docstring mentions* in `harness/core.py:701` and `:1071`, then tests only |
| No packaged skills directory ships | ✅ `find packages -type d -name skills` → nothing |

So both carriers load, are visible to humans (`/skills`, the status panel count,
the RPC list), and **never reach the model**. This is a different layer from #84:
#84 is a toggle with no consumer, this is the mechanism itself.

### The measurement that already exists — do not redo it, but do repeat its shape

A previous session proved with a **ZORBLAX control experiment** that the skill
content never reaches the model — the model was not ignoring it, it was never
sent. Keep that discipline for the fix: an injection that "works" because the
model guessed is indistinguishable from one that works because the text arrived,
unless you use a token the model cannot produce on its own.

### Decisions the fix has to make

1. **Wire `format_skill_invocation` into the append-chunk assembly** (`entry.py`,
   around `_resolve_append_chunks`). pi's shape is progressive disclosure: inject
   **name + description + absolute path only**, plus "read it with the read tool
   if the task matches". Do not inject bodies.
2. **`load_prompt_templates` is a fork in the road**: wire it, or delete it and
   say so. It has been dead since it landed. Leaving a third carrier half-alive
   is how this issue happened.
3. **`enable_skill_commands`** currently advertises a feature that does not
   exist. Once the channel is live, either make the toggle do something or soften
   the copy per #84. It is a derived defect, not an independent one.
4. **A fresh install has no skills at all** — `_resolve_skill_dirs` scans only
   `~/.aelix/agent/skills` and `<cwd>/.aelix/skills`. Wiring the channel on an
   empty tree delivers nothing to a new user. Decide whether the package ships a
   starter skill, and note that #101's whole design assumes it can.

### Regression test that would actually bite

One skill on disk → assert its **name, description and absolute path** appear in
the real system prompt string. Not "the loader found it", not "the count is 1" —
those already pass today, against a build that sends nothing.

## #155 — `--tools` is unvalidated, and the natural spelling is wrong

### Reproduced live at `b24a406`, at the line numbers the issue cites

```
$ aelix --print --model claude-haiku-4-5 --provider anthropic --tools Bash,Frobnicate "hi"
  File ".../cli/entry.py", line 2203, in _harness_factory
    harness = AgentHarness(opts)
  File ".../harness/core.py", line 3581, in _action_set_active_tools
    raise AgentHarnessError(
aelix_agent_core.harness.core.AgentHarnessError: set_active_tools: unknown tool name(s): ['Bash', 'Frobnicate']
EXIT=1
```

### Measured facts to build on

- The **seven** valid names are `bash, edit, find, grep, ls, read, write` — all
  lowercase. `"Bash" in ALL_TOOL_NAMES` is **False**; `"bash"` is True. So the
  most natural spelling of the best-known tool is a fatal typo.
- `--help` says only `--tools, -t <csv>  Restrict tools to this comma-separated
  list` (`cli/args.py:702`). It names no valid value.
- **`--list-tools` does not exist** — grep returns nothing.
- The TUI path already degrades correctly (`✖ agents use failed: …`), so this is
  a missing catch at one boundary, not a missing message.

### Scope

Catch `AgentHarnessError` around the `AgentHarness(opts)` build in
`_harness_factory` and print what the TUI prints, *listing the seven registered
names* — the message is only actionable if it names them. Then validate a
profile's `tools:` at load so `/agents list` can flag it (the same annotate-in-
place surface #152 just added a column to), because a bad profile crashes **every**
launch until the file is edited.

## #156 — a mixed-reason provider blames the build

### Status: latent, and that is a scoping fact, not an excuse

No provider in the bundled catalog is mixed — all six blocked providers are
unanimous in their reason. Reaching it needs an **extension-registered provider**
(#77) or a hand-written `models.json`. Budget the repro harness as part of the
work, not as a prerequisite someone else supplies.

### Caller inventory at `b24a406`

`is_recoverable_block` is consumed at `core/runnable_models.py:444`, `:484` and
`tui/scoped_models.py:283`. The wording defect lives where a **mixed** set falls
into the all-dead-end branch because the predicate is all-or-nothing.

### The verdict is right; only the wording is wrong

"unusable" is correct for a provider with at least one model no configuration can
rescue — that was an explicit #151 decision and must not be reversed. The fix
names the dead-end **subset** instead of condemning the provider.

### Two traps this specific change walks into

1. **It changes a tuple shape** (`recoverable: bool` → a 3-state verdict) and the
   tests that read `entry[2]`. In #151 exactly that widening shipped three pyright
   errors through a green suite and correct live captures, because tuples are
   structurally typed at runtime. **The type gate is now in CI** (ADR-0213), so it
   will be caught — but run `python scripts/check_types.py` locally before pushing
   rather than discovering it there.
2. `is_recoverable_block` already documents that the old `BLOCKED_MIXED` sentinel
   "has no reasons" and must not drive user-facing wording. This issue is the last
   caller that effectively still does. Read that docstring before designing the
   third state — it was wrong once already and the correction is recorded there.

## Traps from the session that produced this handoff

These are not general advice; each one cost real time in the last three issues.

1. **Verify the fixture bites before trusting a green test.** `is_runnable`
   returns **True** when no provider is registered — the deliberate "adapters not
   wired, so do not filter" degrade. A #152 test that skipped registration passed
   against the *broken* build. Assert the precondition inside the fixture.
2. **Anything process-global must be restored in place.** A #152 fixture wrote to
   `aelix_ai.api_registry._PROVIDERS` and did not restore it: **21 unrelated tests
   went red**. Other modules hold a reference to that same dict, so `clear()` +
   `update(saved)`, not rebinding.
3. **Prove a check fails when it should.** A first-cut "the spike still errors"
   check passed against a spike with all three of its assertions deleted, because
   two unrelated errors remained. Delete the thing the check guards and watch it
   go red before believing it.
4. **CI catches what the local suite cannot.** A py3.11-only failure reproduced
   across two CI runs of the same commit and reproduced by *no* local run —
   including the identical `uv sync --all-packages --python 3.11` + `pytest -q`
   invocation. It was a test that waited for one signal and asserted a different
   one. Wait for the thing you assert on.
5. **Live-verify any TUI path.** `/agents use` was fixed and unit-tested, and the
   thing that actually confirmed it was a tmux session against the real binary:
   "Agent profile: badmodel" 0 times, "No provider registered" 0 times.
6. **A kernel edit needs an ADR and an allowlist entry.** The band rule asks one
   question — *did delegation create this requirement?* A repo-wide concern is a
   legitimate reason; write it down in `_KERNEL_CHANGE_ALLOWLIST` with the ADR.
