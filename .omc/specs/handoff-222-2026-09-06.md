## 1. 이번에 한 것

1. **#229** — `_await_zombie`의 win32 폴백을 `OpenProcess(SYNCHRONIZE)`+`WaitForSingleObject`로. 레인이 잡은 것: darwin도 그 폴백을 탄다(CPython에 `os.waitid` 없음) → macOS는 sleep 유지(CI 레그 아님). pyright는 `tests/`를 include하지 않아 이 파일의 win32 타입 오류를 어차피 못 잡는다.
2. **#224** — `aelix-server`를 루트 dev 그룹에(옵션 a). `uv.lock` 두 줄만. 빌드된 wheel의 `Requires-Dist` 불변(실측), plain `uv sync` 뒤 `--all-packages`는 no-op(freeze 바이트 동일). `AGENTS.md` §4 문장을 main 체크아웃에서 고침(untracked라 커밋 불가).
3. **#222** — 설계 rev 2의 결정: 두 사이트 `containment_spawn_kwargs(new_session=True)` + 첫 `await` 전 attach + `kill_on_close=False`; bash 레그 셋 각각 `_end_the_tree` 한 번(`REAP_GRACE` / `INTERRUPT_REAP`); drain을 `to_thread(read)`에서 `_PipeReader(on_chunk, on_eof)` 데몬 리더로(콜백이면 retain 안 함; 청크와 EOF가 같은 `loop._ready` FIFO → 반환 전 전부 전달); kill 경로 drain은 `run_contained`의 규칙(idle 0.1 s 재무장, cap 1.0 s); 성공 경로는 EOF까지(그대로, #232); 정리 순서 watcher → drain → detach(자기 `finally`) → close(최외곽); `stdin=DEVNULL`; 셤 삭제; `_kill_group` 삭제.
4. **라이브** — 규칙 9(tmux TUI): `main`에서 `!python3 -c "…stdin.readline()"`이 TUI를 멈추고 **내가 TUI에 친 키(`'secret\rmore\n'`)를 자식이 찍었다**; 브랜치에서는 즉시 `''`. 규칙 10(haiku, print, yolo, 스크래치 cwd): `setsid` 홀더 프롬프트 **64.3 s → 5.2 s**(2 s 타임아웃), 파이프라인·exit-0 불변.
5. **리뷰가 잡은 회귀(F1)** — 첫 구현은 watcher `finally`가 drain 바깥이라 성공 명령의 exit-path drain 중 abort가 헬퍼를 죽이고 `exit 0`을 "Command aborted"로 보고(측정: main 20.02 s 헬퍼 생존 vs 브랜치 1.01 s 헬퍼 사망). 순서 바꾸고 케이스 핀(RED→GREEN 증명).

## 3. 이 레포에서 이번에 물린 것

1. **`start_new_session=True` 자식은 tty를 읽어도 멈추지 않는다** — controlling terminal이 없어 커널의 background-group 검사가 아예 안 걸린다(`Ss`). #221 §3-1·#226의 SIGTTIN 정지는 `process_group=0`(같은 세션) 얘기다. 대신 TUI와 키 입력을 **경쟁**하고 `tcsetattr`로 터미널을 바꾼다 — 보이지 않아서 더 나쁘다. 실제 TUI에서 재현(§1-4).
2. **`loop.call_soon_threadsafe(on_data, chunk)` + 폴링한 `reader.eof`는 꼬리 청크를 잃는다**(0.3–6 %/run, 네 하네스가 독립 측정). `_run_once`가 `ntodo = len(self._ready)`를 스냅샷하므로 폴이 `eof`를 본 뒤 큐에 든 콜백은 다음 반복에 돈다. 답은 EOF를 **같은 FIFO**로 보내는 것(`on_eof` → `call_soon_threadsafe(event.set)`), 0/4000. 단, *await하는* 폴은 자기도 같은 FIFO 뒤에 서므로 안 잃는다 — 변이 (l)이 초록으로 남은 이유, docstring에 적음.
3. **버려진 `asyncio.to_thread(read)`는 인터프리터 종료를 막는다** — 기본 executor 스레드는 non-daemon, `THREAD_JOIN_TIMEOUT = 300` 뒤 무한 join. "tool call이 멈춘다"가 "Aelix가 못 끝난다"가 된다. 데몬 `_PipeReader`가 답.
4. **`_end_the_tree`를 루프 스레드에서 불러도 된다** — POSIX 1.6 ms(측정, 하트비트 최대 12 ms = sleep 양자), win32 `taskkill`은 `main`도 루프에서 돌리던 것. `to_thread` 처방은 #220 리뷰 2라운드에서 이미 기각(unshielded suspension point). 비판 4개 렌즈가 같은 주장을 했고 반박자가 전부 측정으로 뒤집었다.
5. **bpo-38630의 poll은 `_wait` 워커가 `_waitpid_lock`을 쥔 동안 아무것도 reap하지 않는다**(0/50) — 벨트가 안전한 이유는 "이 pid를 다른 누구도 reap하지 않고 벨트는 어떤 reap보다 먼저 나간다"(150/150)이지 poll이 아니다. docstring을 그렇게 고쳤다.
6. **watcher `finally`는 drain 안쪽에 있어야 한다** — 바깥이면 성공 명령의 exit-path drain 중 abort가 `kill_on_close=False`가 지키려는 헬퍼를 죽인다(F1). `main`의 순서(`await drain_task` 전에 watcher 취소)가 맞았다.
7. **pwsh는 러너에서 0.5–0.57 s에 뜬다** — 0.5 s 예산의 케이스는 "root가 트리를 announce하지 못했다"로 빨개진다. 슬로 셸 래퍼(`sleep 0.5; exec bash "$@"`, `SHELL=`)로 darwin에서 재현·검증할 수 있다.
8. **`stderr=STDOUT`이면 헬퍼의 fd 2가 그 파이프다** — "stdout만 DEVNULL"인 백그라운드 헬퍼는 여전히 파이프를 쥔다(20 s 대기 실측). 세 stdio 전부 DEVNULL.
9. **`_PipeReader`에 콜백을 주면 `chunks`에 append하지 말 것** — 안 그러면 모든 바이트를 두 번 쥔다(200 MB 출력에서 RSS 285 → 535 MB).
10. **attach 창 안에서 죽는 자식은 announce를 못 한다** — 케이스 12(attach 벨트)를 registrar로 등록하려 하면 5.05 s를 헛되이 기다린다. 짧은 sleep + `DEADLINE`의 3배로 충분.
11. **워크플로우가 세션 리밋에 걸리면 완료된 단계는 캐시된다** — `resumeFromRunId`로 재개하면 5개 비판이 재실행 없이 살아나고 죽은 32 반박만 다시 돈다. 리밋 해제 후 바로 재개.
12. **`gh api …/jobs/<id>/logs` + `grep UserWarning`** 이 windows 숫자를 받는 가장 싼 길 — `-q` 로그에도 `warnings.warn`은 남는다(#220 메모리 그대로 유효).
13. **`gh project item-edit`로 보드를 옮길 수 있다** — Status 필드 `PVTSSF_lAHOA-ATMs4BbL-wzhV-Tlw`, In progress `47fc9ee4`, Done `98236657`(닫으면 자동). 프로젝트 id `PVT_kwHOA-ATMs4BbL-w`.
14. **`darwin`에는 `os.waitid`가 없다** — win32 전용이라 믿었던 sleep 폴백을 오너의 박스도 탄다.
15. **Workflow 규모(이번 세션)**: 설계 비판 38 agent·2.05 M·19 min(리밋 전 1.59 M 별도 소모), 구현 5·0.91 M·67 min, 병합 전 리뷰 18·1.91 M·37 min, 수정 3·0.32 M·37 min. 전부 opus. BLOCKING은 이번에도 반박 레인을 통과한 것만 진짜였다(비판 32건 중 F-급 1건이 리뷰에서 나왔다).

## 4. 반증된 것 — 다시 믿지 말 것

- ❌ "`start_new_session=True` 자식이 tty를 읽으면 SIGTTIN으로 정지한다"(rev 1) — 정지하지 않는다; 키 입력을 훔친다(§3-1).
- ❌ "drain bound는 #222 범위 밖(SCOPE-4)" — ADR-0238이 #222에 배정한 것은 *hang*이다; bound 없이는 오너 플랫폼에서 #222가 아무것도 안 바꾼다.
- ❌ "`_end_the_tree`를 루프에서 부르면 5 s 멈춘다"(POSIX-2/WIN32-7/SCOPE-3/TESTS-8) — 1.6 ms. 프로브가 kill을 아예 안 부른 것.
- ❌ "attach 창은 `Popen`이 asyncio보다 훨씬 좁다"(rev 1의 I.1 근거) — 0.99 vs 1.29 ms, 둘 다 자식 첫 명령 8 ms 전. 살아남은 이유는 win32 proactor 창(미측정)뿐.
- ❌ "zombie-leader 테스트의 트리 쌍둥이가 필요하다"(rev 1 C.1) — `test_a_descendant_whose_parent_already_exited_still_dies`가 이미 그 핀; 델타는 inert.
- ❌ "`asyncio.subprocess.Process.wait()`의 2 s 세금을 `returncode` 가드로 뺀다"(ASYNC-2) — no-op(3.00 s 그대로); `run_cancellable`엔 `setsid` 홀더가 생길 수 없다.
- ❌ "`ProcessTree.attach`엔 `platform=` seam이 없어 C.4가 구현 불가"(TESTS-5) — 있다(`:562-586`).
- ❌ "케이스 C.2-1은 POSIX에서 아무것도 못 가른다"(TESTS-3) — `main`에선 초록이지만 변이 (a)에서 빨갛다; 가르는 건 변이다.
- ❌ "두 번째 Esc가 `tree.close()`를 건너뛴다"(POSIX-6) — 최외곽 `finally`는 2×·3× 취소에서도 돌았다; 건너뛰는 건 `detach`(ASYNC-4)였다.
- ❌ "셤의 importer는 둘"(첫 CHANGELOG) — 셋(`test_process_tree_win32.py`).
- ❌ "`ROOT_THAT_BACKGROUNDS_A_HELPER`로 F1을 잴 수 있다"(리뷰 지시) — 헬퍼가 all-DEVNULL이라 drain 창이 ~1 ms; 파이프를 2 s 쥐는 `tail` 자식이 따로 필요했다.
- ❌ "TUI의 `!command`는 `process_group=0`이라 tty를 지킨다"(ADR-0238 :212의 옛 문장) — 그건 `models.json`의 `!command`; TUI의 `!command`는 이 `exec`이고 `main`부터 `setsid`였다.
- ❌ "이 드라이버의 stdin 케이스가 `DEVNULL`을 가른다" — 백그라운드 명령의 stdin이 `/dev/null`이라 `main`도 `''`; 가르는 건 TUI(규칙 9)뿐.
