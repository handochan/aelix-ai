## 1. 이번에 한 것

1. **`print_channel.py`** — 스폰이 `containment_spawn_kwargs(new_session=True)` + 첫 `await` 전 `ProcessTree.attach(kill_on_close=True, handle=_retained_handle)`; tree는 row에(`RunningChild.tree`, `tree_owned`). attach 실패는 스폰의 `except` 밖에서 자체 `try`로 degrade(`tree=None` + warning 로그) — 스폰 `except` 안에 두면 살아 있는 자식이 reaper 없이 버려진다(R3). `run()`의 `finally`가 close의 단일 소유자: reaper가 아직 grace 안이면 done-callback으로 미루고, close와 같은 문장에서 `row.tree = None`(나중의 `abort_child`가 무장 해제된 tree로 가지 않게). `_drain_after_exit`는 win32에서만 tree(`TerminateJobObject`가 실질; 루트가 죽어 `taskkill /T`는 기여 없음). `_eager_abort`는 `kill_tree(tree=)` + **취소 경로의 Q1**(`kill_group_if_live`, reaper task가 없거나 끝났을 때만).
2. **`reaper.py`** — `reap(..., tree=)`, `kill_tree(..., tree=)`, `_is_win32()`, `_usable(tree)`(= `tree is not None and not tree.closed`, `closed`는 attribute로 읽음). win32+usable: leg 1 `soft_kill()`(refused면 grace 건너뜀; `eager_kill`이면 안 보냄 — Q4 hard only), escalation `hard_kill()`만(walk·`_signal_child` 안 돌림 — `TerminateProcess`가 job과 exit status를 두고 경쟁). POSIX: 그대로 + **Q1** = `reap()`의 escalation에서 walk 뒤 `tree.hard_kill()`(`killpg`). `kill_tree` 안에는 절대 아님(다른 두 호출자는 이미 reap된 자식을 든다 — `close()` revision 1의 해악 재현). 새 공개 `kill_group_if_live(proc, tree)`.
3. **`print_mode.py`** — win32 `SIGBREAK` 핸들러(`signal.signal`, `(sig, frame)` 그대로 전달, `previous is not None`으로 복원) + **`sys.exit`를 태스크 안에서 부르지 않는다**: `_signal_cleanup_and_exit`가 `holder["code"] = 128 + sig`를 **dispose 전에** 기록하고 `run_print_mode`가 그 값을 반환(step 7의 `exit_code = 1` 덮어씀). 라이브 실측 main: exit 1 + 트레이스백 2개 → 이번: **143**, stderr "Request aborted"뿐.
4. **`rpc_client.py`** `tree` 프로퍼티; **`rpc_channel.py`** `row.tree = client.tree`, `tree_owned=False`(client가 소유·close), `_reap`/`_eager_abort`/`abort_child` 전부 `row.tree`.
5. **`_process_tree.py`** `closed` 공개 프로퍼티 + docstring(`kill_on_close` 사이트 목록에 print 자식, `_taskkill_tree`의 호출자 열거 정정, finalize가 kill_on_close tree에선 kill임).
6. **테스트** — `tests/agents_ext/test_reaper_tree_win32.py`(디스패치 8건, `_Wedged` waiter — `_Live`는 즉시 resolve해 escalation에 못 닿음), `test_print_channel_spawn.py`(+1000줄: 스폰 kwargs/attach 핀 두 개의 가짜, kill_on_close 사이트 핀, contained 핀, escalation 쌍 — `escalation_reachable` 3사이트 철회, 인스턴스 스파이 `hard_kill` 1회, 비-setsid 손자 스텁, close 순서 테스트, 실제 print 자식 143/149 테스트 with `warnings.warn`), `tests/cli/test_print_mode_signal_handlers.py`, `tests/print_mode_child.py`(json 계약 테스트의 `_CHILD`를 공유 헬퍼로), `test_rpc_channel.py`(+6, `reaper._is_win32` 주입).

## 3. 이 레포에서 이번에 물린 것

1. **태스크 안의 `sys.exit`는 exit code를 잃는다.** `SystemExit`가 루프 밖으로 새면 `asyncio.run`의 `Runner.close()`가 `RuntimeError: Event loop stopped before Future completed`로 덮어쓰고 `main_sync`가 그걸 re-raise → exit 1. Node의 `process.exit(143)`을 그대로 옮기면 안 된다. 그리고 dispose가 `prompt()`를 풀어 주므로 **코드를 dispose 전에 기록**해야 한다(스펙 rev 2의 순서는 rc=1로 실측 반증).
2. **`narrow_tools`는 위임 자식의 grant에서 확장 툴 이름을 버린다**(설계). 라이브 체크의 손자는 모델이 부르는 툴로 못 만들고 로드 시점 hook으로 만들어야 한다. 그리고 **yolo 자식에게 체크아웃을 cwd로 주지 말 것** — 첫 시도에서 모델이 툴을 찾다가 `.aelix/extensions/spawn_sleeper.py`를 레포 안에 써 버렸다(지움). 스크래치 cwd + `.env` 키를 환경으로.
3. **`monkeypatch.setattr(reaper.sys, "platform", "win32")`는 프로세스 전역이다**(`reaper.sys is sys`). 그 아래에서 실제 스폰은 `creationflags=`로 죽고 `ProcessTree.attach`는 `_KernelApi()`에서 `AttributeError: ctypes.WinDLL`. 실제 프로세스 근처에서는 `reaper._is_win32`를 주입하거나 기록 스텁을 쓴다.
4. **`check_citations.py --fix`는 텍스트가 바뀐("stuck") 앵커도 lock에 박는다** — 그 뒤 `--check`는 틀린 번호 위에서 초록. 5단계: `--check`로 "EDITED, not moved" 기록 → `--fix` → 못 옮긴 것 손으로 재유도 → `--lock` → `--check` + 대상 열어 읽기. 게이트 픽스처가 살아 있는 파일을 인용하는 테스트(`test_a_continuation_does_not_steal_a_file_named_after_it`)는 `--fix`가 픽스처만 옮기고 단언은 안 옮겨 빨개진다 — 상수 한 쌍으로 보간해 고쳤다.
5. **fresh worktree의 `uv sync`는 `aelix-server`를 안 깐다**(#224). 전체 스위트는 `uv sync --all-packages` 뒤에.
6. **Q1은 `reap()`과 `_eager_abort`(취소 경로)에만** — `kill_tree`에는 절대. `_drain_after_exit`(성공 경로, 이미 reap된 자식)와 drain 안에서 취소된 `_eager_abort`가 `kill_tree`를 부르기 때문. 취소 경로는 reaper가 없어 main에서 실측으로 새고 있었다(§5).
7. **Windows에서 exit 1은 판별력이 없다**(#202 §3-12 재확인) — `hard_kill` 인스턴스 스파이가 실질 단언, exit code는 보강. 실제 print 자식은 이제 149를 내야 한다(windows 레그가 측정).
8. **`_Live` 스텁(`wait()` 즉시 반환)은 escalation을 못 몬다** — grace 안에서 resolve. wedged waiter가 필요하고, 판별은 `reap`의 elapsed가 아니라 스텁 안 타임스탬프.
9. **`while True` 스텁은 고아를 남긴다** — 이전 세션의 stub 4개가 49분 살아 있었다. 모든 스텁 루프를 `range(2400)`으로 bound.
10. **Workflow 규모**: 설계 반박 55 agent·4.87M·41 min(79건, BLOCKING 24→13), 구현 6·1.12M·90 min, 구현 리뷰+수정 23·2.68M·119 min(32건, BLOCKING 9→7, 변이 34개 중 생존 6 → 전부 처분). BLOCKING은 이번에도 전부 opus 반박·변이 레인에서. 모델을 내려 쓰지 말 것.
11. **`ExtensionContext.exec`·`tools_manager._command_exists`는 격리 없는 `subprocess.run`**이라 자식 그룹에 남는 유일한 자손 모양 — Q1의 macOS 커버리지가 비어 있지 않은 이유이자 #221의 사이트.
12. **`runtime.stop()`이 반환한 뒤 `client.process`를 읽지 말 것.** rpc 채널의 `_shutdown → client.stop()`이 reaper의 반환과 경쟁해 `_proc`를 `None`으로 만든다 — windows py3.12에서 졌고 py3.11·POSIX에서는 이겼다(run 33940861199). stop 전에 `proc`를 잡아 두고 뒤에 `proc.returncode is not None`을 단언한다(`abort_child`는 reaper의 shielded `proc.wait()` 뒤에 반환하므로 경쟁 없음).
13. **windows 레그는 한 번에 한 결함만 보여 준다** — 이번엔 3 run(인용 lock → 경쟁 단언 → 초록)에 45분. push 전에 `check_citations.py --check`와 새 테스트를 5회 돌리는 것이 그 두 run을 아낀다.

## 4. 반증된 것 — 다시 믿지 말 것

- ❌ "실제 print 자식은 SIGTERM에 143으로 끝난다" — 1 + 트레이스백 2개였다(§1). 코드가 그렇게 *적혀* 있었을 뿐.
- ❌ "닫힌 tree가 reaper를 무한 대기시킨다"(W1/P2/R2, 6/6 반박) — `kill_on_close=True` tree는 닫히는 순간 이미 죽은 tree. 실제 잔여는 `contained=False, job=None` 폴백뿐 → `_usable`로 처리.
- ❌ "`kill_on_close=True`는 성공 경로에서 일부러 남긴 헬퍼를 죽이니 print 자식엔 쓰지 말라"(W3) — ADR-0238의 사이트별 규칙이고 rpc 자식이 이미 그렇게 나간다; print 자식은 두 기준(one child per task, pdeathsig)을 다 만족.
- ❌ "Q1의 macOS 커버리지는 비어 있다"(F4) — `extensions/api.py` exec, `tools_manager.py` 두 사이트 + 라이브 실측(§2/§3/§5).
- ❌ "walk 뒤 killpg는 ADR-0238의 '대체 아님' 조항을 뒤집는다"(F3) — 대체가 아니라 보충; rpc 사이트가 이미 walk→killpg 합성을 싣고 있다.
- ❌ "`await dispose()` 뒤에 코드를 기록"(스펙 rev 2 §B.3) — dispose가 `prompt()`를 풀어 `run_print_mode`가 먼저 반환. 기록이 먼저.
- ❌ "revision 1이 지목한 두 테스트 파일이 실제 자식을 띄운다" — 둘 다 인프로세스. 실제 자식은 `test_print_mode_json_contract.py`의 `_CHILD`뿐 → 공유 헬퍼로 승격.
- ❌ "Q1은 `reap()` 안에만"(스펙 rev 2 §A.2) — 취소 경로(reaper 없음)가 macOS에서 실측으로 샜다. `kill_group_if_live`.
- ❌ "`stop_all`이 tree를 belt로 닫으면 안전"(rev 1) — rpc row의 빌린 tree를 `RpcClient.stop()`이 빚진 순서 앞에서 닫아 버린다. `stop_all`은 아무것도 닫지 않는다.
- ❌ "attach는 스폰의 `try` 안에"(rev 1) — 실패가 error 봉투로 삼켜지고 자식은 reaper 없이 산다. 자체 `try`, degrade.
