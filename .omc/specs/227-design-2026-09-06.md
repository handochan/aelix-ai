## §0 Baseline

`main` = `7fa6796`; `/tmp/wt-227` is at the same SHA, `.venv` Python 3.12.13
(darwin/arm64). `pytest tests/oauth/test_resolve_config.py
tests/tools/test_bash_shell_win32.py -q` → `66 passed, 4 warnings in 6.81s`.

**M1 — the bug, reproduced on darwin by taking `sh` away** (`PATH=/nonexistent`;
what a stock Windows box has): spawn raises `FileNotFoundError` in 1.17 ms →
uncached `None`, cached `CalledProcessError … died with <Signals.SIGHUP: 1>`,
`or_throw` `Failed to resolve provider api key from shell command: echo x`. The
symptom is not "no shell": it is a *resolution failure* that blames the user's
command, plus a cascade message that invents a signal (`-1` renders `SIGHUP`).

**M2 — a second bug the same platform makes reachable.** `resolve_config_value`
(cached, `auth.json`) trims with `rstrip("\n")`; `resolve_config_value_uncached`
trims with `.strip()`. Under a shell whose `echo` emits CRLF — cmd.exe and
PowerShell both do — `(0, 'sk-abc\r\n')` becomes cached `'sk-abc\r'` (a bare CR
inside an `Authorization` header) against uncached `'sk-abc'`.

## §A Decision

**A.1 On win32, `!command` runs through a resolved shell chain instead of the
hard-coded `sh`. POSIX is byte-identical to today (`sh -c`, one candidate, no
probing).** The first candidate that *spawns* wins. A candidate that is missing,
not executable, **or not a loadable program image** is skipped and the next is
tried — classified **by errno, not by exception class** (A.9). A malformed argv
(`ValueError`) and every other spawn error keep today's `None`; a spawn failure
is a verdict on that candidate only, and a chain where every candidate fails
still resolves to `None`, which is today's answer, not a new one.

**A.2 The chain (win32 only), best first:**

| # | candidate | invocation | why |
| - | --------- | ---------- | --- |
| 1 | `$SHELL`, only when it names an existing file | `[path, flag, cmd]` | the user's explicit choice, as the bash tool honours it |
| 2 | `sh` on `PATH` | `[path, "-c", cmd]` | **preserves today's behaviour on a Windows box that has an `sh` and no `$SHELL` set** (Git-for-Windows, MSYS2, Cygwin). A `!command` is written for `sh`; where an `sh` exists and the user has named no shell it keeps running under it — an existing `$SHELL` still wins at step 1 (narrowed 2026-09-07 by review DOC-3, which measured the un-narrowed absolute false) |
| 3 | `pwsh` | `[path, "-NoProfile", "-NonInteractive", "-Command", cmd]` | |
| 4 | `powershell` | same | |
| 5 | `%COMSPEC%` | a **raw command line**, `"<path>" /d /s /c "<cmd>"` (§G-1) | |
| 6 | `cmd.exe` | same | the floor: the chain always ends here, and it is the only candidate needing no PATH probe |

Steps 1 and 3–6 are `_resolve_shell_win32`'s chain unchanged (#104), so one
machine gets one shell answer for both the bash tool and `!command`. Step 2 is
the only difference and is deliberately **not** added to the bash tool: `sh` is
in `_CLASSIFIABLE_SHELLS`, so adding it there would flip AUTO mode on MSYS boxes
from "ASK everything" to "read it with the bash grammar" — an ADR-0237/#204
decision, not this issue's.

`-NoProfile` is correctness, not hygiene, and is measured (M5): a PowerShell
profile that writes to stdout is **prepended to the resolved API key**
(`profile-banner\nsk-KEY`).

**`-NonInteractive` is not about timing.** `stdin=DEVNULL` (#222, kept by A.5)
already ends a plain `Read-Host` — measured M8: 0.652 s without the flag against
a ~0.45 s no-prompt baseline; the 8.6 s hang one critique reported came from a
**pty** on stdin, which is neither this call site's shape nor the bash tool's
since #222. On win32 the same branch is taken, *reasoned not measured*: `nul` is
a char device `GetConsoleMode` rejects, so `Console.IsInputRedirected` is true,
`ConsoleHost` sets `ui.ReadFromStdin`, and `ReadLine` takes `ReadLineFromFile`,
which returns at the first EOF. What the flag buys is three things stdin cannot
reach, all from one guard (`HandleThrowOnReadAndPrompt`, ahead of every read and
write in `Prompt`, `ReadLine` and `ReadLineAsSecureString`): (1) **the prompt
text stays out of the key** — measured M9 end to end, `'give me a key: \nGOT:'`
without it against `'GOT:'` with it, the same pollution class as M5 and the one
half that *is* measured; (2) the **masked read** (`Read-Host -AsSecureString`,
`Get-Credential`'s console path — the shape a credential helper actually has)
opens `CONIN$` with `CreateFile` and calls `ReadConsole`, so `stdin=DEVNULL`
cannot end it and it costs the whole `_COMMAND_TIMEOUT`; (3) the prompt **write**
goes to `CONOUT$` through a handle opened by name so redirection cannot capture
it — unguarded, it paints into Aelix's own terminal. (2) and (3) are read from
PowerShell 7.6.5's ConsoleHost sources; nothing on win32 was measured, and
**Windows PowerShell 5.1 — the candidate a stock box actually lands on, since
`pwsh` exists only if the user installed PS7 — is a different implementation
nobody has run this against**; its `Get-Credential` takes a CredUI branch the
open-sourced snapshot shows is *not* behind the guard. So #226's win32 clause
narrows for PowerShell's OWN prompts only: a helper that opens the console
itself (git, ssh, gpg) is untouched.

`/d` is `-NoProfile`'s argument for cmd.exe's registry `AutoRun`; `/s` makes
cmd's quote-stripping deterministic. Both **reasoned from cmd.exe's documented
switches, not measured on win32.**

**A.3 The trim in `resolve_config_value` becomes `.strip()`** — Pi's `.trim()`,
and what its sibling resolver already does. This is a **cross-platform** change,
not a Windows one: `.strip()` also removes a leading newline and leading and
trailing spaces and tabs that `rstrip("\n")` kept, so an existing POSIX user's
cached value can change. Said that way in the CHANGELOG. `rstrip("\r\n")` is the
partial fix, pinned against in §C-11.

**A.4 Layering: the shell-resolution primitive moves DOWN into `aelix_ai`**
(`aelix_ai/utils/_shell.py`); `tools/bash.py` imports it. The dependency
direction is one-way (AGENTS.md §1) and this is the shape the repo already uses
for this exact problem: `containment_spawn_kwargs()` / `ProcessTree` live in
`aelix_ai/utils/_process_tree.py` and are consumed by both
`oauth/_resolve_config.py` and `tools/bash.py` (ADR-0238). Two things revision 1
got wrong:

- **`ShellConfig` moves too; there is no second dataclass.** A parallel
  `CommandShell` would have identical fields and compare unequal to it silently.
- **No compat re-export.** Measured: the naive re-export is 6× `F401` plus an
  `I001` under this repo's own ruff config, and `ruff check .` is a CI job.
  Moving `ShellConfig` as well makes every import that stays in `bash.py` a
  *used* one — measured `All checks passed!` (M12) — and the three in-tree
  consumers stop reaching a private name of another package through a re-export.

Ruled out: *an injection seam* (`set_command_shell_resolver()`) — a bare
`aelix_ai` consumer silently keeps the broken behaviour, two behaviours for one
function decided by import order; *a duplicated win32 chain inside
`_resolve_config.py`* — two chains agreeing by review, which this repo has been
bitten by (`fd` vs the walk arm claiming "same set", ADR-0193/#231, five rules
deep). The move obeys the existing direction rather than inventing a rule, so it
earns ADR **amendments**, not a new ADR (§D.4).

**A.5 Unchanged, on purpose:** `containment_spawn_kwargs()` *as a function*
(#202), the ~1 MB cap, the 10 s timeout, `stdin=subprocess.DEVNULL`, the #226
stop detector (inert on win32), the cache semantics, and every POSIX code path.
What changes at the spawn is one OR into `creationflags` (A.8).

**A.6 Corrections to the issue text, from Pi HEAD `da840b6`.** Pi's
`executeWithConfiguredShell` calls `getShellConfig()`, which on win32 resolves
**Git Bash → `bash.exe` on PATH → throw**; the throw falls to
`executeWithDefaultShell` = `execSync` = cmd.exe. `POWERSHELL_ARGS` belongs to
`getPowerShellConfig()`, which only the `powershell` *tool* uses — **Pi never
runs a `!command` under PowerShell.** Pi's real shape is "a POSIX shell if you
have one, else the native shell", which is what A.2 is; the divergence is that
Aelix reaches PowerShell before cmd.exe (its own #104 order) and hardens both.
**Pi's stdin transport (legacy WSL `bash -s`) is not adopted**: Aelix never
selects `C:\Windows\System32\bash.exe` unless the user exports it as `$SHELL`,
`stdin=DEVNULL` is load-bearing here (#222), and a WSL bash resolves a Linux
filesystem where a Windows credential helper is not (§G-6).

**A.7 The error message names the shell that actually ran.**
`resolve_config_value` rebuilds `["sh", "-c", cmd]` for its
`CalledProcessError`; after A.1 that is a lie on win32. The argv rides back on
the existing `_Failure` seat.

**A.8 The win32 child gets no console window.** Pi passes `windowsHide: true` at
exactly this spawn and Node's default is false, and CPython gives it for free
only for `shell=True` — the single `STARTF_USESHOWWINDOW`/`SW_HIDE` assignment
sits inside `_execute_child`'s `if shell:` branch (both M13). This site spawns a
list argv. Today the win32 spawn of `sh` fails before an image loads, so the
question has never arisen; after A.1 a console-subsystem shell is spawned, per
request (§G-3), and CreateProcess gives a console child a NEW console when the
parent has none — `pythonw`-shaped hosts are a shape this repo already defends
against (`util/stdio.py::harden_stream`, `aelix_agents/consent.py`). So
`CREATE_NO_WINDOW` is OR'd in **at this call site only**, not inside
`containment_spawn_kwargs()`: its other callers (`extensions/subprocess_hooks`,
`rpc/rpc_client`, `aelix_agents/reaper`) end their trees with
`ProcessTree.soft_kill()` → `ctrl_break()`, which that module's own comment says
"needs a shared console", so the flag there would silently demote three
teardowns to hard kills; this site's ladder is `tree.hard_kill()` only. Second
reason, in this repo's terms: a shared console is the shape ADR-0238 rejected on
POSIX, where a `setsid` helper was measured "eating the line the user had typed
at Aelix's own prompt — silent theft in place of a visible stop"; a helper
opening `CONIN$` on Aelix's console is that theft. The price is that a win32
console prompt becomes certainly unanswerable — what A.2's #226 clause already
says. Divergence: Pi hides its configured-shell spawn but not its `execSync`
fallback; Aelix hides every win32 candidate (stricter; ADR-0235 permits).
**What Windows does with the flag is reasoned, not measured.**

**A.9 The fall-through is by errno.** CPython maps a win32 spawn failure to an
errno through `PC/errmap.h` *before* `OSError`'s subclass table is consulted
(`oserror_parse_args` runs ahead of `OSError_new`'s `errnomap` lookup), and that
table has no `ENOEXEC` and no `EINVAL` entry (M10). So a `sh.cmd` / `pwsh.bat` /
non-PE `$SHELL` — `ERROR_BAD_EXE_FORMAT` 193, with 11 and 188..202 — arrives as
a **bare `OSError`**, as does every winerror falling to `errmap.h`'s
`default: return EINVAL`. Catching by class would abort the chain before the
`cmd.exe` floor and leave `!command` exactly as dead as #227 found it. The
allowlist is `{ENOENT, ENOTDIR, EACCES, EPERM, ENOEXEC, ELOOP, EINVAL}`;
`EMFILE`/`ENOMEM`/`EBADF` are process-resource failures the next candidate
cannot fix and keep today's `None` after one spawn. A **winerror** allowlist was
rejected: `exc.winerror` fails the host pyright leg (handoff §3-6 inverted),
while `exc.errno` is clean on both (M10).

## §B Code changes

**B.1 NEW `packages/aelix-ai/src/aelix_ai/utils/_shell.py`** — the primitive, a
private module like `_process_tree.py` whose names are public inside it. Moved
verbatim from `tools/bash.py`: `shell_basename`, `command_flag_for` (was
`_command_flag_for`), `ShellConfig` with its Pi-parity docstring, the three flag
constants (`POSIX_COMMAND_FLAG`, `CMD_COMMAND_FLAG`, `POWERSHELL_COMMAND_FLAG`)
and the two name sets (`POWERSHELL_NAMES`, `CMD_NAMES`). `_VERSION_SUFFIX_RE`
moves and **stays private** — measured, it has no consumer outside
`shell_basename`. `shell_basename` plus the two name sets are the family
accessor both consumers use; `command_flag_for` is that same answer projected
onto a flag. New:

```python
def windows_command_shells(
    env: Mapping[str, str], *, include_posix_sh: bool = False
) -> list[ShellConfig]:
    """Every Windows shell candidate, best first (§A.2). ``[0]`` is what
    ``_resolve_shell_win32`` has always returned; the list exists because a
    caller that SPAWNS can fall through a candidate a caller that only NAMES
    one cannot."""
    out: list[ShellConfig] = []
    if (shell := env.get("SHELL")) and Path(shell).exists():
        out.append(ShellConfig(shell, command_flag_for(shell)))
    path = env.get("PATH")            # NOT ``shutil.which(..., path=None)``:
    if path is not None:              # that reads the HOST's PATH, so a fixture
        if include_posix_sh and (found := shutil.which("sh", path=path)):
            out.append(ShellConfig(found, POSIX_COMMAND_FLAG))
        for exe in ("pwsh", "powershell"):
            if found := shutil.which(exe, path=path):
                out.append(ShellConfig(found, POWERSHELL_COMMAND_FLAG))
    if comspec := env.get("COMSPEC"):
        out.append(ShellConfig(comspec, command_flag_for(comspec)))
    out.append(ShellConfig("cmd.exe", CMD_COMMAND_FLAG))
    return out
```

The `path is not None` guard changes behaviour only for an env with **no** `PATH`
key: today `shutil.which(…, path=None)` reads the host's (measured — it finds
this darwin box's `/bin/sh`, so a fixture meant as "stock Windows" is silently
`sh`-present). In production `env` is `os.environ`, which always has one.

**B.2 `tools/bash.py`** — delete the moved names and **do not re-export them**.
`bash.py` imports the three it still uses, `from aelix_ai.utils._shell import
ShellConfig, command_flag_for, windows_command_shells` (isort places the block
after `_process_tree`), and **`import re` is deleted** — `_VERSION_SUFFIX_RE`
was its only use (measured; `shutil` and `sys` stay). Measured on the real file
with the repo's ruff: `All checks passed!`, 86 lines leave `bash.py` (M12).

    resolution shares it; ``include_posix_sh`` is False here because ``sh`` is
    classifiable and the gate's answer is ADR-0237's decision, not this one."""

`POWERSHELL_NAMES`, `shell_basename` — its docstring's old spellings update with

**B.3 `oauth/_resolve_config.py`** — `import errno` joins the import block.

- `_Failure` gains `argv: list[str] | str | None = None`; `_StoppedByTerminal`'s
  `cmd` annotation widens the same way (the detector is inert on win32, so it
  only ever sees a list, but pyright must still type the seat).
- New module-level, the first with a docstring carrying A.2's table and M5/M9:

```python
_POWERSHELL_HARDENING = ("-NoProfile", "-NonInteractive")
_CMD_HARDENING = ("/d", "/s")
CREATE_NO_WINDOW = 0x0800_0000   # a literal for the same reason
    # ``CREATE_NEW_PROCESS_GROUP`` is one: the name does not exist off Windows
    # (measured, ABSENT on darwin) and the win32 arm of these tests is read there.

#: Spawn failures meaning "this candidate is not a runnable shell" (§A.9).
_NOT_A_RUNNABLE_SHELL = frozenset({
    errno.ENOENT, errno.ENOTDIR, errno.EACCES, errno.EPERM,
    errno.ENOEXEC, errno.ELOOP, errno.EINVAL,
})

def _shell_argv(shell: ShellConfig, cmd: str) -> list[str] | str:
    """The family is the PRIMITIVE's answer; the hardening is THIS caller's policy.

    Classified with ``shell_basename`` against ``POWERSHELL_NAMES``/``CMD_NAMES``
    imported from ``aelix_ai.utils._shell`` — the same three ``dialect_for_shell``
    imports rather than a second table (#204). A literal set here would be that
    second copy and the drift is measured: ``{"pwsh","powershell"}`` against
    ``Path(p).stem.lower()`` diverges on 18 of 66 candidate paths — a ``$SHELL``
    of ``pwsh-7.5.0.exe`` would take ``-Command`` with NO ``-NoProfile`` (M5's
    banner inside the key) and ``command.com`` ``/d`` beside a POSIX ``-c``.
    Dispatching on ``shell.command_flag`` agrees on every candidate the primitive
    produces (300/300) but rests on an invariant ``ShellConfig`` does not enforce.

    The cmd family returns a RAW COMMAND LINE (§G-1): win32-only, so POSIX's "a
    ``str`` is the program name" is never reached, and CPython's win32
    ``_execute_child`` passes a ``str`` to CreateProcess verbatim.
    """
    # pwsh/powershell -> [path, *_POWERSHELL_HARDENING, flag, cmd]
    # cmd/command     -> f'"{shell.path}" /d /s /c "{cmd}"'   (path quoted: a
    #                    spaced %COMSPEC%/$SHELL breaks a bare f-string)
    # anything else   -> [path, flag, cmd]

def _shell_argv_candidates(
    cmd: str, *, platform: str | None = None, env: Mapping[str, str] | None = None
) -> list[list[str] | str]:
    if _resolve_platform(platform) != "win32":
        return [["sh", "-c", cmd]]          # POSIX: exactly today's argv
    return [_shell_argv(s, cmd) for s in windows_command_shells(
        os.environ if env is None else env, include_posix_sh=True)]

def _spawn_kwargs(platform: str | None = None) -> dict[str, Any]:
    kwargs = containment_spawn_kwargs(platform=platform)
    if _resolve_platform(platform) == "win32":
        kwargs["creationflags"] |= CREATE_NO_WINDOW      # 0x0800_0200
    return kwargs
```

`_POWERSHELL_HARDENING`/`_CMD_HARDENING` stay HERE and are deliberately not part
of the primitive: `tools/bash.py` runs the user's interactive shell and must keep
their PowerShell profile, while a `!command` must not (M5). The primitive owns
the family answer; each consumer owns its policy.

- `_run_shell_command(cmd, *, failure=None, platform=None, env=None)`: the single
  `Popen` becomes a loop. `platform`/`env` are resolution seams spelled like
  `_stopped_by_the_terminal`'s and read through the same `_resolve_platform`; the
  spawn calls `**_spawn_kwargs()` with **no** argument, because an injected
  `platform` must never reach a real POSIX spawn (measured: `Popen(creationflags=…)`
  raises `ValueError` there). `env` is a resolution seam only — it is not passed
  to `Popen`, so the child still inherits `os.environ`.

```python
    candidates = _shell_argv_candidates(cmd, platform=platform, env=env)
    if failure is not None:
        failure.argv = candidates[0]          # so a total failure still names one
    proc = None
    for argv in candidates:
        try:
            proc = cast("subprocess.Popen[bytes]", subprocess.Popen(argv, ...))  # kwargs otherwise unchanged
        except ValueError:
            return None                       # a malformed argv is not a shell answer
        except OSError as exc:
            if exc.errno in _NOT_A_RUNNABLE_SHELL:
                continue                      # not a runnable shell — next candidate
            return None                       # today's answer for every other error
        if failure is not None:
            failure.argv = argv
        break
    if proc is None:
        return None                           # nothing spawned — today's answer
```

  Classified by intent, not by class (§A.9). The CONSTRUCTOR raising means no
  command ran — POSIX reaps the failed fork inside `Popen.__init__`, win32's
  CreateProcess fails atomically — so falling through cannot double-run anything
  (measured: no strays on either arm). Everything after the spawn —
  `ProcessTree.attach`, the reader thread, the poll/stop/timeout/overflow ladder,
  the two bounded waits, `tree.close()` — is untouched.
- `resolve_config_value`: `argv = failure.argv or ["sh", "-c", cmd]`, and
  `out = result[1].strip()` (A.3).

**B.4 `utils/_process_tree.py`** — `containment_spawn_kwargs`'s closing docstring

## §G Risks, open questions, out of scope

1. **Two quoting conventions, one a deliberate divergence.** The pwsh candidate
   is correct as a list: on win32 the .NET host CRT-parses the command line back
   into argv before PowerShell's parser sees it, so `\"` is the escape Microsoft
   documents for `-Command` (measured on darwin — pwsh given the post-CRT string
   matches `sh -c` byte for byte; given the raw `\"` text it prints `\a b\`). The
   **cmd family is the real mismatch**: `cmd /?`'s rule 2 strips one leading and
   one trailing quote and cmd implements no `\"`, so a `list2cmdline` rendering
   hands the child literal backslash-quotes — hence the raw-string branch;
   reasoned from `cmd /?`, **not measured on win32**. Attribution corrected:
   CPython's win32 `shell=True` builds `%ComSpec% /c "<raw>"` (no `/d`, no
   `/s`); Node's shell spawn is the one documented `/d /s /c`. The cmd family is
   reached only when neither `sh`, `pwsh` nor `powershell` is on `PATH`, and the
   windows leg has Git's `sh.exe`, so case 1 never exercises it — 14 and 17 are
   the only guards.
2. **`shutil.which` searches the CWD first on win32, and across `PATHEXT`.** After
   #227 that resolver decides which program is handed the user's `op read`, with
   the agent's working directory — routinely a freshly cloned repository — ahead
   of `PATH`. Measured (M11): 3.12 prepends `os.curdir` unless
   `NoDefaultCurrentDirectoryInExePath` is set, and `which("sh")` expands across
   `.COM;.EXE;.BAT;.CMD;.VBS;.JS;.WS;.MSC`, never the bare name. The `PATHEXT`
   half is **defused by A.9**: CreateProcess refuses a `.BAT`/`.CMD`/`.VBS` with
   `ERROR_BAD_EXE_FORMAT` → `ENOEXEC` → next candidate, so such a file cannot run
   the command. A hostile `sh.exe`/`sh.com` in the CWD still would — the
   pre-existing `_resolve_shell` shape (#104), unchanged in kind but now reaching
   a credential path. Named, not closed; follow-up below.
   **OPEN QUESTION — only the owner can answer.** A `!command` was written for
   `sh`, because `sh` was hard-coded. On a stock box the chain now hands it to
   PowerShell, which can run it to a zero exit and a *wrong* value rather than
   fail — a POSIX `$VAR` expansion resolves to empty there, and the resolver
   takes whatever a zero-exit command printed. This design proceeds on "run it,
   and say in the guide and the CHANGELOG to write the command for the shell
   that will run it" (§D.1a, §D.5), because the alternative — stop the chain at
   `sh` and raise a named "no POSIX shell for this `!command`" — leaves the
   stock box exactly as broken as #227 found it, only with a better message. If
   the owner prefers the loud failure, the change is one branch in
   `_shell_argv_candidates` and cases 16/17 invert; nothing else moves.
3. **Cost.** `get_api_key_and_headers` is the harness's per-request callback and
   the registry path is deliberately uncached, so a Windows box that lands on
   PowerShell pays ~0.5 s **per model turn** (M6, pwsh 7.6.5 on darwin; 5.1 is
   typically slower). Not a regression — today that box pays nothing because
   nothing works — but a real product consequence.
4. **A refused prompt still exits 0, and the cached path caches the empty
   value.** Measured (M9): with `-NonInteractive` the prompt fails but the exit
   code follows the command's *last* statement, so rc was 0 with empty output.
   `_execute_command_uncached` ends `out or None`; `resolve_config_value` has no
   such check and caches `""` — an empty `Authorization` header that survives
   until invalidation. Not fixed here: that path's contract is *raise*, not
   `None`, so aligning them changes an exception contract. The user-facing text
   therefore promises "refused", never "a named error".
5. **Windows PowerShell 5.1 stdout encoding.** `_run_shell_command` decodes UTF-8
   with `errors="replace"`, safe while the only Windows shell was MSYS `sh`; 5.1's
   redirected stdout uses the console/OEM code page. Case 16 pins an ASCII `x`
   byte-for-byte; a non-ASCII key is unmeasured.
6. **Legacy WSL `bash -s` stdin transport** (Pi's `commandTransport`) is not
   adopted (A.6). A user exporting `$SHELL=C:\Windows\System32\bash.exe` gets
   `bash -c` and Pi's quoting hazard.
7. **`$BASH_ENV`** is the same pollution class as a PowerShell profile and is not
   closed here — but not for the reason first written. The counterpart flags do
   NOT close it: measured on bash 3.2.57, 4.4.20, 5.1.4, 5.2.21 and 5.2.37,
   `--noprofile --norc` still sources `$BASH_ENV` and still prepends its output
   to the resolved key; only `-p` stops it, and that drops the rest of the
   user's environment with it. It is reachable on ONE candidate only — a
   `$SHELL` that names a real `bash.exe`; the same binary invoked as `sh` reads
   neither `$BASH_ENV` nor `$ENV` when non-interactive (measured on 5.2.21).
   And the layering reason does not apply: `tools/bash.py` builds its own argv
   and never imports `_resolve_config`. Named in the guide, not fixed.
8. **`command_flag_for` answers `-c` for `command.com`** (only `.exe` is
   stripped), so a `%COMSPEC%` naming real MS-DOS `command.com` gets a flag it
   cannot take. Pre-existing (#104), neither introduced nor fixed here — named so
   the `cmd/command` row of `_shell_argv` is not read as covering it.
9. **`tools/bash.py`'s own spawn** catches `(FileNotFoundError,
   NotADirectoryError)` and lets a WinError 193 escape as an uncaught `OSError`
   instead of its exit-127 report — A.9's root cause at a different site,
   pre-existing on `main`, out of scope.
10. **Out of scope:** AUTO mode's dialect on Windows (ADR-0237/#204), the
    `!command` cache policy, #230/#232's drain rules, anything in `tools/bash.py`
    beyond the delegation.
