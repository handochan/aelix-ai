## 이 레포에서 실제로 물린 규칙

- **게이트 스크립트는 워크트리 자기 것으로 부른다.** `/tmp/wt-304`에서
  `uv run python /Users/handochan/dev/aelix-ai/scripts/check_citations.py --check`를 부르면
  **메인 체크아웃**을 검사한다(917 gated). `uv run python scripts/check_citations.py --check`는
  그 워크트리를 검사한다(923). 스크립트가 자기 위치에서 트리를 유도하기 때문이다.
  산문(AGENTS.md)은 절대경로, 게이트는 상대경로 — 방향이 반대다.
- **`--fix`를 돌리기 전에 대상 줄을 직접 읽는다**(#310). 이번 배치에서 네 번 rebase했고
  매번 `citations.lock.json`이 충돌했다. 푸는 순서는 (1) 충돌은 HEAD 쪽(=main)을 취하고,
  (2) `--check`가 부르는 drift/unlocked 목록의 **대상 줄을 sed로 직접 읽어** 인용문과
  맞는지 확인한 뒤, (3) `--fix`를 돌리고, (4) `git diff citations.lock.json`으로 바뀐 키가
  방금 확인한 것뿐인지 대조한다. `--check`가 green이라는 사실은 증거가 아니다.
- **CHANGELOG 충돌은 양쪽을 다 남긴다.** 두 브랜치가 똑같이 Unreleased 맨 위를 원한다.
  단순 병합이지만 자동으로는 안 된다.
- **CI는 lint → type gate → test가 한 잡의 연속 스텝이다.** lint가 죽으면 네 레그 전부
  테스트를 못 돌린다. `.omc/specs/`도 ruff 대상이다(`.gitignore:59`가 un-ignore한다).
  #303이 커밋한 프로브가 SIM105로 걸려 푸시 전에 잡혔다 — 구현자의 lint 증거가
  **자기 파일 두 개에만** 걸려 있었던 탓이다. 게이트는 항상 트리 전체에 돌린다.
- **배치 안에서 먼저 머지한 것이 뒤 것의 rebase를 만든다.** 네 이슈의 *소스* 파일은 안
  겹쳤는데도, 인용 게이트가 모든 레인을 서로의 파일로 끌고 들어와 매번 충돌했다.
  "파일이 안 겹치면 병렬"은 소스에만 해당한다.
- **서브에이전트는 TTY가 없다.** TUI 라이브 확인은 내가 pty 드라이버로 직접 했다.
  `.omc/specs/299-live-tui.py`는 `AELIX_299_SESSION_DIR`을 **고정해야** `--continue`가
  앞 실행을 이어받는다. 안 주면 매번 새 임시 디렉터리를 만들어서, replay가 실패한 것처럼
  보인다 — 실제로 그렇게 한 번 헛다리를 짚었다.

## 반증된 것 — 다시 믿지 말 것

- **"리뷰 한 번이면 충분하다"** — 아니다. 이번 배치는 4개 레인 전부에 구현 → 리뷰 →
  수정 → 재검증을 태웠고, **그러고도 Codex가 두 레인에서 실질을 더 찾았다.**
  #299에서는 커밋된 수정이 만든 회귀(`\n\n`으로 끝나는 출력의 본문 전체 유실)를,
  #301에서는 그 커밋이 **새로 만든 `failed_writes` 계약**이 코드보다 많은 것을 주장한다는
  것을 반례 둘로 짚었다. 어려운 작업에 Codex 교차 리뷰(CLAUDE.md 8)는 형식이 아니다.
- **"테스트가 빨개지는지 보면 그 테스트는 유효하다"** — 부족하다. #303의 orphan 단언은
  코루틴 이름 문자열에 의존해서, 감시 대상을 진짜로 깨뜨려도 **shell.py에서 이름만 바꾸면
  다시 green**이 됐다. #304의 빈 grant 강화는 `list(...) or None` 한 글자 되돌리기가
  **다른 5029개 테스트에 전혀 안 보였다.** "무엇이 이 단언을 조용히 무력화하는가"를
  따로 물어야 한다.
- **"상한을 걸었으니 bounded다"** — #299의 첫 커밋이 출력에 2000줄/50KB 상한을 걸고도
  (a) 정확히 상한인 입력은 공지 없이 51,201바이트가 통과했고, (b) **명령문 자체에는
  상한이 없어** 6만 바이트 모델 메시지가 만들어졌다. 그 브랜치가 ADR-0242에 직접 써 넣은
  "writer에서 bound된다"는 규칙을 그 브랜치가 안 지키고 있었다(`git log -S`로 확인).
- **"`git diff main..branch`에 있는 파일 = 브랜치가 건드린 파일"** — 아니다. main 쪽에만
  있는 변경도 거기 나온다. 네 브랜치 전부 `docs/decisions/0244-…md`를 건드린 것처럼
  보였는데, 실은 아무도 안 건드렸고 main에 내 ADR 커밋이 있었을 뿐이다.
  브랜치가 뭘 했는지 보려면 `git diff <브랜치의 base>..<브랜치>`다.
- **"실패한 CI 레그 = 내 변경의 문제"** — 이번 배치에서 Windows 실패가 넷 났는데
  **셋이 무관한 기존 flake**였다(#313 · #315, 그리고 #313의 재현). 하나만 진짜였고
  (#299의 `\r\n`), 그건 Codex가 CI보다 먼저 예측했다. 실패 테스트가 내 변경이 건드린
  표면인지부터 본다.

## 이 배치를 돌린 방식 (다음에 그대로 쓸 것)

worktree 4개 병렬, 레인마다 **구현 → 독립 리뷰 → 수정 → 독립 재검증**, 그 위에 Codex
교차 리뷰. 사람(=메인 루프)이 한 일은 셋뿐이다: 오너 결정 기록, **라이브 TUI 확인**
(서브에이전트는 TTY가 없다), 그리고 rebase·머지·이슈 발행.

값이 난 지점을 순서대로 적으면:

1. **리뷰어에게 "수정하지 말고 보고만 하라"고 못박은 것** — 네 레인 중 셋에서 블로커가
   나왔고, 그중 #303은 **푸시했으면 네 레그가 전부 lint에서 죽었을** 것이었다.
2. **리뷰어에게 "새 테스트를 수정 전 코드에서 빨갛게 만들어 보라"고 시킨 것** — 가장
   값이 큰 단일 검사였다. #304에서 7개, #301에서 12개가 실제로 빨개지는 것을 확인했고,
   반대로 **빨개지지 않는** 테스트(#304의 `has_ui` 양성 케이스)도 정직하게 보고됐다.
3. **Codex 교차 리뷰** — 위 네 패스를 전부 통과한 뒤에도 두 레인에서 실질을 찾았다.
   ("반증된 것" 첫 항목 참조.)
4. **이슈를 발행하며 범위를 지킨 것** — 8건을 새로 팠다. 한 레인이 "이것도 고칠까요"를
   물어올 때마다 `follow_ups`로 받아 이슈로 옮겼고, 커밋은 하나씩으로 유지했다.
