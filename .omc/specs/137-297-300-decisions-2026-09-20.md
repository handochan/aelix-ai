## 오너 결정

### D1 — 두 번째 터미널이 같은 세션을 열면: **물어보고 선택**

거부(pi·codex 방식)도, 조용한 자동 fork도 아니다. 선택지를 띄운다:
fork해서 계속 / 읽기 전용으로 열기 / 취소.

- fork: 전체 대화를 물려받은 **새 세션 파일**로 진행. 원본은 첫 터미널 소유로 남는다.
- 읽기 전용: 쓰기 락을 잡지 않고 본다 (`filelock.ReadWriteLock.acquire_read`).
- 미정: `-p` · `--mode json` · RPC 등 **비대화형 경로의 기본 동작**. 설계에서 정한다.

### D2 — 배치: **#137 + #297 + #300 한 레인**

핸드오프는 "#297은 #137과 파일이 겹치니 다른 배치"라고 적었다. **뒤집는다.**
이유는 파일 겹침이 아니라 **의미 의존**이다 — D1의 fork 경로가 #297·#300이 깨뜨리는
바로 그 경로를 밟는다.

- **#297**: 헤더가 512바이트를 넘으면 `--continue`가 fork본을 못 보고 원본을 이어 쓴다.
  → fork로 갈라 놓고 다음 `--continue`가 원본으로 돌아가면 D1이 무의미해진다.
- **#300**: 첫 사용자 메시지 앞에서 fork하면 세션 전체가 복사된다.
  → 자동/수동 fork 시점이 정확히 "열 때"라 이 지점을 밟는다.

구현 순서는 **#297 → #300 → #137**. 앞 둘이 fork를 정상화한 뒤 #137이 그 위에 얹힌다.

### D3 — 락: **`filelock` 의존성 추가** (`packages/aelix-agent-core`)

`portalocker`는 탈락 — Windows에서 `pywin32`(컴파일 대형 패키지) extra를 끌어들인다.

## D3 근거 (실측)

| | filelock 4.0.1 | portalocker 4.4.0 |
|---|---|---|
| 라이선스 | **MIT** (SPDX `MIT`, OSI classifier) | BSD-3-Clause |
| 런타임 의존성 | **0** | 0 (단 `win32` extra → `pywin32>=226`) |
| 배포물 | `py3-none-any`, 106 KB | `py3-none-any`, 130 KB |
| requires-python | `>=3.10` (우리 바닥 3.11 충족) | `>=3.10` |

소스를 직접 열어 확인한 것(`_unix.py` / `_windows.py`):

- `_unix.py` → `fcntl.flock(fd, LOCK_EX|LOCK_NB)`
- `_windows.py` → 진짜 Win32 **`LockFileEx`** (`msvcrt.locking`이 아니다), 1바이트 범위,
  `UnlockFileEx`, reparse point 거부까지.
- 둘 다 **OS 수준 락**이라 프로세스가 죽으면 **커널이 놓는다**
  → **stale 락 회수 로직이 필요 없다.**
- `ReadWriteLock.acquire_read/acquire_write` 제공 → D1의 "읽기 전용으로 열기"가 공유 락으로 성립.
- flock 없는 파일시스템(NFS 등)용 soft-lock 폴백 포함.

### 반증된 것 — 다시 믿지 말 것

- **"직접 구현하면 O_EXCL + pid + mtime 하트비트가 필요하다"** — 아니다. 그건 **pi의 우회**다.
  pi가 `proper-lockfile`로 `stale: 2_000` / `update: 1_000` 하트비트를 다는 이유는
  **Node에 OS 락 API가 없어서** `mkdir` + mtime으로 흉내 내기 때문이다. Python에는
  `fcntl.flock`과 `LockFileEx`가 있으므로 그 복잡도를 베낄 이유가 없다.
  (이 세션의 첫 권고가 이 오해 위에 있었다. 실측 후 뒤집었다.)
- **"pi가 이 문제를 안 고치기로 했다"** — 아니다. 아래 참조.

## pi 참조 (CLAUDE.md 11번)

로컬 체크아웃 `~/dev/pi`는 87커밋 뒤처져 있었다. `origin/main` 기준으로 읽었다.

- **mainline CLI에는 크로스 프로세스 잠금이 없다.** `jsonl/repo.ts:98`의
  `Session is already open`은 `openSessions` **Map** — 한 프로세스 안에서만 걸린다.
  즉 pi mainline도 #137과 같은 상태다.
- 잠금은 **experimental 트랙에만** 있다:
  - `experimental/session-worker.ts:533` — `lockfile.lock(metadata.path, {realpath:true,
    stale:2_000, update:1_000, retries:{…maxRetryTime:8_000}})` 세션 파일 소유권 락.
  - `experimental/micro/sessions.ts:44` — `retries:0`, 실패 즉시 `Micro session is already open`.
  - 방향은 **"세션 하나에 살아 있는 writer 하나"**, 두 번째는 **거부**. fork로 넘기지 않는다.
- pi 이슈 4건이 정확히 이 결함이고 **전부 신규 기여자 자동 close 봇에 닫혔다**
  (메인테이너 판단 아님):
  - **#9596** — `pi -c` 두 개가 한 파일에 섞임. 재현 스크립트 포함. 우리 #137과 같은 결함.
  - **#8848** — prior art로 **codex-rs `WriterLockCoordinator`**
    (`thread-store/src/local/writer_lock.rs`: per-thread OS 파일 락 `file.try_lock()` +
    부기용 coordination 락 + 크래시 시 stale 정리) 인용.
  - **#8177** — 설계 논의: 실패 / 읽기 전용 / 회수 가능한 lease 중 택일.
  - **#8334** — 테스트 붙은 브랜치 설계(`tcf909:fix/session-writer-ownership`):
    락 + **append 전 물리적 tail 검증** + 경쟁 프로세스 fail closed + 소유권 회수.
    즉 "락"과 "꼬리 재읽기"를 **같이** 쓴다.
