## 3. 이 레포에서 이번에 물린 것

1. 🔴 **리밋 셋이 다 물렸다** — 설계 워크플로우는 **주간** 리밋(12 레인 전멸, 저널 0건), 구현은
   **세션** 리밋(21 레인 사망, 반쪽 적용된 수정 레인 하나), Codex는 병렬 3건 × ultra로 10분 만에 소진.
   살아남는 법: `resumeFromRunId`(완료 레인 캐시), 죽은 수정 레인은 progress §8을 읽고 **적용된 항목을
   감사한 뒤 빠진 것만**(프롬프트에 그 절을 넣었더니 FIX 1–13 적용 확인 후 FIX 14만 돌았다), Codex는
   순차·소형 프롬프트.
2. 🔴 **`main`이 배치 도중 움직였다**(`7fa6796` → `fafabea`, 오너 세션의 외부 PR 병합). 겹침은
   `citations.lock.json`(3 브랜치)과 #238의 `tui/shell.py`·`cli/agent_context.py`. rebase 뒤
   `check_citations.py --fix` 재실행이 필수.
3. **`/usr/bin/bash`는 usr-merge된 ubuntu-latest에 실존한다** — "spawn 못 하는 경로"의 표본으로 쓰면
   Linux 레그만 빨갛다(darwin 초록). `tmp_path` 기반 가짜 경로로.
4. **PowerShell 프로필은 값을 오염시킨다** — `-NoProfile` 없이는 프로필의 stdout이 API 키 앞에
   붙는다(실측 `profile-banner\nsk-…`). `-NonInteractive`의 `Read-Host`는 `stdin=DEVNULL` 아래서
   0.45–0.54 s에 프롬프트 텍스트를 **값 안에** 넣고 돌아온다 — "거부된다"가 아니다.
5. **ENOEXEC/EINVAL에는 OSError 서브클래스가 없다** — `except (FileNotFoundError, …)` 튜플은 `sh.cmd`
   셤이 내는 WinError 193에서 체인을 중단시킨다. errno 허용목록으로 분류(#243은 bash.py의 같은 구멍).
6. **`settings.json`의 병합 읽기가 행을 거짓말하게 한다** — 프로젝트 `false` + 전역 `set_…(True)` →
   getter가 `False`. live 행의 getter는 전역 셀만 읽는다(#238), 그리고 `/settings` 도움말은 78셀에서
   조용히 잘린다(22행 중 14가 초과 — #245).
7. **정지·취소 케이스는 창이 줄면 공허해진다** — #232가 성공 drain을 0.1 s로 줄이자 #222의 케이스
   8b(0.3 s 뒤 abort)는 `exec`이 이미 돌아온 뒤 abort를 보냈다. 수다 홀더로 창을 유지하고
   `assert not task.done()`을 abort 직전에.
8. **삭제해도 스위트가 초록인 보호는 보호가 아니다** — 이번 리뷰가 잡은 것: `_run_shell_command`의
   `break`(후보마다 명령이 돌아 마지막 stdout이 값), `windows_command_shells`의 `path is not None`
   가드(호스트 `/bin/sh` 누출), bash 사이트의 deadline 항, `stdin=DEVNULL`, 완성기 기본 seam, `finally`의
   `_finish()`. 전부 케이스를 추가해 핀했다.
9. **`awk 'length>N'`은 바이트를 센다** — em dash가 3바이트라 100열 검사가 틀린다. 문자 수로 재라.
10. **`abort._finish()`를 `._finished`로 읽으면 (d)절이 reaped 경로에 진입하자마자 발화한다** — 설계의
    변이 (d) 예측 arm이 거꾸로였다(진술은 맞고 arm만 틀림). 변이표는 실행 결과로 고쳐 적었다.
11. **`SendMessage` 금지 절이 효과 있었다** — 이번 배치는 레인이 오케스트레이터에게 묻지 않고
    ORCHESTRATOR STEP으로 적었다(이슈 7건, 보드). 대신 이슈 번호를 미리 파서 프롬프트에 주입했다.
12. **워크플로우 규모(이번 배치)**: 설계 65·8.1 M·78 min, 구현 117·13.5 M·186 min(리밋 재개 포함).
    설계 문서가 664–770줄로 커졌다 — 비판 21–31건의 해결을 담으면 250줄이 안 된다. 다음엔 §H 측정표를
    별도 파일로 뗄 것.

## 4. 반증된 것 — 다시 믿지 말 것

- ❌ "`_finish()`를 reap으로 옮기면 충분하다"(#230 rev 1) — 헬퍼는 살지만 호출은 cap까지 1.5 s를 더
  기다린다; (d)절이 필요했다.
- ❌ "타임아웃 레그의 `_end_the_tree` 뒤에는 항상 reap돼 있다" — 10회 중 1회 미reap(가드 필요).
- ❌ "Pi의 uncapped idle 규칙으로 충분하다"(#232) — 50 ms 수다 홀더가 5.08 s까지 끈다(DOC-1). cap 필수.
- ❌ "`timeout > 0` 가드로 `proc.wait(0)`의 raise를 막아야 한다" — `wait(0)`은 exit한 자식에 25 µs로
  0을 돌려준다; 가드는 #221 cap을 20배 느슨하게 만들었을 것.
- ❌ "성공 drain 변경은 kill 경로도 빠르게 한다"(#232 README 초안) — kill 레그는 1.109 → 1.107 s,
  움직인 것은 성공 레그뿐. 그리고 "Aelix가 다른 모든 곳에서 쓰는 규칙"도 거짓(세 사이트가 여전히 EOF).
- ❌ "Pi HEAD는 win32에서 `POWERSHELL_ARGS`로 `!command`를 돌린다"(#227 이슈 본문) — 그건 Pi의
  `powershell` *도구*; `executeWithConfiguredShell`은 `getShellConfig()`(Git Bash → `bash.exe` →
  throw → `execSync` = cmd.exe).
- ❌ "`-NonInteractive`가 `Read-Host`를 거부한다" — `stdin=DEVNULL`에선 EOF로 즉시 돌아오며
  프롬프트 텍스트가 값에 섞인다.
- ❌ "`parametrize(sorted(rc._NOT_A_RUNNABLE_SHELL))`이 errno 목록을 핀한다" — 자기참조라 그 변이를
  통과시킨다(6 passed). 리터럴 목록으로.
- ❌ "`--no-ignore-vcs`가 'git이 무시하는 것 보이기'다"(#238) — `.ignore`/`.fdignore`는 남는다;
  `--no-ignore`만 walk 집합과 같다.
- ❌ "TTL 캐시라 토글이 2 s 뒤 반영되면 된다" — 캐시 키에 플래그를 넣으면 다음 키 입력에 반영;
  없으면 2.05 s stale.
- ❌ "`get_respect_gitignore`는 병합된 설정을 읽어야 한다" — 프로젝트 셀이 있으면 행이 거짓말한다.
- ❌ "설계 문서는 250줄이면 된다" — 이번 넷은 664–770줄이 됐고 줄이면 결정이 지워졌다.
